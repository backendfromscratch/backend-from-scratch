## The problem

Imagine the shop's API is already live. One Saturday, a customer writes to Luis: “when I paid I got a screen full of weird lines, something like `at file:///Users/ana/backend-course/…`.” That customer has seen the server's insides: its folders, its libraries and the line that failed. They're no use to the customer; to someone looking for a way to attack the shop, they are.

And Ana doesn't know what happened: her terminal has hundreds of lines of free text, and none of them says which one was that customer's.

The server has to fail well: for the customer, a short message and a reference number; for Ana, every detail in the <Term id="log">log</Term>, with that same number.

## The analogy

<Analogy>

Think of a restaurant. A cook burns a sauce. The waiter doesn't bring the pan to the table: he says “there's been a problem with your dish; your order is number 41.” In the kitchen, the head chef writes in his notebook: “order 41, 9:14 p.m., sauce burned on burner 3.”

If the customer complains, they give the order number, and with it the note is found. And a problem a cook can't solve ends up with the head chef, who doesn't let a sauce close the restaurant.

<div slot="limits">

- In a restaurant without a head chef, a burned sauce only spoils one table. In Node, an error nobody catches shuts down the whole program, and leaves every client without service at once.
- The notebook is read by a person. A log is also read by programs, and that's why every line follows a fixed format.

</div>

</Analogy>

This program reads an order that arrived cut off. `JSON.parse` turns <Term id="json">JSON</Term> text into data (you saw it in [“JavaScript”](/en/phase-3/javascript-for-backend/)):

- **The `1` at the end** is the <Term id="exit-code">exit code</Term> from [lesson 3 of Phase 1](/en/phase-1/pipes-and-redirection/): something failed.

### throw throws an error, try and catch catch it

An error can also be thrown on purpose, as in this new shop <Term id="route">route</Term>:

<ProjectCode file="shop-api/08-errors-and-logs/src/app.ts" region="error-route" />

- `new Error('…')` creates an error with its message. Node adds the stack trace to it at the moment it's created.
- `throw` throws it: the function stops there, and the error goes up to whoever called it, and so on upward, until someone catches it.

To catch it, the code that might fail goes inside a `try`, and what to do if it fails goes in a `catch`:

```ts title="catch.ts"
try {
  const order = JSON.parse('{"productId": 1, "quantity": ');
  console.log('Order read:', order);
} catch (error) {
  if (error instanceof Error) console.log('Could not read it:', error.message);
}
console.log('The program goes on');
```

`node catch.ts` prints `Could not read it: Unexpected end of JSON input` and then `The program goes on`: the error happened in the `try`, the program jumped to the `catch` and kept going.

`error` is whatever was thrown, and `throw` can throw anything. That's why its <Term id="type">type</Term> is `unknown` ([“TypeScript”](/en/phase-3/typescript-with-node/)), and `error instanceof Error` checks that it's an `Error` before reading its `message`.

### With async, the error arrives at the await

An `async` function returns a <Term id="promise">promise</Term>, a value that will arrive later. If the function fails, it doesn't throw the error right away: the promise arrives with the error instead of the value. `await` waits for that promise and, if it brings an error, throws it on that line, where the `catch` sees it:

```ts title="async.ts"
async function loadOrder(id: number) {
  throw new Error(`Order ${id} does not exist`);
}

try {
  await loadOrder(7);
} catch (error) {
  if (error instanceof Error) console.log('Could not find it:', error.message);
}
console.log('The program goes on');
```

`node async.ts` prints `Could not find it: Order 7 does not exist` and `The program goes on`. Now delete the `await` on line 6 and run it again:

### Why a server doesn't go down with every error

In [lesson 4](/en/phase-3/node-http-server/), without a <Term id="framework">framework</Term>, the `.catch` in `createServer` answered `500` if something failed. Without it, a `throw` in a route brings down the whole process, and the next request, whoever it comes from, gets `Couldn't connect to server`.

Hono, like Express or Fastify, wraps each request in its own `try`/`catch`. If a route throws an error, Hono catches it, answers `500` with the text `Internal Server Error`, writes the stack trace in the terminal and keeps serving everyone else.

A program dying isn't always bad: if it fails at startup (the port is taken, the configuration is incomplete), it's better for it to end and say why. In production it starts again on its own: `Restart=always` in systemd does that ([lesson 6 of Phase 1](/en/phase-1/systemd-services-and-apt/)), and Docker will do it in Phase 7.

### A 500 that gives nothing away

That `500` isn't JSON, like the rest of the API, and the stack trace Hono writes in the terminal doesn't say which request it belongs to. This changes that:

<ProjectCode file="shop-api/08-errors-and-logs/src/app.ts" region="errors" />

- **`app.notFound`** answers when no route matches: a `404` in JSON.
- **`app.onError`** receives any error that escapes from a route or a <Term id="middleware">middleware</Term>, and `c`, the request's context ([lesson 5](/en/phase-3/express-hono-fastify/)).
- **`HTTPException`** is the error Hono throws when it already knows which code applies, like the `400` for a body that isn't JSON. In [lesson 7](/en/phase-3/zod-validation/) it came as plain text; now it comes out in JSON, with its code (`error.status`) and Hono's text, meant for the client, in `detail`.
- **`log.error(…)`** writes down the whole error, with its stack trace, and the request's id.
- **`c.json(…, 500)`** gives the client only `Internal server error` and the id.

Neither the message nor the stack trace of an unexpected error goes out to the client: they would show anyone your folders, libraries and versions. The `500` is enough, “I failed” ([status codes](/en/phase-2/http-status-codes/)), plus a number to complain with.

### An id for every request

The id is set by a Hono middleware, `requestId`, which goes first:

<ProjectCode file="shop-api/08-errors-and-logs/src/app.ts" region="layers" />

`requestId()` gives each request a random text that never repeats, like `bf209234-574b-452c-9969-de31923346e2`. It stores it in the context, where `c.get('requestId')` gets it from, and returns it in the `X-Request-Id` <Term id="header">header</Term>.

It goes before `requestLog` so the log already has the id: order matters ([lesson 6](/en/phase-3/what-is-middleware/)).

### Structured logs: one JSON line per event

In [Phase 1](/en/phase-1/pipes-and-redirection/) you searched the practice log for `500`s with `grep '" 500 '`, knowing the code was field 9. A <Term id="structured-log">structured log</Term> gives each piece of data a name. This is what a line of the shop's log looks like now:

```json
{"level":30,"time":1791890346764,"pid":177,"hostname":"laptop","requestId":"bf209234-574b-452c-9969-de31923346e2","method":"GET","path":"/error","status":500,"ms":2,"msg":"request"}
```

It's written by pino, a <Term id="package">package</Term> that does only this. The project creates a single `log` with `pino(…)` and uses it everywhere:

<ProjectCode file="shop-api/08-errors-and-logs/src/log.ts" />

Lesson 6's request log wrote a sentence with `console.log`; now it writes data:

<ProjectCode file="shop-api/08-errors-and-logs/src/middleware/request-log.ts" region="request-log" />

- `log.info(data, message)` writes a line of level `info` with the object's data and the message in `msg`.
- pino adds `level`, the level as a number; `time`, the milliseconds since 1970; `pid`, the process number ([lesson 5 of Phase 1](/en/phase-1/linux-processes-and-signals/)), and `hostname`, the computer.
- An error, like the one in `log.error({ err: error })`, is written with its type, its message and its stack trace: `type`, `message` and `stack`.

### Levels: how much the log says

Every line has a <Term id="log-level">level</Term>, and the log has a minimum: it only writes the lines of that level or a higher one.

| Level | Number | What for |
|---|---|---|
| `fatal` | 60 | The program can't go on |
| `error` | 50 | Something failed, like the `500` from `/error` |
| `warn` | 40 | Odd, but not a failure: a warning |
| `info` | 30 | The usual: startups, requests |
| `debug` | 20 | Details for hunting a bug while you code |
| `trace` | 10 | Even more detail |

`silent` writes nothing. The minimum comes from the <Term id="environment-variable">environment variable</Term> `LOG_LEVEL`, which `log.ts` passes to pino as `level`: `info` day to day, `debug` when you're hunting a bug and `silent` in the tests.

### The configuration is checked at startup

Until now, the admin token was written in the code, and a <Term id="secret">secret</Term> can't live there ([environment variables](/en/phase-1/environment-variables/)). Now it comes from the environment, like the port and the log level:

<ProjectCode file="shop-api/08-errors-and-logs/src/config.ts" region="config" />

- **`configSchema`** is a Zod <Term id="schema">schema</Term>, like the ones in lesson 7, for the environment variables.
- **`z.coerce.number()`** turns `PORT` into a number, because an environment variable always arrives as text; `.default(3000)`, if there isn't one. `z.enum` accepts only one of the levels.
- **`ADMIN_TOKEN`** has no default value and is at least 16 characters long.
- **`safeParse(process.env)`** checks everything at once. If something fails, it writes each problem with `console.error`, which goes to <Term id="stderr">stderr</Term>, and `process.exit(1)` ends with code 1.

With `parse`, which throws an exception instead of returning the result, it would also end, but with a stack trace instead of a clear sentence. And it's better to refuse to start than to fail in the middle of the night, with the first request that needs the token.

## You have already seen it

- **Error pages with a code.** “Something went wrong. Reference: 7F3A…”: that's your request's id, the one support looks up in their log.
- **The `cf-ray` header** from backenddesdecero.com, in [lesson 4 of Phase 2](/en/phase-2/http-headers/), is the id Cloudflare gives each request; GitHub uses `x-github-request-id`. They're in [DevTools](/en/phase-2/#before-you-start-devtools), in the response headers.
- **The DevTools console** shows a page's errors with their stack trace, like the one from `crash.ts`.

## Common mistakes

- **Sending the client the message or the stack trace of an unexpected error.** You're showing your code to anyone. For the client, a fixed message and the id; everything else, to the log.
- **An empty `catch`.** `catch {}` makes the error disappear: nobody finds out. If you catch an error, at least write it in the log.
- **Forgetting the `await`.** The `try` ends before the error arrives, and in a server that uncaught error can bring the process down.
- **Writing secrets in the log.** A log is stored, copied and read by many people: never the `Authorization` header, a token or a password.

## Summary

- `throw` throws an error and `try`/`catch` catches it; with `async`, only if you wait for it with `await`. An error nobody catches ends the program with code 1.
- Hono catches the errors of each request. With `onError`, the client gets a `500` with no stack trace and with an id (also in `X-Request-Id`), and the log gets the stack trace with that id.
- A structured log is one JSON line per event: you read it, filter it with `grep` and ask it questions with `jq`.
- `LOG_LEVEL` sets the minimum level: `info` day to day, `debug` to hunt a bug and `silent` in the tests.
- The configuration comes from environment variables and is checked with Zod at startup: if something is missing, the server doesn't start and says why.
