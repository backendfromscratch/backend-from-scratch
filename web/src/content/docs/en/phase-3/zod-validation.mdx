## The problem

Imagine someone sends strange orders to the shop's API with `curl`. This is what the API from [lesson 6, “Middleware”](/en/phase-3/what-is-middleware/) answers:

```sh
curl -w '\n' --json '{"productId":1,"quantity":-3}' localhost:3000/orders
curl -w '\n' --json '{"productId":1,"quantity":"lots"}' localhost:3000/orders
curl -w '\n' --json '{"productId":1}' localhost:3000/orders
```

```
{"id":1,"productId":1,"quantity":-3,"status":"pending"}
{"id":2,"productId":1,"quantity":"lots","status":"pending"}
{"id":3,"productId":1,"status":"pending"}
```

Three orders saved: minus three T-shirts, “lots” of T-shirts and one with no quantity. None of them makes sense, and the API accepted them all.

In [Phase 0](/en/phase-0/what-is-the-backend/#why-the-frontend-cant-do-it-all) you saw the golden rule of the backend: **never trust the <Term id="client">client</Term>**. The website's form can check the quantity, but anyone can skip it and write the request by hand, as you've just seen. In this lesson, your server starts following that rule.

## How it really works

### TypeScript's types disappear when the code runs

In [lesson 4](/en/phase-3/node-http-server/), you added `as { productId: number; quantity: number }` to an order's body, and in lessons 5 and 6, the annotation `data: { … }`. Both promise TypeScript that the body has that shape, and TypeScript believes you without checking.

And Node [erases the types before running](/en/phase-3/typescript-with-node/#node-erases-the-types-when-it-runs). That's why `npm run check` doesn't complain about the API from lesson 6, which still saves `"lots"` as a quantity.

| | TypeScript | A schema |
|---|---|---|
| When it checks | While you write the code | Every time a request arrives |
| What it checks | That your code uses the data correctly | That the data arriving is what you expect |
| If something's wrong | The editor marks it in red | The server answers with an error |

You need both. **TypeScript watches your code; the schema watches the data from outside.**

### A schema describes the shape of the data

A <Term id="schema">schema</Term> is a description of what some data has to look like: which fields it has, whether each one is a number or text, and which values are accepted. A program compares what arrives against it and tells you whether it matches or what's wrong. That's <Term id="validation">validation</Term>.

One of the most used tools for this in TypeScript is Zod. Install it in the project folder, `~/backend-course/phase-3/shop-api`, along with its connector for Hono, the <Term id="framework">framework</Term> from [lesson 5](/en/phase-3/express-hono-fastify/):

<TryIt
  title="In the REPL: a schema and two orders"
  lang="js"
  cmd={`const { z } = await import('zod')
const orderSchema = z.object({ productId: z.number(), quantity: z.number().int().min(1) })
orderSchema.safeParse({ productId: 1, quantity: 2 })
orderSchema.safeParse({ productId: 'one', quantity: -3 }).error.issues`}
  output={`undefined
undefined
{ success: true, data: { productId: 1, quantity: 2 } }
[

    expected: 'number',
    code: 'invalid_type',
    path: [ 'productId' ],
    message: 'Invalid input: expected number, received string'
  },
  {
    origin: 'number',
    code: 'too_small',
    minimum: 1,
    inclusive: true,
    path: [ 'quantity' ],
    message: 'Too small: expected number to be >=1'
  }
]`}
>

Word by word:

- `const { z } = …` takes the piece called `z` out of Zod and keeps it under that name. `z` is all of Zod: each piece of a schema is asked for with `z.something`.
- `z.object({ … })` describes an <Term id="object">object</Term> and its fields. `z.number()` says “a number,” and each dot adds a rule: `.int()`, a whole number, and `.min(1)`, at least 1.
- `safeParse` compares some data with the schema. If it matches, it returns `success: true` and the data in `data`.
- If it doesn't match, `success` is `false` and `error.issues` is the list of problems: one per field that fails.

Each problem says what happened (`code`), a message (`message`) and, above all, **where**: `path`, the field that fails.

Zod also has `parse`, which returns the data or, if it doesn't match, throws an error, an <Term id="exception">exception</Term>: you'll see it in [lesson 8](/en/phase-3/node-errors-and-logging/). In a server, `safeParse` lets you decide what to answer.

</TryIt>

### Messages in plain English, written by you

Zod's messages are in English, but they're written for programmers: “expected number to be >=1”. Look at the ones for an order with no product and half a T-shirt:

<TryIt
  title="In the REPL: Zod's own messages"
  lang="js"
  cmd={`orderSchema.safeParse({ quantity: 2.5 }).error.issues.map((p) => p.message)`}
  output={`[
  'Invalid input: expected number, received undefined',
  'Invalid input: expected int, received number'
]`}
>

The messages are taken out with `map` ([lesson 2](/en/phase-3/javascript-for-backend/#choosing-and-transforming-a-list-filter-and-map)).

Someone using the shop doesn't know what “undefined”, “int” or “>=1” mean. Zod also comes with translations into other languages (`z.locales`), but they translate these same phrases.

</TryIt>

That's why the project writes its own messages, for the people who will read them. This is an order's schema, in a new file, `src/schemas.ts`:

<ProjectCode file="shop-api/07-validation/src/schemas.ts" region="order" />

Word by word:

- `export` lets other files use the schema, as in [lesson 3](/en/phase-3/typescript-with-node/).
- `z.number({ error: '…' })` is “a number,” with the message for when it isn't one. A missing field isn't a number either, so it gets the same message.
- `.int('…')`, `.min(1, '…')` and `.max(10, '…')` are the rules, each with its message. The maximum of 10 is the shop's decision: nobody orders a hundred hoodies at once.
- `z.infer<typeof orderSchema>` takes the TypeScript type out of the schema: `{ productId: number; quantity: number }`. Between `<` and `>` goes where the type comes from, and `typeof` means here “the type of this value.”

The last line saves you from writing the shape twice, once for TypeScript and once for Zod. **The schema is the only source**: if you add a field to it, the type has it too.

### A middleware validates before the route runs

In [lesson 6](/en/phase-3/what-is-middleware/) you saw that a <Term id="middleware">middleware</Term> is a layer the request goes through before it reaches the route, and that it can answer without letting it continue. Validating is exactly that. This is the project's middleware, in `src/middleware/validate.ts`:

<ProjectCode file="shop-api/07-validation/src/middleware/validate.ts" region="validate" />

Word by word:

- `zValidator` is Hono's connector with Zod. It reads the part of the request you tell it (`target`), compares it with the schema, like `safeParse`, and gives you the result.
- `target` can be `'json'` (the <Term id="request-body">body</Term>), `'param'` (the <Term id="route-parameter">route parameters</Term>, like the `:id`), `'query'` (the <Term id="query-string">query string</Term>), and also the headers or the cookies.
- What goes between `<` and `>`, with the two types from the `import type`, tells TypeScript what `target` and `schema` can be: a part of the request and a Zod schema. Thanks to that, the route will know later what type the data has. You can read it as `validate(target, schema)`.
- The function at the end gets the `result`. If it isn't a success, it turns each problem into `{ field, problem }`, with `path.join('.')` so that a field inside another one, like `[ 'address', 'street' ]`, reads `address.street`. And it answers `422`: it could read the request, but the data is no good.
- If everything matches, it returns nothing, and the request goes on to the route.

Without that function, `zValidator` would answer `400` with the whole Zod error, `{"success":false,"error":{"name":"ZodError",…`, with the list of problems packed into a single string of text, hard to read for whoever uses your API.

### The route gets the data already checked

With `validate`, the orders route looks like this:

<ProjectCode file="shop-api/07-validation/src/app.ts" region="new-order" />

- `validate('json', orderSchema)` goes between the route and its function, like `adminOnly` in lesson 6. If the body doesn't match, the route's function doesn't even run.
- `c.req.valid('json')` returns the data already checked, and TypeScript knows its type: no more `as` or annotation needed. This time the promise is true. `const { productId, quantity } = …` takes out those two values, like `const { z }` in the REPL.

Notice the check that's left: `findProduct`. An order for product 99 has the perfect shape and passes the schema. But the shop has no product 99, and the route answers `422`, as it would to a value that's no good. It isn't a `404`: `/orders` exists, and what's wrong is a value in the body.

They're two different questions:

- **Does the data have the right shape?** The schema answers it, without knowing anything about the shop.
- **Does it make sense for the shop right now?** Whether the product exists or there's stock depends on the data at that moment. The route answers it.

### What comes in the path and the query string is always text

In `/products/2`, the `2` arrives as the text `"2"`, and in `?max=10`, the `10` too. A URL is text. So `z.number()` would always reject the parameters. That's what `z.coerce` is for:

<TryIt
  title="In the REPL: the text “2” and the number 2"
  lang="js"
  cmd={`z.number().safeParse('2').success
z.coerce.number().safeParse('2')
z.coerce.number().safeParse('abc').success`}
  output={`false
{ success: true, data: 2 }
false`}
>

`z.coerce.number()` turns the text into a number before checking it: `'2'` passes and arrives as `2`. `'abc'` isn't any number, and it fails.

</TryIt>

### 422 if the data is no good; 400 if it can't even be read

This API follows the rule from [Phase 2's lesson 3](/en/phase-2/http-status-codes/#the-codes-that-matter): with a `400`, the server couldn't even read the request; with a `422`, it read it, and what it asks for makes no sense.

| What reaches `POST /orders` | Code | Who answers |
|---|---|---|
| A body that isn't JSON | `400` | Hono, before the schema sees it |
| `{"productId":1,"quantity":-3}` | `422` | `validate`, with `details` |
| `{"productId":99,"quantity":1}` | `422` | The route, without `details` |

The `400` for a broken body is written by Hono on its own, and in text, not JSON: `Malformed JSON in request body`. In [lesson 8](/en/phase-3/node-errors-and-logging/) you'll turn it into JSON, like the rest of the API.

Not every API makes the distinction: [Stripe](https://docs.stripe.com/api/errors), or `zValidator` itself without your function, answers `400` to any data that's no good, because `400` is the general client error. What matters is always following the same criterion and having the body say what's wrong.

## You have already seen it

- **Forms that mark a field in red** before you send them (“This field is required”) validate in the browser. It's convenient for whoever is typing, but the server checks again, because that check can be skipped.
- **The errors that arrive after you send**, like “That ZIP code doesn't exist,” come from the server. If you open DevTools ([how to open them](/en/phase-2/#before-you-start-devtools)), in the **Network** tab you'll see a `400` or a `422` with a list of fields, like your `details`, which the page uses to mark each one.

## Common mistakes

- **Validating only in the form.** Anyone can send the request with `curl`, without going through the website.
- **`z.number()` for a route or query string parameter.** They always arrive as text and would always fail. Use `z.coerce.number()`.
- **Forgetting `Content-Type: application/json`.** With `curl -d` and no `-H`, Hono doesn't read the body as JSON and every field fails with “Must be a number”. Use `--json`.
- **Using `parse` in a route on its own.** If the data doesn't match, it throws an error, and the client gets a `500` instead of a `422`. In a server, use `safeParse`, or a middleware like `validate`.

## Summary

- TypeScript's types are erased when the code runs: they don't protect you from what comes over the network. A schema does, because it checks the data every time it arrives.
- With Zod, `z.object` describes the shape, each dot adds a rule and `safeParse` says whether it matches or what's wrong, field by field. `z.infer` takes the type from the same schema.
- The `validate` middleware checks the body, the path or the query string, and if something doesn't match it answers `422` with each problem, without reaching the route. A body that isn't JSON gets a `400` from Hono: it couldn't even be read.
- What comes in the URL is always text: `z.coerce` converts it before checking it.
- The schema checks the shape; the rules that depend on the shop's data, like whether the product exists, are checked by the route.

`/products/2` and `/products/abc` would fail the same way. With `z.coerce.number()`, `"2"` is turned into `2` before it's checked.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="POST /orders gets a body cut in half, which isn’t valid JSON. What does this lesson’s API answer?"
  review="422 if the data is no good; 400 if it can't even be read"
>

<QuizOption text="A 422 with details: the schema sees the quantity is missing.">

The schema never sees it: first the JSON has to be read, and it can't be. The `422` is for data that was read and is no good.

</QuizOption>

<QuizOption text="A 400, from Hono: the schema never even looks at it." correct>

Hono can't read the body and answers `400` before `validate` does, with `Malformed JSON in request body`: the server couldn't even read the request.

</QuizOption>

<QuizOption text="A 500: broken JSON makes the whole server fail.">

Hono catches that failure and answers `400`: the error is the client's, and the server keeps running. A `500` would say “I failed.”

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Someone orders 2 units of product 99, which the shop doesn’t have. Who stops it?"
  review="The route gets the data already checked"
>

<QuizOption text="Nobody: if the schema lets it through, the data is valid and the order is created.">

The schema only says the data has the right shape. That's why the route still checks that the product exists.

</QuizOption>

<QuizOption text="The schema: z.number() only accepts the numbers of products that exist.">

`z.number()` knows nothing about the shop: it accepts any number. Which products there are depends on the data at each moment.

</QuizOption>

<QuizOption text="The route’s check, with findProduct." correct>

99 passes the schema. Whether the product exists is a rule of the shop: the route checks it, and answers `422` without `details`.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="You add a note field to the order’s schema, an optional text. What else do you have to change for TypeScript to know about it?"
  review="Messages in plain English, written by you"
>

<QuizOption text="Nothing: the OrderInput type comes from the schema with z.infer." correct>

`z.infer` takes the type from the schema every time TypeScript looks at it. A new field in the schema is already in the type.

</QuizOption>

<QuizOption text="The OrderInput type, by hand: otherwise the editor will mark an error.">

With `z.infer`, the type isn't written by hand: there aren't two versions that can stop matching.

</QuizOption>

<QuizOption text="The validate middleware, which has to name every field it checks.">

`validate` doesn't know which fields there are: it gets the schema and passes it to Zod. It works the same for orders, products and parameters.

</QuizOption>
