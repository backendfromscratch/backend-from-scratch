In Phase 2 you were the one answering, but by hand, with `nc`, or with an nginx configuration that said which text to return at each address. In this phase you write the <Term id="server">server</Term>: a program of your own that receives each <Term id="request">request</Term>, reads it and decides what to answer.

It's the first phase with code. You don't need to have ever programmed: two of its lessons teach the language from scratch, and every block of code is explained piece by piece.

## What changes when you write the code

Remember Ana and Luis's shop from Phase 2. Its nginx had an address, `/api/orders`, that acted as the <Term id="api">API</Term> for the shop's website. It always answered the same thing, `{"orders":[]}`, no matter what you sent it. You could send it an order with a `POST` and get a `200`, but nobody saved it: it was a fake API.

A configuration can only choose among the things nginx already knows how to do. With code, the server does whatever you write: save the order, check that the quantity is a number, warn you if the product doesn't exist. It's the same HTTP conversation as in Phase 2; what changes is who decides each response.

| With the nginx configuration | With your own code |
|---|---|
| Each address returns a fixed text | The response depends on what comes in the request |
| `POST /api/orders` answers `200` and saves nothing | `POST /orders` saves the order and returns its number |
| Odd data gets through without anyone looking at it | You check every piece of data and answer `422` with a clear message |
| If something fails, it's nginx's fault | If something fails, it's your fault, and you find it in your <Term id="log">logs</Term> |

**That last row is the price:** everything nginx used to decide, you decide now, including what happens when something goes wrong. That's what lessons [7, “Validation”](/en/phase-3/zod-validation/) and [8, “Errors and logs”](/en/phase-3/node-errors-and-logging/) are about.

## What you will build

By the end of the phase, the shop will have a real API, written by you and running on your computer. This is how it answers a well-formed order and one with an impossible quantity (we captured it with the final version of the project and Node 26, and trimmed some headers with `…`):

```text
HTTP/1.1 201 Created
content-type: application/json
location: /orders/1
…

{"id":1,"productId":2,"quantity":3,"status":"pending"}
```

```text
HTTP/1.1 422 Unprocessable Entity
content-type: application/json
…

{"error":"The data is not valid","details":[{"field":"quantity","problem":"At least 1"}]}
```

The first one creates order number 1, three mugs, and its `location` header says where to look it up: `/orders/1`. The second one asked for zero: the server could read the request, but the data makes no sense, and it rejects it with a `422` that says which field is wrong and why. If the body weren't even JSON, it would answer `400`. You know all three codes from [lesson 3 of Phase 2](/en/phase-2/http-status-codes/#the-codes-that-matter), which calls the `422` by its current name, *Unprocessable Content* (Node still writes the old one). Now you're the one sending them.

These are the addresses it will have:

| Request | What it does |
|---|---|
| `GET /products` | The list of products, in <Term id="json">JSON</Term>. With `?max=20`, only the ones that cost €20 or less |
| `GET /products/2` | One product, or a `404` if it doesn't exist |
| `POST /products` | Adds a product. Only someone with the admin key can do it |
| `GET /orders` | The orders placed |
| `GET /orders/1` | One order, or a `404` if it doesn't exist |
| `POST /orders` | Creates an order, after checking every piece of data |

The data is kept in the program's memory: if you stop the server, the orders disappear. Keeping them for good in a database is Phase 5.

## What you will learn

By the end of this phase you'll be able to write a small HTTP server and understand every line. You'll know:

- What <Term id="nodejs">Node.js</Term> is and how it runs JavaScript and TypeScript outside the browser.
- How to read and write the JavaScript and TypeScript a server needs, even if you've never programmed before.
- How to write a server with no outside help, with what comes with Node, and see there's no magic inside: Phase 2's request, now in variables.
- What a <Term id="framework">framework</Term> like Hono or Express gives you, and what <Term id="middleware">middleware</Term> is.
- Never to trust what the client sends, and to check all of it.
- How to handle errors without showing your secrets, and how to write logs a machine can read.
- What the <Term id="event-loop">event loop</Term> is and why a single slow request can hold up all the others.

## Before you start: Node.js with nvm

Node.js is the program that runs JavaScript outside the browser; lesson 1 tells you what it is on the inside. Here you just install it, and you do it with **nvm** (*Node Version Manager*): a program that installs Node and lets you switch versions with one command.

Why not the installer from Node's website? For two reasons:

- **Each project asks for its own version.** This course uses Node 26, which becomes the long-term support (LTS) version on October 28, 2026. A project at work may ask for another one, and with nvm you switch in a second.
- **It doesn't touch the system.** nvm installs everything in your home folder, without `sudo`.

nvm works the same on macOS, on Linux and on WSL. If you already have Node installed some other way, that's fine: nvm puts itself first in your `PATH`, the list of folders where the shell looks for programs ([lesson 7 of Phase 1](/en/phase-1/environment-variables/)).

### 1. Install nvm

nvm is installed with a <Term id="script">script</Term> that adds a few lines to the file your shell reads when it starts: `~/.zshrc` on the Mac and `~/.bashrc` on Linux and WSL. **On a Mac,** if that file doesn't exist, nvm doesn't know where to write. Create it first, just in case (if it already exists, nothing happens to it):

<TryIt title="On the Mac only" cmd="touch ~/.zshrc">

`touch` creates an empty file if it doesn't exist, and if it does, leaves it as it was. It doesn't write anything. On Linux and WSL you don't need it: `~/.bashrc` is there from the start.

</TryIt>

Now, the installation. It's the command nvm itself gives on its page, with version 0.40.8:

<TryIt
  title="Install nvm"
  cmd="curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh | bash"
  output={`  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
100 17883  100 17883    0     0   367k      0 --:--:-- --:--:-- --:--:--  371k
=> Downloading nvm from git to '/home/ana/.nvm'
=> Cloning into '/home/ana/.nvm'...
* (HEAD detached at FETCH_HEAD)
  master
=> Compressing and cleaning up git repository

=> Appending nvm source string to /home/ana/.bashrc
=> Appending bash_completion source string to /home/ana/.bashrc
=> Close and reopen your terminal to start using nvm or run the following to use it now:

export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && \\. "$NVM_DIR/nvm.sh"  # This loads nvm
[ -s "$NVM_DIR/bash_completion" ] && \\. "$NVM_DIR/bash_completion"  # This loads nvm bash_completion`}
>

Word by word:

- **`curl -o-`** downloads the script and, instead of saving it to a file, writes it to the output (the `-` in `-o-` means “the screen”).
- **`|`** passes that output to the next command, as in [lesson 3 of Phase 1](/en/phase-1/pipes-and-redirection/).
- **`bash`** runs what it receives: the install script.

The output is from Ubuntu; in yours, the first line will have other speeds, and you can ignore the Git lines (`HEAD detached`, `master`). What matters are the two that start with `Appending`: nvm has added its lines to your `~/.bashrc`, or to your `~/.zshrc` on the Mac, with `/Users/ana` instead of `/home/ana`.

If you get `Profile not found`, nvm didn't find that file: run the `touch` from before and repeat the command.

</TryIt>

<Aside type="caution" title="A script you haven't read">

`curl … | bash` runs a program from the internet without you reading it first. Here you trust nvm, a well-known project that lives on GitHub, and the address pins the version: `v0.40.8` is always the same file. With a script from a website you don't know, do what you did in [Phase 2](/en/phase-2/): download it with `curl -O`, read it with `less` and run it afterward, if you're convinced.

</Aside>

### 2. Open a new terminal and check nvm

nvm is loaded from `~/.zshrc` or `~/.bashrc`, and the shell only reads that file when it starts. So **close the terminal and open another one**. Then:

<TryIt title="Is nvm there?" cmd="command -v nvm" output="nvm">

`command -v` says whether the shell knows a command. If it answers `nvm`, it's ready.

If it prints nothing, the shell hasn't loaded nvm: check that you opened a new terminal. If it still fails, look at the end of your `~/.zshrc` (or `~/.bashrc`) with `tail` ([lesson 2 of Phase 1](/en/phase-1/linux-file-commands/)): it must have the three `NVM_DIR` lines that showed up during the installation.

</TryIt>

### 3. Install Node 26

**On Linux and WSL,** first install `libatomic1`, a piece Node 26 needs and that WSL's Ubuntu doesn't include: without it, `nvm install` seems to go well, but `node` won't start. You install it with `apt` ([lesson 6 of Phase 1](/en/phase-1/systemd-services-and-apt/)): first the catalog, then the package. On the Mac you don't need it.

<TryIt
  title="On Linux and WSL only"
  cmd={`sudo apt update\nsudo apt install -y libatomic1`}
  output={`…
The following NEW packages will be installed:
  libatomic1
…
Setting up libatomic1:arm64 (14.2.0-4ubuntu2~24.04.1) ...`}
>

We trimmed the output (`…`). What matters is `Setting up libatomic1`: it's done. On most PCs you'll see `amd64` instead of `arm64`. If you already had it, apt says `libatomic1 is already the newest version`.

</TryIt>

<TryIt
  title="Install Node 26"
  cmd="nvm install 26"
  output={`Downloading and installing node v26.11.1...
Downloading https://nodejs.org/dist/v26.11.1/node-v26.11.1-linux-arm64.tar.gz...
######################################################################## 100.0%
Computing checksum with sha256sum
Checksums matched!
Now using node v26.11.1 (npm v11.20.0)
Creating default alias: default -> 26 (-> v26.11.1 *)`}
>

`nvm install 26` looks for the most recent version of Node 26 and installs it. Line by line:

- **`Downloading`:** it fetches Node from its official website, `nodejs.org`. The end of the name says which system and which processor it's for: on a Mac you'll see `darwin` instead of `linux`, and on most PCs, `x64` instead of `arm64`.
- **`Checksums matched!`:** nvm has checked that the file is identical to the published one, with a <Term id="hash">hash</Term>, the fingerprint Git uses to name each commit ([lesson 10 of Phase 1](/en/phase-1/git-internals/)). If the file had arrived broken or changed, it would stop here. On the Mac, this line may name a different tool (`shasum`).
- **`Now using node v26.11.1 (npm v11.20.0)`:** you have it, and with it <Term id="npm">npm</Term>, which comes included. You'll use it from lesson 1 on.
- **`default -> 26`:** it's the version every new terminal will have.

Your version numbers may be higher: Node publishes fixes every few weeks, and everything in this course works with any Node 26.

</TryIt>

### 4. Check the versions

<TryIt
  title="Node and npm"
  cmd={`node --version\nnpm --version`}
  output={`v26.11.1
11.20.0`}
>

Both commands print their version and finish. The first one must start with `v26`.

If you get another one, for example `v22`, that terminal is still using a Node you already had: open a new one, or type `nvm use 26`.

On Linux or WSL, if you get `error while loading shared libraries: libatomic.so.1`, you're missing `libatomic1`: install it as in step 3 and try again.

</TryIt>

## Before you start: the editor

Until now you've edited files with `nano`, inside the terminal. A project has many files, and a code editor helps you with them: it colors each part of the code, shows you all the folders at once and, above all, underlines mistakes while you type. In [lesson 3](/en/phase-3/typescript-with-node/) you'll see why that's worth so much.

The course uses **VS Code** (*Visual Studio Code*), from Microsoft: it's free, it works on all three systems and it's the most widely used. If you already have another editor you like, stick with it: the lessons only use VS Code for what the terminal doesn't show.

- **macOS and Linux:** download it from [code.visualstudio.com](https://code.visualstudio.com/) and install it like any other application.
- **Windows:** install it on Windows, not inside Ubuntu, and add its “WSL” extension (in the *Extensions* panel). With it, VS Code on Windows opens and edits the folders in your Ubuntu.
- **Language:** the lessons name the menus in English, as VS Code comes. If your system is in another language, VS Code will offer you its language pack.

The easiest way is to open the editor from the terminal, in the folder you're in, with `code .` (the dot is “this folder”, as in Phase 1). On Linux and WSL it works from the start. **On the Mac**, you first have to teach it to the shell: open VS Code, press <kbd>Cmd</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd>, type `shell command` and choose *Shell Command: Install 'code' command in PATH*.

## Try it: your first program

The goal: get Node to run a program you wrote and tell you which version it ran it with. It's the project's first file: a comment and two commands.

<ProjectCode file="shop-api/01-node/hello.js" />

Piece by piece:

- **The line that starts with `//`** is a comment: a note for whoever reads the code. Node skips it, just as nginx skipped the lines with `#`.
- **`console.log(…)`** writes in the terminal what's between the parentheses, and goes to a new line.
- **`'Hello from Node.js'`** is a piece of text. The quotes mark where it starts and where it ends: they aren't written on the screen.
- **The third line** uses backticks (`` ` ``), which let you put a value inside the text with `${…}`.
- **`process.version`** is the version of the Node that's running the program. `process` is the <Term id="process">process</Term> from [lesson 5 of Phase 1](/en/phase-1/linux-processes-and-signals/), seen from the inside.

Lesson 2 goes back over each of these pieces calmly. To create the file, in VS Code choose *File* › *New File…*, name it `hello.js` and type the three lines inside. Type them yourself instead of copying them: that's how you get used to the punctuation. Save with <kbd>Cmd</kbd> + <kbd>S</kbd> (<kbd>Ctrl</kbd> + <kbd>S</kbd> on Windows and Linux).

<TryIt
  title="Run it"
  cmd="node hello.js"
  output={`Hello from Node.js
You're using Node.js v26.11.1`}
>

`node` followed by a file name reads the file and runs what's inside, line by line. When it gets to the end, it finishes and gives you back the prompt.

Look at the second line: where the code said `${process.version}`, your version came out. You wrote the text; Node put that number there when it ran it.

If you get `Error: Cannot find module '…/hello.js'`, Node can't find the file in the folder you're in. Look at the path in the error: check with `pwd` that you're in `shop-api`, and with `ls` that the file is called `hello.js`, with no `.txt` at the end. If you get `SyntaxError`, a quote or a parenthesis is missing: compare your file with the one above, character by character.

</TryIt>

You now have a program that works. In [lesson 1](/en/phase-3/what-is-node-js/), this file becomes the first one of a real Node project.

## If you get stuck: each lesson's code

One missing comma is enough to stop a program from starting, and sometimes it's hard to find. That's why **each lesson's code can be downloaded**, just as it is at the end of the lesson, so you can compare it with yours.

Each lesson has its own, with its number in front: `01-node`, `02-javascript`, `03-typescript`… up to `09-event-loop`. You download them like this, from the phase's folder, so they don't get mixed up with your project. For example, lesson 1's:
