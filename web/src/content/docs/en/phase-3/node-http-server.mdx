## The problem

The shop's nginx, in [Phase 2](/en/phase-2/), had an address, `/api/orders`, that gave the same answer to everything: a `200` and `{"orders":[]}`. Imagine Luis sends an order for three mugs there. He gets a `200` and thinks it went well, but the order isn't anywhere: nginx didn't even read it.

And it can't. An nginx configuration says “at this address, answer this.” Taking an order means reading the <Term id="request-body">body</Term>, checking that the product exists, saving it and answering `201` with its number: it takes a program that decides on every <Term id="request">request</Term>.

In [lesson 1 of Phase 2](/en/phase-2/http-request-and-response/) you did that work by hand with `nc`. Now you write the program that does it for you, with only what comes with <Term id="nodejs">Node.js</Term>, no <Term id="framework">framework</Term> (the ready-made code almost every server uses). And you'll see there's no magic: they're the same lines of text, now in <Term id="variable">variables</Term>.

## The analogy

<Analogy>

Think of a company's mail. In the mail room they open each envelope and leave the letter on your desk with a slip: what it asks for (the method), which department it's for (the path) and who sends it (the headers). Next to it, a blank reply form.

You read, decide and fill in the form: a code (“done,” “that doesn't exist,” “we don't do that here”) and the content. The mail room sends it. Node.js is the mail room, and your code is the person at the desk: **you write every response.**

<div slot="limits">

- The content doesn't come inside the envelope: it arrives in chunks, and you have to put them together before reading it.
- The mail room doesn't check the letter. If someone asks for −5 mugs, it passes it on all the same.
- If you forget to send the reply, nobody warns you: whoever wrote is left waiting.

</div>

</Analogy>

- **`createServer(…)`** creates the server and gives it the function that will handle each request. Node calls it once per request with two <Term id="object">objects</Term>: **`req`** (*request*), the request that has arrived, and **`res`** (*response*), the response you're going to write.

- **`export`** lets `server.ts` and the tests use `createShopServer`.

### The Phase 2 request, in variables

Node reads the bytes that arrive over the connection, separates the start line and the headers, and gives you everything in `req`:

| In the message | In the code | For example |
|---|---|---|
| The <Term id="http-method">method</Term>, in the start line | `req.method` | `'POST'` |
| The path and the <Term id="query-string">query string</Term>, in the start line | `req.url` | `'/products?sort=price'` |
| The <Term id="header">headers</Term> | `req.headers` | `{ host: 'localhost:3000', 'content-type': 'application/json', … }` |
| The body, after the empty line | `req` itself, which is read in chunks | `{"productId":2,"quantity":3}` |

Notice two things:

- **`req.url` isn't a whole URL:** it's what travels in the start line, the path with its query string. The server's name goes in the `Host` header.
- **Header names arrive in lowercase.** HTTP doesn't care about upper or lower case ([lesson 4 of Phase 2](/en/phase-2/http-headers/)), so Node makes them all the same: you always look up `req.headers['content-type']`.

`node:http` only takes the request apart. What to answer is up to you.

### Responding: code, headers and body

All the shop's JSON responses go through this function:

<ProjectCode file="shop-api/04-http-server/src/app.ts" region="respond" />

- **`sendJson`** is ours, not Node's. It takes `res`, the <Term id="status-code">status code</Term>, the data and, if needed, more headers (`= {}`: if it isn't given any, none).
- **`res.writeHead(status, {…})`** writes the status line and the headers: the `HTTP/1.1 201 Created` and the `Content-Type`. Node adds the phrase, `Created`, based on the number.
- **`...headers`** copies the extra headers into the same object. That's how `Location` or `Allow` are added.
- **`JSON.stringify(data)`** turns the data into <Term id="json">JSON</Term> text, and **`res.end(…)`** writes it as the body and marks the response as finished. Without `res.end`, the client waits forever.
- **`methodNotAllowed`** answers `405` with `Allow`, the methods that are accepted, as the standard requires ([lesson 2 of Phase 2](/en/phase-2/http-methods/)).

### Choosing what to do: routes, with if

`handle` looks at the <Term id="route">route</Term> and the method, and gives the right answer. Its beginning:

<ProjectCode file="shop-api/04-http-server/src/app.ts" region="routes-start" />

- **`async`** lets the function wait with `await` ([lesson 2](/en/phase-3/javascript-for-backend/#waiting-for-what-takes-time-promises-async-and-await)).
- **`new URL(req.url ?? '/', 'http://localhost')`** builds a whole URL to separate its parts; `'http://localhost'` is only a base, because `req.url` doesn't include the server. `??` means “if it's missing, use `'/'`.”
- **`const { pathname } = …`** takes the `pathname` part out of that URL and stores it in a variable with the same name. It's the path without the query string: `/products?sort=price` also goes into `/products`.
- **`if (pathname === '/')`**: `===` compares, and if they're equal the block runs.
- **`return`** ends the function. Without it, the code would keep going down and try to answer again.
- **On `/products`,** the method comes first: if it isn't `GET`, `405` with `Allow: GET`; if it is, the list with a `200`.

Next, a specific product, like `/products/2`:

<ProjectCode file="shop-api/04-http-server/src/app.ts" region="routes-product" />

- **`pathname.match(/^\/products\/(\d+)$/)`** compares the path with a pattern, a regular expression: “starts with `/products/`, goes on with one or more digits (`\d+`) and ends.” The parentheses keep the digits: `route[1]` is the text `'2'`, and `Number(…)` turns it into the number 2. If it doesn't fit, `match` returns `null` and the `if` isn't entered.
- **`if (!product)`**: `!` means “not.” If `findProduct` hasn't found anything, `404`.

And the end, with the orders:

<ProjectCode file="shop-api/04-http-server/src/app.ts" region="routes-orders" />

- **`/orders`** accepts `GET`, the list, and `POST`, which creates an order with `newOrder` (you'll see it in a moment). With any other method, `405` and `Allow: GET, POST`.
- **`/orders/1`** works like `/products/2`, with its own pattern and `findOrder`. It's the address each new order gets; if it doesn't exist, `404`.
- **The last line** is only reached if no `if` has answered: `404`.

**`404` is a route that doesn't exist; `405`, a route that exists with a method it doesn't accept.** It works, but every new route is another `if`. A framework saves you that part: you'll see it in [lesson 5](/en/phase-3/express-hono-fastify/).

### The body arrives in chunks

The method and the headers are in `req` from the start; the body isn't. It can take up megabytes, like a photo, and it travels in several TCP <Term id="segment">segments</Term> ([Phase 0](/en/phase-0/tcp-vs-udp/)). Instead of waiting until it has the whole thing, Node gives you each chunk as it arrives: it's a <Term id="stream">stream</Term>.

<ProjectCode file="shop-api/04-http-server/src/app.ts" region="read-body" />

- **`const chunks: Buffer[] = []`** creates an empty <Term id="array">array</Term>, a list to keep the chunks in. Each chunk is a `Buffer`: bytes, not text yet.
- **`for await (const chunk of req)`** goes through the chunks as they arrive, and `push` adds each one to the list. `await` waits for the next one without stopping the rest of the server (why, in [lesson 9](/en/phase-3/node-event-loop/)).
- **When there are no chunks left,** `Buffer.concat` puts them together and `toString('utf8')` turns the bytes into text.
- **`Promise<string>`** says what it returns: a <Term id="promise">promise</Term> of a text, which arrives when the body is complete.

They're put together before converting them because an é takes up two bytes ([Phase 2](/en/phase-2/http-request-and-response/)) and can end up split between two chunks.

### A new order: JSON in, JSON out

<ProjectCode file="shop-api/04-http-server/src/app.ts" region="new-order" />

- **`let data: { … }`** creates the variable before the `try`, with the expected shape, so it can be used afterwards. It's `let` because it gets its value later.
- **`JSON.parse(await readBody(req))`** waits for the whole body and turns the JSON text into data. If it isn't valid JSON, it throws an error (an <Term id="exception">exception</Term>).
- **`try { … } catch { … }`** means “try this; if it fails, do this instead”: here, a `400`, because the server couldn't even read the data.
- **If the product doesn't exist,** `422`: the JSON was read, but it asks for something that doesn't exist. It's the rule from [lesson 3 of Phase 2](/en/phase-2/http-status-codes/#the-codes-that-matter): `400` if the request can't be read, and `422` if it can be read and the data isn't valid.
- **If everything goes well,** `createOrder` saves it and the response is a `201 Created` with `Location`, the address of the new order. `` `/orders/${order.id}` `` is a text with a gap ([lesson 2](/en/phase-3/javascript-for-backend/#text-with-gaps-backticks)): with order 1, `/orders/1`.

**The `as` lies to <Term id="typescript">TypeScript</Term>.** It tells it “trust me: the data has this shape,” and nobody checks it: `JSON.parse` returns whatever arrived, and the types are erased when it runs ([lesson 3](/en/phase-3/typescript-with-node/#node-erases-the-types-when-it-runs)). If `"quantity": -5` arrives, it goes through. [Lesson 7](/en/phase-3/zod-validation/) fixes it.

The orders are kept in `data.ts`:

<ProjectCode file="shop-api/04-http-server/src/data.ts" region="orders" />

- **`orders`** is a list in memory: when the server stops, it's lost. The database arrives in Phase 5.
- **`findProduct`** you already had, and **`findOrder`** does the same with the orders: it returns the one with that `id`, or `undefined` if there isn't one.
- **`createOrder`** gives it the next number (`orders.length + 1`), marks it `'pending'` and adds it with `push`.

```sh

```

It doesn't print anything if it goes well. It ends up like this, with `dev` at the end of `scripts` (the order doesn't matter):

<ProjectCode file="shop-api/04-http-server/package.json" />

- **`npm start`** runs `node src/server.ts`. Node reads your code when it starts: if you change a file, the running server doesn't notice.
- **`npm run dev`** adds `--watch`: Node watches `server.ts` and the files it imports, and restarts the server every time you save one. It's for when you're programming.

## You have already seen it

- **In Phase 2, with `nc`.** What you typed by hand, the status line, the headers and the body, is now written by `res.writeHead` and `res.end`.
- **In the shop's nginx.** Each `location` with its `return` was a route with a fixed response. Your `if`s also read the body and decide.
- **In the browser.** Open `http://localhost:3000/products`: the browser makes a `GET` and shows you the JSON. In DevTools' **Network** tab ([how to open them](/en/phase-2/#before-you-start-devtools)) you'll see the same headers as with `curl -i`.

## Common mistakes

- **Forgetting the `return` after answering.** The code reaches another response: the client gets the first one, but Node throws `Error [ERR_HTTP_HEADERS_SENT]: Cannot write headers after they are sent to the client` and the server crashes.
- **Forgetting `res.end`.** The response never ends, and `curl` is left waiting.
- **Comparing `req.url` with the route.** `/products?sort=price` isn't `/products`, and you answer `404`. Compare the `pathname`.
- **Starting it twice.** The second one fails with `Error: listen EADDRINUSE: address already in use 127.0.0.1:3000`: the port already belongs to the first.

## Summary

- `createServer` takes a function that Node calls with every request: `req` is what arrives and `res`, the response you write. `listen` makes it listen on a port.
- The request is in variables: `req.method`, `req.url` (path and query string) and `req.headers` (in lowercase). The body is a stream: it arrives in chunks.
- Routes are `if`s on the `pathname` and the method: `404` if the route doesn't exist; `405` with `Allow` if it doesn't accept the method.
- If the body isn't JSON, `try`/`catch` and a `400`; if it is, but it asks for a product that doesn't exist, `422`. The `as` checks nothing: [lesson 7](/en/phase-3/zod-validation/) will.
- `npm run dev` (`node --watch`) restarts the server when you save, and `npm test` checks that it answers what it promises.

The running server uses the code it read when it started. With `--watch`, it restarts on its own when you save.

</QuizOption>

<QuizOption text="curl stores the responses and repeats the last one until you delete it.">

`curl` doesn't store anything between one command and the next: each time it makes a new request.

</QuizOption>

<QuizOption text="Node takes a few minutes to compile the .ts files after you save them.">

Node doesn't compile separately: it reads the `.ts` files when it starts, removes their types and runs them.

<QuizQuestion
  question="Why is the body read with a loop (for await) instead of being in req from the start, like req.method?"
  review="The body arrives in chunks"
>

<QuizOption text="Because it arrives in chunks, and you have to put them all together before turning them into text." correct>

The body is a stream: Node gives you each chunk as it arrives, and the loop puts them together.

</QuizOption>

<QuizOption text="Because each chunk is a field of the JSON: one for productId and another for quantity.">

Chunks are cut as the bytes arrive, not by meaning: even a letter can end up split between two.

</QuizOption>

<QuizOption text="Because the server has to ask the client for the body in a second request.">

The body travels in the same request, after the empty line; it just doesn't all arrive at once.

</QuizOption>

<QuizQuestion
  question={`An app sends {"productId":"2","quantity":1}: the 2 is in quotes, as text. The code has the as { productId: number; … }. What happens?`}
  review="A new order: JSON in, JSON out"
>

<QuizOption text="TypeScript rejects it when it arrives, because productId has to be a number.">

TypeScript isn't there when the server runs: the types are erased, and the `as` checks nothing.

</QuizOption>

<QuizOption text="Node turns the text into the number 2 and creates the order, because the type says number.">

Nobody converts anything: `JSON.parse` returns the text `"2"` as it is. The type is a promise nobody watches over.

</QuizOption>

<QuizOption text="It answers 422, “No such product”: the text isn’t equal to the number 2." correct>

`JSON.parse` leaves the text `"2"` as it is, and `findProduct` compares with `===`: the text isn't the number `2`. The message is misleading: lesson 7 will say which field is wrong.

</QuizOption>

<QuizOption text="Run npm install, because a package is missing.">

The error doesn't talk about packages: it says the address, port 3000, is already in use.

</QuizOption>

<QuizOption text="Find the server that’s already running and stop it, or use another port." correct>

Only one process can listen on a port, and it's usually your own server, forgotten in another terminal: <kbd>Ctrl</kbd> + <kbd>C</kbd> there stops it.

</QuizOption>

Port 3000 doesn't need special permissions. The problem is that another process is already using it, and `sudo` doesn't change that.
