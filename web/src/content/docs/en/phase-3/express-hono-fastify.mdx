## The problem

In [lesson 4](/en/phase-3/node-http-server/) you wrote the shop's API with `node:http` alone. It works, but look at how it finds out which product is being asked for: `pathname.match(/^\/products\/(\d+)$/)`. That's a regular expression, a text pattern you have to read with a magnifying glass, and all it does is pull the `2` out of `/products/2`. On top of that, every route repeats its own `if (req.method !== 'GET')`.

Now Ana wants to filter by price: `/products?max=25`, “the products that cost €25 or less.” Later she'll want to create products. Every new idea is another `if`, another regular expression and another place to make a mistake.

And every server needs the same things: sorting out the requests, reading the data in the URL and in the body, and answering in JSON. That's what frameworks are for: code that already solves that part, so you only write yours.

## The analogy

<Analogy>

Think of the front desk of an office building. Visitors don't go from office to office: they say what they've come for, and the receptionist checks the directory and tells them where to go. “An invoice? Accounting, second floor.” If they bring a case number, the receptionist writes it on the slip they hand over, and the office doesn't have to ask for it again.

You write the directory, and the receptionist applies it to every visit. In lesson 4 you did both jobs. The visitor is the request; the directory, your list of routes; each office, the function that answers; and the case number, the `2` in `/products/2`.

<div slot="limits">

- A receptionist understands what you want even if you say it your own way. The framework only compares patterns: `/product/2`, without the “s”, matches nothing and gets a `404`.
- A receptionist would tell you “we don't do that here; only inquiries.” Hono, Express and Fastify answer `404` to a wrong method: you write the `405` yourself.
- The building hired the receptionist. Other people wrote the framework: your server depends on their code, their versions and their bugs.

</div>

</Analogy>

## How it really works

### What a framework does for you

This is the same API, in lesson 4 and in this one:

| What's needed | In lesson 4, with `node:http` | With Hono |
|---|---|---|
| Choosing which code handles the request | One `if` per route, and a regular expression | `app.get('/products/:id', …)` |
| Reading the `2` in `/products/2` | What the regular expression captured, `route[1]` | `c.req.param('id')` |
| Reading the `25` in `?max=25` | It didn't: you'd have to read the URL by hand | `c.req.query('max')` |
| Reading the body of an order | `readBody`, chunk by chunk, and `JSON.parse` | `await c.req.json()` |
| Answering in JSON | `writeHead`, `JSON.stringify` and `end` | `c.json(data)` |

That's what a <Term id="framework">framework</Term> is: code already written that solves what every server repeats, and that calls your functions when a request arrives. The difference from any other <Term id="package">package</Term>, like the ones in [lesson 1](/en/phase-3/what-is-node-js/), is who calls whom: you call a package; a framework calls you.

What **doesn't change is HTTP**. The request still brings its method, its headers and its body, and a `404` is still a `404`, as in [Phase 2](/en/phase-2/). The framework only saves you code.

### Why Hono in this course

Of the three best-known frameworks for Node.js, Express, Fastify and Hono, this course uses Hono for three reasons:

- **It speaks like `fetch`.** It uses the `Request` and `Response` <Term id="object">objects</Term> of `fetch`, the function the browser makes requests with; you used it in the console in [lesson 6 of Phase 2](/en/phase-2/what-is-cors/). What you learn here works there, and the other way around.
- **It runs in many places.** The same code runs on Node.js and on Cloudflare Workers, the servers this site is published on, among others.
- **It's small and written in <Term id="typescript">TypeScript</Term>.** It's a single package, with no dependencies.

### Request and Response: the fetch objects

`app.fetch` is a function that receives a `Request` and returns a `Response`. A `Request` carries the method, the URL, the headers and the body; a `Response`, the code, the headers and the body. It's the HTTP message from Phase 2, in two objects.

`node:http` doesn't use those objects: it gives you `req` and `res`, as you saw in lesson 4. The adapter translates in both directions:

```mermaid
flowchart TB
    A["curl<br/>GET /products/2"] -->|the bytes arrive over TCP| B["node:http<br/>reads them into req"]
    B -->|@hono/node-server translates it| C["A Request<br/>like the ones in fetch"]
    C -->|app.fetch looks for the route| D["Your function<br/>returns a Response"]
    D -->|the adapter writes it into res| E["curl<br/>gets the response"]
```

On Cloudflare Workers you don't need the adapter: the platform hands `app.fetch` a `Request` directly. That's why `app.ts` works the same there, and the only part specific to Node.js is `server.ts`.

The routes go below. A <Term id="route">route</Term> is a method, a path and the function that answers:

<ProjectCode file="shop-api/05-framework/src/app.ts" region="routes" />

Piece by piece:

- **`app.get('/', …)`** adds to Hono's list a route for `GET` requests to `/`.
- **`(c) => …`** is an arrow function ([lesson 2](/en/phase-3/javascript-for-backend/)) that receives `c`, the context: the request is in `c.req`, and `c` has the methods to answer.
- **`c.text('…')`** answers `200` with text.
- **`c.req.query('max')`** reads the `max` in the <Term id="query-string">query string</Term>. If the URL doesn't bring it, it gives `undefined`.
- **`c.json(products)`** answers `200`, with `Content-Type: application/json` and the list in JSON.
- **`products.filter(…)`** keeps the ones that cost `max` or less. `Number(max)` is needed because everything that comes in a URL is text.
- **`'/products/:id'`**: the colon turns `id` into a <Term id="route-parameter">route parameter</Term>. The route matches `/products/2` and `/products/7`, and `c.req.param('id')` gives `'2'`, also as text.
- **`c.json({ error: … }, 404)`**: the second argument is the <Term id="status-code">status code</Term>. Without it, it's `200`.
- **The two `/orders` routes** repeat the idea: the whole list, and one order by its number, or a `404` if it doesn't exist.

A rule for choosing: the route parameter says **which resource** you're asking for (product 2); the query string **filters or searches** a list (the ones at €25 or less).

### The body of an order

<ProjectCode file="shop-api/05-framework/src/app.ts" region="new-order" />

- **`app.post('/orders', …)`**: the same path as `app.get('/orders')`, with another method, is another route.
- **`await c.req.json()`** reads the whole body and converts it from JSON: Hono puts together the chunks that `readBody` used to put together. Because of the `await`, the function is marked `async`.
- **`try` and `catch`**: if the body isn't JSON, `c.req.json()` fails and the `catch` answers `400`, as in lesson 4.
- **`let data: { productId: number; quantity: number }`** promises TypeScript a shape that nobody checks: `c.req.json()` returns whatever arrived. You'll fix that in [lesson 7](/en/phase-3/zod-validation/).
- **`if (!findProduct(…))`**: the JSON was read fine, but it asks for a product that doesn't exist. That's a `422`, not a `400`: the request is understood, and what it asks for makes no sense ([the status codes lesson](/en/phase-2/http-status-codes/)).
- **`c.json(order, 201, { Location: … })`**: the third argument is the headers. A `201` with `Location`, the address of the new order, which the `GET /orders/:id` route handles.

But `/products` exists; what it doesn't accept is that method. [The methods lesson](/en/phase-2/http-methods/) made it clear: that's a `405`, with the `Allow` header. Express and Fastify also answer `404`, so in all three you write it yourself:

<ProjectCode file="shop-api/05-framework/src/app.ts" region="not-allowed" />

- **`app.all`** creates a route for any method, one for each path in the API.
- **They go after the rest.** Hono tries the routes in the order you wrote them, so `app.all` only gets what nobody has handled before.
- **The third argument** sets the `Allow` header with the methods that are valid.

### How to choose

| | Express | Fastify | Hono |
|---|---|---|---|
| Weekly downloads on npm (October 13, 2026) | 145 million | 15 million | 74 million |
| Since | 2010 | 2016 | 2021 |
| Packages it installs | 68 | 48 | 1 |
| Your functions receive | `req` and `res` from `node:http` | The request, and they return the data | `c`, with a `Request` inside |
| TypeScript | Separate types, from the community (`@types/express`) | Types included | Written in TypeScript |
| Designed for | Node.js | Node.js | Node.js, Cloudflare Workers, Deno, Bun… |

We counted the packages by installing each one in an empty folder. **Express** is what you'll find most in job listings and tutorials. **Fastify** was born to be fast, and it validates data with <Term id="schema">schemas</Term>, a description of its shape. **Hono** is the newest.

What you learn with one carries over to the others: routes, parameters, status codes and the <Term id="middleware">middleware</Term> of [lesson 6](/en/phase-3/what-is-middleware/). Switching frameworks is learning other names for the same ideas.

## You have already seen it

- **Route parameters in the addresses you visit.** In `github.com/user/repository` two pieces change depending on what you're looking at, and in `youtube.com/watch?v=…` the video goes in the query string.
- **`X-Powered-By` in DevTools.** In the **Network** tab of some websites you'll see `X-Powered-By: Express` or `X-Powered-By: Next.js` among the response headers: it's the header you just saw on 3001.
- **`fetch` in the console.** The `await fetch(…)` from [the CORS lesson](/en/phase-2/what-is-cors/) returns a `Response`, like your Hono routes.

## Common mistakes

- **A URL with `?` and no quotes in zsh.** `curl localhost:3000/products?max=25` answers `zsh: no matches found: localhost:3000/products?max=25`: to zsh, `?` is a file name wildcard. Put the URL in quotes.
- **Using a parameter as if it were a number.** `c.req.param('id')` gives `'2'`, text, and `'2' === 2` is false: the search never finds anything. If you pass the text to `findProduct`, `npm run check` warns you: `error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.`
- **`app.all` before the other routes.** Even the `GET` requests get the `405`.
- **Thinking the framework checks the data.** `?max=cheap` answers `200` with `[]`, without an error: `Number('cheap')` isn't a number, and no price passes the filter. You'll fix that in [lesson 7](/en/phase-3/zod-validation/).
- **Copying a tutorial for another version.** Express 5 no longer accepts `app.get('*', …)`: it fails on startup with `Missing parameter name at index 1: *`. The wildcard now has a name, `'/*rest'`. Always check the tutorial's version.

## Summary

- A framework does what every server repeats: choosing the route, reading its parameters, the query string and the body, and answering in JSON. You write what's specific to your shop.
- A route is a method, a path and the function that answers. `:id` marks a parameter, which always arrives as text.
- Hono works with the `Request` and `Response` of `fetch`; `@hono/node-server` translates them from and to `node:http`.
- HTTP doesn't change: you write the `405` with `Allow` yourself, in Hono, in Express and in Fastify.
- Express is the most used, Fastify was born to be fast and Hono is the smallest. The ideas work in all three.

</QuizOption>

<QuizOption text="Because Hono doesn’t let you have /orders and /orders/:id in the same app.">

They're two different routes, and Hono accepts both at once: the shop already has `/products` and `/products/:id`.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="You write app.get('/cart', …) and no other route for /cart. What does someone who sends DELETE /cart get?"
  review="A wrong method: Hono answers 404"
>

<QuizOption text="A 405 with Allow: GET, because Hono knows which methods each path has.">

Hono, Express and Fastify don't do it on their own: the `405` with `Allow` is one more route that you write.

</QuizOption>

<QuizOption text="A 200: Hono uses the GET function for any method.">

`app.get` only handles `GET` requests. For any method there's `app.all`.

</QuizOption>

<QuizOption text="A 404, because there’s no route for that method and that path." correct>

Hono looks for a route for `DELETE /cart`, doesn't find one and answers the same as to a route that doesn't exist.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Someone moves the app.all routes for the 405 to the top of app.ts, before the GET and POST ones. What does a GET /orders get now?"
  review="A wrong method: Hono answers 404"
>

<QuizOption text="A 405: Hono uses the first route that matches, and app.all works for everything." correct>

Order matters. That's why the `405` routes go at the end: they only get what nobody has handled before.

</QuizOption>

<QuizOption text="The list of orders: Hono prefers the route with the exact method over app.all.">

Hono doesn't sort the routes by how exact they are: it tries them in the order you wrote them.

</QuizOption>

<QuizOption text="Nothing: the server doesn’t start, because Hono doesn’t accept two routes with the same path.">

Hono accepts several routes with the same path, like `GET /orders` and `POST /orders`, which the shop already has.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="At your job, the team moves an API from node:http to Express. What do you have to relearn about HTTP?"
  review="What a framework does for you"
>

<QuizOption text="The status codes: each framework defines its own.">

The codes belong to the HTTP standard: a `404` means the same in Express, in Hono and in nginx.

</QuizOption>

<QuizOption text="Nothing: methods, codes and headers stay the same; the code changes." correct>

The framework only saves you code. The request and the response that travel are the ones from Phase 2.

</QuizOption>

<QuizOption text="The message format: Express uses its own protocol on top of HTTP.">

Express speaks HTTP like any server: `curl` talks to it the same as to Hono, as you saw on port 3001.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="You want to take the Hono API to Cloudflare Workers. Which part of the project wouldn’t you need there?"
  review="Request and Response: the fetch objects"

<QuizOption text="package.json: Workers doesn’t use npm packages.">

Workers uses npm packages: Hono itself is one, and it's what you'd take with you.

</QuizOption>

<QuizOption text="app.ts: on Workers, routes are written with Cloudflare’s tool.">

`app.ts` is exactly what you take as is: Hono's routes don't depend on where they run.

</QuizOption>

<QuizOption text="server.ts: there, the platform already hands each Request to app.fetch." correct>

`server.ts` and `@hono/node-server` only translate between `node:http` and the `fetch` objects. On Workers you don't need them: the platform already speaks in `Request` and `Response`.
