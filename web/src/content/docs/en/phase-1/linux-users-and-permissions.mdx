## The problem

Imagine a friend's online shop has a bug in the form where customers upload their photo. Someone discovers it and manages to make the server run their commands. What can they do from there? It depends on one thing only: which user the server program runs as.

If it runs as the administrator, the attacker can do everything: read the passwords, copy the database, delete it and install whatever they want. If it runs as a user of its own that can only touch its folder, the damage stays in that folder.

In your day-to-day work you'll see it differently: a `Permission denied` when you try to read a file or start a program. The temptation is to fix it with `sudo` or with `chmod 777`, and that opens exactly the holes from the first paragraph. Here you'll learn to read permissions and to grant them carefully, on your own practice server.

## The analogy

<Analogy>

Imagine an office building. Each person has a badge with their name, and the badge also says which departments they belong to. Each office has a sign on the door with three lines: what its owner, its department and anyone else can do: read the papers, change them or use what's inside. To reach an office, you go through hallways with doors, and each door has its own sign.

The building manager has a master key that opens everything. If you need something your badge doesn't open, you ask him for it just for that one thing, and he writes down in a logbook who asked for it and what for.

The cleaning company has its own badge, which only opens the rooms it cleans. If someone steals it, they don't get into the safe.

On Linux, the badges are users; the departments, groups; the signs, permissions; and the building manager, root.

- The master key doesn't just open doors: root can change the signs, make new badges or tear down the building, and nobody asks it “are you sure?”

## How it really works

The examples in this section are from an Ubuntu server like the one you'll create in “Try it.” If you want to try them while you read, [create it first](#first-your-practice-server).

### Every person and every program is a user

On Linux, everything that happens is done by a <Term id="user">user</Term>: every <Term id="process">process</Term> runs on behalf of one, and every file has one as its owner. Two commands tell you who you are:

```text
$ whoami
ubuntu
$ id
uid=1000(ubuntu) gid=1000(ubuntu) groups=1000(ubuntu),4(adm),20(dialout),24(cdrom),25(floppy),27(sudo),29(audio),30(dip),44(video),46(plugdev)
```

`whoami` gives your name. `id` gives more details:

- **`uid=1000(ubuntu)`:** your user number. To the system, a user is a number; the name is for people.
- **`gid=1000(ubuntu)`:** your primary group. On Ubuntu, every user has one with the same name.
- **`groups=…`:** all your <Term id="group">groups</Term>. A group brings users together so they can be given permissions all at once. The one that matters here is `sudo`: whoever is in it can act as the administrator.

The list of users is in a text file, `/etc/passwd`. Each line is one user, with their details separated by `:`:

```text
$ grep www-data /etc/passwd
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
```

They are the name, an `x` (the password is stored in another file, `/etc/shadow`), the user number, the group number, a description, the home folder and the <Term id="shell">shell</Term>. `www-data` isn't a person: it's the user for web servers, and its shell, `nologin`, doesn't let anyone log in as it.

### The ten letters of `ls -l`

In [lesson 1](/en/phase-1/basic-terminal-commands/) you saw letters like `drwxr-xr-x` at the start of `ls -l`. They're the <Term id="permissions">permissions</Term>. This is `ubuntu`'s home folder, with a file and a folder:

```text
$ ls -l
total 8
-rw-rw-r-- 1 ubuntu ubuntu    6 Oct 12 13:29 notes.txt
drwxrwxr-x 2 ubuntu ubuntu 4096 Oct 12 13:29 project
```

The ten letters read like this, with `notes.txt`:

| `-` | `rw-` | `rw-` | `r--` |
|---|---|---|---|
| Type: `-` is a file; `d`, a folder (*directory*) | The owner (*user*, `u`) | The group (`g`) | Everyone else (*others*, `o`) |

After them come the owner (`ubuntu`) and the group (`ubuntu`). Each set of three letters says the same thing, always in the same order:

- **`r`** (*read*): read.
- **`w`** (*write*): write, that is, change.
- **`x`** (*execute*): run, if it's a program.

A dash means “no.” So `notes.txt` can be read and changed by its owner and its group, and everyone else can only read it.

### What r, w and x mean on a folder

On a folder, the same letters mean something else:

| Letter | On a file | On a folder |
|---|---|---|
| `r` | Read its contents | See the list of what's inside (`ls`) |
| `w` | Change its contents | Create, rename and delete files inside |
| `x` | Run it as a program | Go in (`cd`) and reach what's inside |

A folder's `x` is the hallway door: **without it you can't reach any file inside**, even if the file lets you read it. And it's the folder's `w`, not the file's, that decides whether you can delete it.

### How Linux decides whether you can

When a program opens a file, the system asks, in order:

1. Are you root? You can do almost anything; permissions don't count.
2. Are you the owner? The first three letters are used, and nothing else.
3. Are you in the file's group? The middle three are used.
4. If not, the last three.

Look at `/etc/shadow`, the password file:

```text
$ ls -l /etc/passwd /etc/shadow
-rw-r--r-- 1 root root   888 Sep 17 02:17 /etc/passwd
-rw-r----- 1 root shadow 502 Sep 17 02:17 /etc/shadow
$ cat /etc/shadow
cat: /etc/shadow: Permission denied
```

`ubuntu` isn't the owner (`root`) and isn't in the `shadow` group, so it gets the last three letters: `---`. `/etc/passwd`, on the other hand, ends in `r--`: anyone can read it.

### Changing permissions with `chmod`: letters or numbers

Imagine you download a script, `hello.sh`: a file with commands for the shell (you'll write some in [lesson 8](/en/phase-1/bash-scripts/)). You try to run it:

```text
$ ./hello.sh
-bash: ./hello.sh: Permission denied
$ ls -l hello.sh
-rw-rw-r-- 1 ubuntu ubuntu 42 Oct 12 13:29 hello.sh
$ chmod u+x hello.sh
$ ls -l hello.sh
-rwxrw-r-- 1 ubuntu ubuntu 42 Oct 12 13:29 hello.sh
$ ./hello.sh
Hello from course
```

Without `x`, it couldn't be run. `chmod` (*change mode*) changes the permissions, and `u+x` means “add `x` for the owner.” Only a file's owner, or root, can change them.

**With letters** you say who, which operation and which permission:

- Who: `u` (the owner), `g` (the group), `o` (everyone else) or `a` (all).
- The operation: `+` adds, `-` removes and `=` sets exactly those.
- Examples: `chmod o-r notes.txt` takes reading away from everyone else; `chmod go= secret.txt` takes everything away from the group and everyone else.

**With numbers**, each permission is worth an amount: `r` = 4, `w` = 2 and `x` = 1. You add up the ones in each set of three, and you get three digits: the owner, the group and everyone else. `rw-` is 4 + 2 = 6, and `r-x` is 4 + 1 = 5:

```text
$ chmod 600 notes.txt
$ ls -l notes.txt
-rw------- 1 ubuntu ubuntu 6 Oct 12 13:29 notes.txt
$ chmod 755 hello.sh
$ ls -l hello.sh
-rwxr-xr-x 1 ubuntu ubuntu 42 Oct 12 13:29 hello.sh
```

With numbers you set all nine permissions; with letters, only the ones you name. These are the most common:

| Number | Letters | What for |
|---|---|---|
| `644` | `rw-r--r--` | A normal file: you change it, everyone reads it |
| `600` | `rw-------` | A secret, like a password or a key: only you |
| `755` | `rwxr-xr-x` | A program or a folder: everyone goes in or runs it, only you change it |
| `700` | `rwx------` | A private folder: only you go in |
| `777` | `rwxrwxrwx` | Everyone can do everything. Almost never a good idea |

### Changing the owner with `chown`

`chown` (*change owner*) gives a file to another user. Imagine the shop's website, which runs as `www-data`, has to save photos in the `uploads` folder:

```text
$ chown www-data uploads
chown: changing ownership of 'uploads': Operation not permitted
$ sudo chown www-data uploads
$ ls -ld uploads
drwxrwxr-x 2 www-data ubuntu 4096 Oct 12 13:29 uploads
```

Only root can give files away; otherwise, anyone could put their own files in someone else's name. That's why you need `sudo`, which you'll see next. To change the group too: `sudo chown www-data:www-data uploads`. (`-d` makes `ls` show the folder itself and not what's inside it.)

### root, `sudo` and least privilege

<Term id="root">root</Term> is the Linux administrator: user number 0, the building manager from the analogy. Permissions don't affect it: it can do everything, including making mistakes with nothing to stop it.

That's why nobody works as root. You work as a normal user, and when you need something only the administrator can do, you ask for it for one single command with <Term id="sudo">sudo</Term> (from *superuser do*):

```text
$ whoami
ubuntu
$ sudo whoami
root
$ sudo head -1 /etc/shadow
root:*:20713:0:99999:7:::
```

`sudo` runs the command that follows it as root, and only that one. On Ubuntu, users in the `sudo` group can use it. It normally asks for your password, and it records every use in a log: the building manager's logbook.

Behind all this there's a rule, <Term id="least-privilege">least privilege</Term>: **every user and every program has only the permissions it needs, and no more**. If one day something fails or someone gets in where they shouldn't, the damage stays within the little that user could touch.

### Why each server has its own user

Because of that rule, each program on a server has its own user: `www-data` for the web server, `postgres` for the database (Phase 5). That way, if someone tricks the web server, as in “The problem,” they can't read the database's files.

But there's a catch. In [Phase 0](/en/phase-0/ip-ports-sockets/) you saw that the web uses <Term id="port">port</Term> 80. On Linux, **ports 0 to 1023 can only be opened by root**:

```text
$ nc -l 80
nc: Permission denied
```

With 8080 there would be no problem. Web servers solve it in two steps: they start as root, open port 80 and hand the work over to processes that run as their own user. This is what nginx looks like, the web server you'll install in [lesson 6](/en/phase-1/systemd-services-and-apt/):

```text
$ ps -o user,pid,cmd -C nginx
USER         PID CMD
root        2887 nginx: master process /usr/sbin/nginx -g daemon on; master_process on;
www-data    2888 nginx: worker process
```

The root process only supervises; the one that handles the requests is the `www-data` one. In Phase 8 you'll do something similar with your own program: it will listen on 3000 as its own user, and nginx, on 80, will pass the requests on to it.

## You have already seen it

- **On your Mac.** The `ana staff` in `ls -l` in [lesson 1](/en/phase-1/basic-terminal-commands/) are your user and your group. In the Finder, “Get Info” (<kbd>Cmd</kbd> + <kbd>I</kbd>) ends with “Sharing & Permissions”: the same three lines, for you, `staff` and everyone else.
- **When you install something.** Your Mac and Windows ask for the administrator password. That's the idea behind `sudo`: you work as a normal user and ask for permission only to touch the system.
- **On your phone.** Each app asks for permission to use the camera or your location, and it only has what you give it: least privilege.

And if you code:

- `npm install -g` sometimes answers `EACCES: permission denied`: it wants to write to a folder that belongs to root. `sudo` “fixes” it and leaves root-owned files on your computer; a version manager like nvm installs Node in your folder and avoids it.
- Git stores each file's `x`. After a `chmod +x`, `git diff` shows `old mode 100644` and `new mode 100755`: the permissions as numbers, after a `100` that means “regular file.”

## Common mistakes

- **`chmod 777` to get rid of a `Permission denied`.** It works, and it lets anyone change the file, including an attacker who gets in as the website's user. Check who the owner is and who needs it, and grant only that.
- **`sudo` for everything.** What you create with `sudo` belongs to root, and afterwards you can't change it without `sudo`. Use it only on the command that needs it.
- **`sudo` with `>`.** `sudo echo "hello" > /etc/greeting.txt` answers `-bash: /etc/greeting.txt: Permission denied`. The redirection is done by your shell, which isn't root, before `sudo` starts (you saw this in [lesson 3](/en/phase-1/pipes-and-redirection/)). Use `echo "hello" | sudo tee /etc/greeting.txt`: `tee` copies whatever reaches it into a file, and here it does so as root.
- **A folder without `x`.** `chmod -R 644` (`-R` applies it to everything inside) takes the `x` away from the folders, and then nobody can go into them.
- **On WSL, working in `/mnt/c`.** Those are the Windows folders, and Linux permissions don't work the same way there: everything shows up as `rwxrwxrwx` and `chmod` may not change anything. Practice in `~`.

## Summary

- Every file has an owner, a group and three sets of permissions: the owner (`u`), the group (`g`) and everyone else (`o`). `ls -l` shows them at the start of each line.
- `r` is read, `w` change and `x` run. On a folder, `x` means being able to go in and reach what's inside.
- `chmod` changes permissions with letters (`u+x`) or with numbers (`r` = 4, `w` = 2, `x` = 1: `644`, `600`, `755`). `chown` changes the owner, and only root can do it.
- root bypasses permissions. You work as a normal user and use `sudo` for one single command.
- Least privilege: every program runs as its own user with only the permissions it needs. Web servers only use root to open port 80.

It is: with `777`, any user on the server can delete or change the logs, including an attacker who gets in through another program.

</QuizOption>

<QuizOption text="Start the program as root, which is no riskier than with its own user.">

It's much riskier: as root, a bug in the program hands the whole server to whoever exploits it.

</QuizOption>
