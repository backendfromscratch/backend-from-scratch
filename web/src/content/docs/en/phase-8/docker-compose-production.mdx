## The problem

Picture Ana copying the Phase 7 shop to her server, typing `docker compose up -d` and going to bed. It works, but with the practice accounts: two of them are admins, with their password published in the course's README.

A week later, Ana reboots the server after an update, and the shop doesn't come back: nobody told Docker to start it. Months later, the logs fill the disk. And the day a `down -v` slips out, there's no copy of the orders anywhere.

**What's enough on your computer isn't enough on a server.** In this lesson the shop goes up to yours with what it's missing.

## The analogy

<Analogy>

Think of someone who cooks at home and opens a restaurant. The recipes are the same, but the place needs more:

- **The key to the till** is kept at the restaurant, not in the recipe book: the secrets, in a `.env` that only exists on the server.
- **The cold room comes back on its own** after a power cut: the restart policy.
- **Old receipts get thrown out**, or there'd be no room left in the kitchen: logs with a limit.
- **Every night, the accountant copies the books:** the copy of the database.

<div slot="limits">

- The cold room comes back because it's electric. Docker only starts again what has a restart policy, and it respects what you stopped yourself.
- The accountant keeps the copy at their own office. This lesson's copy stays on the server itself: getting it out of there is up to you.

</div>

</Analogy>

## How it really works

### A file for the server: compose.production.yaml

The `35-production` folder brings Phase 7's `compose.yaml`, for your computer, and one for the server, `compose.production.yaml`, which you pick with `-f` (*file*). Both describe the same four services. This is PostgreSQL:

<ProjectCode file="shop-api/35-production/compose.production.yaml" region="db" />

- **`restart: unless-stopped`**: the <Term id="restart-policy">restart policy</Term>, in the next section.
- **`${POSTGRES_PASSWORD:?…}`**: with no password in `.env`, Compose starts nothing and prints the message.
- **No `ports`**: PostgreSQL isn't published, and neither is Redis. Only the shop's containers can see them.

`migrate` changes in two ways:

<ProjectCode file="shop-api/35-production/compose.production.yaml" region="migrate" />

- **`build: .` next to `image: ${IMAGE:-shop-api}`**: `up --build` builds the image on the server and calls it `shop-api`. `:-` means "if `IMAGE` doesn't exist, use this." In lesson 6, `IMAGE` will name the image GitHub publishes.
- **`--no-accounts`**: it loads the sample products, not the practice accounts. You'll create your admin account with a script in the step, `create-admin`.

And the API:

<ProjectCode file="shop-api/35-production/compose.production.yaml" region="api" />

**`127.0.0.1:3000-3001:3000`** is the rule from [lesson 2](/en/phase-8/secure-linux-server/#docker-bypasses-ufw): since Docker bypasses `ufw`, the API is published only on the server's own address. It can't be reached from outside; in [lesson 4](/en/phase-8/nginx-reverse-proxy/), nginx will talk to it from inside.

The last piece pins the network:

<ProjectCode file="shop-api/35-production/compose.production.yaml" region="network" />

Docker's internal network has its own range of addresses, and Compose picks a free one when it creates it. Pinning it keeps the address the API sees nginx arriving from, `172.18.0.1`, from changing. Today it does nothing; in [lesson 4](/en/phase-8/nginx-reverse-proxy/#the-visitors-ip-x-forwarded-for), the API will use it to know each visitor's IP.

### Inside, 0.0.0.0 and the node user

In [Phase 3](/en/phase-3/node-http-server/#a-server-is-a-function-node-calls-with-every-request) we told you that a public server listens on `0.0.0.0`, all the machine's addresses. **Inside the container, the API listens on `0.0.0.0`** (the `HOST` variable in the `Dockerfile`), so Docker can pass the requests on to it. On the server, it's only published on `127.0.0.1`.

And in [Phase 1](/en/phase-1/linux-users-and-permissions/#why-each-server-has-its-own-user) we told you your program would listen on 3000 as its own user. It's **`node`**, a user with no privileges that comes with the image, not `root`.

### If it crashes, it comes back: the restart policy

With no policy, a container that stops stays stopped. The shop's, `unless-stopped`, means "start it again, unless I'm the one who stopped it." This is what it looks like when you kill the API's process from the server:

```sh
$ sudo kill -9 $(docker inspect --format "{{.State.Pid}}" shop-api-1)
$ docker compose -f compose.production.yaml ps --format "table {{.Name}}\t{{.Status}}" api
NAME         STATUS
shop-api-1   Up 2 seconds (health: starting)
$ docker inspect --format "{{.RestartCount}}" shop-api-1
1
```

A moment later it's running again (`Up 2 seconds`), with one restart counted. With `docker compose stop api`, on the other hand, it stays `Exited`.

| Policy | If it crashes | If you stop it | When the server boots |
|---|---|---|---|
| `no`, the default | Stays stopped | Stays stopped | Stays stopped |
| `always` | Comes back | Stays stopped | Comes back, even if you stopped it |
| `unless-stopped` | Comes back | Stays stopped | Comes back, unless you stopped it |

When the server boots, the one starting the containers is Docker, a <Term id="systemd">systemd</Term> service since the [introduction](/en/phase-8/#install-docker-on-the-vm), not Compose: it starts them all at once, without waiting for the healthchecks. In our test, the three started within 10 milliseconds of each other, and by the time we logged back in, 18 seconds later, all three were healthy. `migrate` has no policy: it's a task.

### The secrets are generated on the server

You copy `.env.production.example` as `.env` **on the server**. Its two secrets:

<ProjectCode file="shop-api/35-production/.env.production.example" region="secrets" />

In [Phase 5](/en/phase-5/#the-shop-role), PostgreSQL's password was `shop`, and we promised you that on a server it would be long and secret. Now it's 48 random characters:

- **They're generated on the server** with `openssl rand`, and never leave it: not through a chat, not through your laptop. They aren't the development ones: if a production one leaks, your laptop's are still safe, and the other way around.
- **`chmod 600 .env`**: only your user can read it, with the permissions from [Phase 1](/en/phase-1/linux-users-and-permissions/#changing-permissions-with-chmod-letters-or-numbers).
- **Never in Git**, as in [Phase 6](/en/phase-6/rate-limiting-secrets/#secrets-out-of-the-code-and-out-of-git).

The other lines come in other lessons: `TRUSTED_PROXY` in [lesson 4](/en/phase-8/nginx-reverse-proxy/), `ALLOWED_ORIGINS` in 5, `IMAGE` in 6. Phase 6's identity provider stays off: the practice one lives on your laptop.

<ProjectCode file="shop-api/35-production/.env.production.example" region="provider" />

**Leave the four lines with their `#`.** `OIDC_ISSUER=` with no value isn't the same as not having it: the variable exists, empty, and the API refuses to start.

### Logs: Docker doesn't trim them

Docker saves what the API writes in one file per container, with its default *driver*, `json-file`. According to [Docker's documentation](https://docs.docker.com/engine/logging/drivers/json-file/), **that file isn't rotated**: it grows with no limit. The installation from the introduction doesn't change that: `/etc/docker` is left empty.

Do the math. The healthcheck asks `/health` every 10 seconds, and each question is a line of about 290 bytes. That's 8,640 lines a day, about 2.5 MB: about 900 MB a year **without a single visitor**.

You fix it in `/etc/docker/daemon.json`, the engine's configuration:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

At 10 MB, Docker starts another file, and it keeps three at most. **It only applies to containers created afterwards**: you have to recreate them. systemd's journal, on the other hand, trims itself.

### A copy every night

A volume isn't a copy, as you saw in [Phase 7](/en/phase-7/docker-volumes/#backups-with-pg_dump): it's the only place your data lives. The <Term id="backup">backup</Term> is made by a script in the step:

<ProjectCode file="shop-api/35-production/deployment/backup.sh" region="backup" />

- **`umask 077`**: whatever the script creates is born for your user only. A backup holds the emails and the password hashes.
- **`exec -T db pg_dump … | gzip`**: the dump, compressed. `-T` means "no terminal," so it can go through the *pipe*.
- **First `.tmp`, then `mv`**: `set -e` stops the script at the first failure, and `trap … EXIT` is what runs on the way out, whether things went well or badly: it deletes the `.tmp`. There's never a half-made copy with the name of a good one.

<ProjectCode file="shop-api/35-production/deployment/backup.sh" region="prune" />

The pruning deletes the ones 7 days old or more, and only after a good new copy: if the database is down, the script has already failed and the old ones stay.

A systemd timer launches it, with two files like the service from [Phase 1](/en/phase-1/systemd-services-and-apt/#the-service-sheet-the-unit-file):

<ProjectCode file="shop-api/35-production/deployment/shop-backup.service" />

<ProjectCode file="shop-api/35-production/deployment/shop-backup.timer" />

- **`Type=oneshot`**: a task that ends, not a server.
- **`User=ubuntu`**: your user, not `root`. It can talk to Docker because it's in the `docker` group, which [is as good as root](/en/phase-8/#without-sudo-the-docker-group).
- **`OnCalendar=*-*-* 03:30:00`**: every day at 03:30. **`Persistent=true`**: if the server was off, it makes the copy when it boots.

**A copy on the same disk doesn't save you if you lose the disk.** Take it somewhere else every now and then, for example from your computer: `rsync -av ubuntu@192.168.5.15:/opt/shop/backups/ shop-backups/`.

### The .env, with new secrets

<TryIt
  title="2. A .env only you can read"
  cmd={`cp .env.production.example .env
chmod 600 .env
ls -l .env`}
  output="-rw------- 1 ubuntu ubuntu 2351 Oct 18 01:47 .env"
>

Look at `-rw-------`: read and write for `ubuntu`, nothing for anyone else. If you start it now, Compose refuses with `required variable POSTGRES_PASSWORD is missing a value`.

</TryIt>

Generate the two secrets and write them into `.env` without them going through your screen:

```sh
sed -i "s|^WEBHOOK_SECRET=.*|WEBHOOK_SECRET=$(openssl rand -base64 32)|" .env
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$(openssl rand -hex 24)|" .env
```

- **`$(openssl rand …)`**: the terminal runs what's inside and puts its output in its place.
- **`sed -i "s|A|B|"`**: changes in the file (`-i`) whatever matches `A` into `B`. `^WEBHOOK_SECRET=.*` is the line that starts with `WEBHOOK_SECRET=`. The separator is `|` because base64 uses `/`.

`.env` is still `600`. `grep -c change-this .env` should say `0`: the example secret is gone.

### Put a limit on the logs

`docker compose -f compose.production.yaml logs api` shows what the API has written; with `-f`, it waits for new lines. Look at its limits:

<TryIt
  title="8. No limit"
  cmd={`docker info --format "{{.LoggingDriver}}"
docker inspect --format "{{json .HostConfig.LogConfig}}" shop-api-1`}
  output={`json-file
{"Type":"json-file","Config":{}}`}
>

`Config` is empty: neither `max-size` nor `max-file`.

</TryIt>

`sudo tee` writes, with `root`'s permissions, whatever reaches it up to the `EOF` line:

<TryIt
  title="9. With a limit"
  cmd={`sudo tee /etc/docker/daemon.json <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
EOF
sudo systemctl restart docker
docker compose -f compose.production.yaml up -d --force-recreate
docker inspect --format "{{json .HostConfig.LogConfig}}" shop-api-1`}
  output={`{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
…
{"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}`}
>

`tee` repeats what it writes. When Docker restarts, the shop comes back on its own, but with an empty `Config` until `--force-recreate` creates its containers again. The last line now has the limits. If Docker doesn't start, the JSON has a mistake: `sudo journalctl -u docker -n 20` tells you which.

</TryIt>

### Restore the copy

A copy you've never restored is a hope. Try it in a new database, `test`, with your file's name:

<TryIt

  cmd={`docker compose -f compose.production.yaml exec -T db createdb -U shop test
gunzip -c backups/shop-2026-10-18-014942.sql.gz | docker compose -f compose.production.yaml exec -T db psql -U shop -d test -q -v ON_ERROR_STOP=1`}
  output={`…

--------

(1 row)`}
>

`createdb` creates the empty database, `gunzip -c` decompresses the copy and `psql` runs it in `test`. **`ON_ERROR_STOP=1`** stops at the first error instead of leaving it half done. The last `setval` puts the `id` counter back where it was.

</TryIt>

  cmd={`docker compose -f compose.production.yaml exec -T db psql -U shop -c "DELETE FROM users;"

`DELETE 1` is the disaster. `dropdb` can't delete a database with open connections: that's why the API is stopped first. `> /dev/null` throws away `psql`'s results, which you already saw in `test`. ## You have already seen it

- **Your home router.** After a power cut, it gives you wifi again without you doing anything: its policy is "always."
- **WhatsApp backups.** They happen on their own every day, if you choose so, and they go to iCloud or Google Drive, not to the phone: if you lose it, the copy is still there.
- **Time Machine, on the Mac.** It keeps hourly copies for the last day, daily copies for the last month and weekly copies before that: it deletes the old ones, like the 7-day pruning.

## Common mistakes

- **`docker compose up` without `-f` on the server.** It starts the development `compose.yaml`, with the same volume: it loads the practice accounts, with two admins whose password is public, and it doesn't come back after a reboot. You don't need it on the server: after `rm compose.yaml`, Compose will say `no configuration file provided: not found`.
- **Copying your development `.env`, or pushing it to Git.** The same secret lives in two places, and `localhost` and your laptop's provider get mixed up with production.
- **An `OIDC_` line with no `#` and no value.** The API doesn't start: `OIDC_ISSUER is not a URL`.
- **Copies that never leave the server, or that you've never restored.** If the disk dies, they go with it; if they don't restore, you find out on the worst possible day.
- **`down -v` in production.** It deletes the volume with all the orders. To stop, plain `down`.

## Summary

- `compose.production.yaml` is the server's shop: `restart: unless-stopped`, the API only on `127.0.0.1`, PostgreSQL and Redis with no ports and no practice accounts.
- The secrets are generated on the server, in a `.env` with `600` permissions that never goes to Git.
- With `unless-stopped`, Docker starts the shop again if it crashes and when the server boots, except what you stopped yourself.
- `json-file` doesn't trim the logs: `max-size` and `max-file` in `daemon.json`, and recreated containers.
- A systemd timer runs a `pg_dump` every night and keeps 7 days. A copy is worth what its last restore was worth, and it's better off the server.
