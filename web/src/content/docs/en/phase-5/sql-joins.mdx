## The problem

The delivery company from [Phase 4](/en/phase-4/) wants to print a label for each order: “Order 1: 2 × Mug.” You ask the database for the orders, and this is what's there:

```sql
SELECT id, product_id, quantity, status FROM orders ORDER BY id LIMIT 3;
```

```
 id | product_id | quantity | status
----+------------+----------+---------
  1 |          2 |        2 | shipped
  2 |          3 |        3 | shipped
  3 |          1 |        4 | shipped
(3 rows)
```

No sign of “Mug.” Order 1 says `product_id` 2, and the name is in another table, `products`. That's on purpose: the Mug appears in 9 of the 25 orders. If each order copied its name and its price, renaming it to “Large mug” would mean changing 9 rows, and if you forgot one, the shop would have two names for the same mug.

Each piece of data lives in a single place, and the order only points to it. For the label, you have to put them back together: that's a <Term id="join">JOIN</Term>.

## The analogy

If the Mug goes up in price, he changes a single line on the first page, not every order. And if he wants to write next to each order its product's category, and the Mug is in “Home” and in “Gifts,” that order takes up two lines: one per category.

## How it really works

The <Term id="query">queries</Term> in this lesson use the shop's data (`shop.sql`) freshly loaded, as in [lesson 1](/en/phase-5/what-is-sql/). The outputs are from PostgreSQL 18.6.

### Each row has a unique number: the primary key

This is how the `products` table starts in `shop.sql`:

```sql
CREATE TABLE products (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
```

`PRIMARY KEY` makes `id` the <Term id="primary-key">primary key</Term>: the column that identifies each row. **Its value is never repeated and can't be missing.** `GENERATED ALWAYS AS IDENTITY` asks PostgreSQL to fill in the number itself, 1, 2, 3…, as each product is inserted.

A primary key can also be two columns. In `product_categories`, which says which categories each product is in, it's the pair `(product_id, category_id)`: the T-shirt can be in Clothing once, not twice. If you try it (with no column list, the values go in the table's order):

```sql
INSERT INTO product_categories VALUES (1, 1);
```

```
ERROR:  duplicate key value violates unique constraint "product_categories_pkey"
DETAIL:  Key (product_id, category_id)=(1, 1) already exists.
```

The pair (1, 1) already exists. A <Term id="constraint">constraint</Term> is a rule that PostgreSQL checks on every change, and the primary key is one.

### An order points to its product: the foreign key

In `orders`, the column that points to the product is declared like this:

```sql
product_id integer NOT NULL REFERENCES products (id),
```

`REFERENCES products (id)` turns it into a <Term id="foreign-key">foreign key</Term>: its values have to exist in the `id` column of `products`. See what happens if someone creates an order for product 99:

```sql
INSERT INTO orders (product_id, quantity, status, created_at)
VALUES (99, 1, 'pending', now());
```

```
ERROR:  insert or update on table "orders" violates foreign key constraint "orders_product_id_fkey"
DETAIL:  Key (product_id)=(99) is not present in table "products".
```

The database refuses: product 99 isn't in `products`. `now()` is the date and time at this moment.

It works the other way around too. `DELETE FROM products WHERE id = 2;` fails with `Key (id)=(2) is still referenced from table "orders"`: the Mug has orders pointing to it. What to do in that case is chosen when the table is created: forbid it, as here, or delete those rows too, as `shop.sql` does with a product's categories. You'll see it in [lesson 4, “Modeling”](/en/phase-5/data-modeling-normalization/#on-delete-what-happens-when-you-delete-something-others-point-to).

**The foreign key guarantees that every order points to a product that exists.** Without it, a bug in the program would leave orphan orders, and a JOIN wouldn't find their product.

### INNER JOIN puts each order together with its product

This is the query for the labels:

```sql
SELECT o.id, p.name, o.quantity
FROM orders AS o
JOIN products AS p ON p.id = o.product_id
ORDER BY o.id
LIMIT 5;
```

```
 id |  name   | quantity
----+---------+----------
  1 | Mug     |        2
  2 | Hoodie  |        3
  3 | T-shirt |        4
  4 | Mug     |        1
  5 | Hoodie  |        2
(5 rows)
```

Word by word:

- `FROM orders AS o`: the first table, the orders. `AS o` gives it a short name, an alias.
- `JOIN products AS p`: the second table, with the alias `p`. Plain `JOIN` is `INNER JOIN`; both forms work.
- `ON p.id = o.product_id`: the condition. A row from orders and one from products go together when the product's `id` is the order's `product_id`.
- `SELECT o.id, p.name, o.quantity`: the columns, each with the table it comes from in front. `o.id` is the order's id, not the product's.
- `ORDER BY` and `LIMIT`, the ones from [lesson 1](/en/phase-5/what-is-sql/#order-by-and-limit-in-what-order-and-how-many).

For each order, PostgreSQL looks for the products that meet the condition, and **each pair that matches is a row of the result**. Order 1 carries 2, and product 2 is the Mug: row “1, Mug, 2”.

`INNER` means that only the pairs come out. A product with no orders, like the Cap, doesn't appear.

### Aliases shorten the names of the tables

Both tables have an `id` column. If you don't say which one you mean, PostgreSQL doesn't guess:

```sql
SELECT id, name, quantity
FROM orders
JOIN products ON products.id = orders.product_id;
```

```
ERROR:  column reference "id" is ambiguous
LINE 1: SELECT id, name, quantity
               ^
```

PostgreSQL can't tell which `id` you mean, and the `^` points to where. `name` and `quantity` don't cause an error, because each only exists in one of the two. You fix it with the table's name in front: `orders.id`.

With aliases, instead of `orders.id` you write `o.id`. The `AS` is optional (`FROM orders o` works too), but it reads better. **An alias only lasts as long as the query**: it doesn't change the table's name.

### LEFT JOIN also keeps the rows without a match

Which product has nobody ordered? With `INNER JOIN` you can't see it: the product with no orders has no pair, and it disappears. That's what `LEFT JOIN` is for:

```sql
SELECT p.name, o.id AS order_id
FROM products AS p
LEFT JOIN orders AS o ON o.product_id = p.id
ORDER BY o.id DESC
LIMIT 3;
```

```
  name   | order_id
---------+----------
 Cap     |
 Mug     |       25
 T-shirt |       24
(3 rows)
```

`LEFT JOIN` returns the same pairs as `INNER JOIN` and, on top of that, **each row of the left table that matches nothing, once, with the right table's columns empty**. The left one is the one before the `JOIN`: here, `products`. The Cap has no orders, and it comes out with `order_id` empty: it's `NULL`, [the missing value](/en/phase-5/what-is-sql/#null-the-missing-value) from lesson 1 (the playground writes it `NULL`).

`o.id AS order_id` changes the column's name in the result. `DESC` sorts from highest to lowest, and PostgreSQL puts the `NULL`s first in that order: that's why the Cap tops the list.

To keep only the ones without a match, filter by that empty value:

```sql
SELECT p.name
FROM products AS p
LEFT JOIN orders AS o ON o.product_id = p.id
WHERE o.id IS NULL;
```

`WHERE o.id IS NULL` keeps the rows where no order turned up. One comes out: Cap.

There's also `RIGHT JOIN`, the same with the tables the other way around, and `FULL JOIN`, which keeps the unmatched rows on both sides. You almost always write `LEFT JOIN`, with the table you want whole on the left.

### Three tables: the products and their categories

A product can be in several categories, and a category has several products. That's why neither `products` nor `categories` stores the relationship: it's in a third table, `product_categories`, with one row per pair. To read the names, you need two JOINs in a row:

```sql
SELECT p.name, c.name AS category
FROM products AS p
JOIN product_categories AS pc ON pc.product_id = p.id
JOIN categories AS c ON c.id = pc.category_id
ORDER BY p.id, c.name;
```

```
  name   | category
---------+----------
 T-shirt | Clothing
 Mug     | Gifts
 Mug     | Home
 Hoodie  | Clothing
 Cap     | Clothing
 Cap     | Gifts
(6 rows)
```

- The first `JOIN` pairs each product with its rows in `product_categories`.
- The second pairs each of those rows with its category, by `category_id`.
- `ORDER BY p.id, c.name` sorts by product and, within each one, by category.

Four products and six rows: the Mug and the Cap come out twice, once per category. Why this intermediate table is the right way to store the relationship, you'll see in [lesson 4, “Modeling”](/en/phase-5/data-modeling-normalization/#many-to-many-an-intermediate-table).

### A JOIN pairs up rows instead of intersecting sets

If you search for “SQL JOIN” in images, you'll see overlapping circles: two tables, and the `INNER JOIN` is the shared area. That drawing suggests the result never has more rows than the smallest table. It's false. Count the rows of each query in this lesson (`COUNT(*)` counts the rows of the result, and you'll see it in depth in [lesson 3, “GROUP BY”](/en/phase-5/sql-group-by/)):

| Query | Rows |
|---|---|
| `orders` alone | 25 |
| `products` alone | 4 |
| `orders JOIN products` | 25 |
| `products LEFT JOIN orders` | 26 |
| `orders JOIN product_categories` (each order with its product's categories) | 34 |

`orders JOIN products` gives 25, more than the 4 products: each order finds its product, and the Mug comes out in 9 rows. And with the categories, 34, more than either of the two tables:

```sql
SELECT o.id, p.name, c.name AS category
FROM orders AS o
JOIN products AS p ON p.id = o.product_id
JOIN product_categories AS pc ON pc.product_id = p.id
JOIN categories AS c ON c.id = pc.category_id
ORDER BY o.id, c.name
LIMIT 4;
```

```
 id |  name   | category
----+---------+----------
  1 | Mug     | Gifts
  1 | Mug     | Home
  2 | Hoodie  | Clothing
  3 | T-shirt | Clothing
(4 rows)
```

Order 1 comes out twice. The math: 9 Mug orders times 2 categories, 18 rows; plus 8 Hoodie orders and 8 T-shirt orders, with one each; 34.

**The rule: each row of one table comes out as many times as there are rows in the other that match it.** If it matches none, zero times in an `INNER JOIN` (in a `LEFT JOIN`, once, with empty values); once if it matches one, and several times if it matches several. The Venn diagram only gets right which rows survive, not how many times they come out.

This matters when you count or add up: if someone adds up the units sold after joining orders with categories, each mug counts twice.

## You have already seen it

- **The confirmation email for a purchase** carries each product's name and photo, even though the order only stores its number: someone did a JOIN to write it.
- **VLOOKUP** in a spreadsheet is a JOIN done by hand: for each row, it looks up its value in another table and brings back a column. The difference: VLOOKUP stops at the first match, and a JOIN returns them all.
- **The shop's API** returns `productId` in each order, and in the [GraphQL lesson](/en/phase-4/graphql-grpc-rest/#the-problem) the app had to make one more request per product. With a JOIN on the server, the name can arrive in the same response.

## Common mistakes

- **Forgetting the condition.** `JOIN` without `ON` is a syntax error in PostgreSQL, but the old form, `FROM orders, products`, without a `WHERE`, pairs every order with every product: 100 rows (25 times 4), almost all of them wrong.
- **Using `INNER JOIN` when you want them all.** A sales report per product with `INNER JOIN` has no row for the Cap: it looks as if it doesn't exist, when what's happening is that it sells zero.
- **Filtering the right table of a `LEFT JOIN` in the `WHERE`.** With `LEFT JOIN orders … WHERE o.status = 'pending'`, the Cap disappears again, because its `status` is empty. If you want “each product with its pending orders, if it has any,” put the condition in the `ON`: `ON o.product_id = p.id AND o.status = 'pending'`.
- **Adding up after a JOIN that multiplies.** If a row comes out twice, its numbers count twice.
- **Writing `id` when there are two.** Ambiguous column: put the table or its alias in front.

## Summary

- The shop's data is in several tables so that each piece lives in a single place. The primary key identifies each row, and a foreign key points to another table's.
- `REFERENCES` won't let you save an order for a product that doesn't exist nor, unless something else is said when creating the table, delete a product that has orders.
- `INNER JOIN` returns the pairs of rows that meet the `ON` condition; `LEFT JOIN`, on top of that, the rows on the left with no match, with empty values.
- With an intermediate table, two JOINs in a row join products and categories.
- A JOIN pairs up rows: each row comes out as many times as there are rows in the other table that match it. The result can have more rows than any of its tables.
