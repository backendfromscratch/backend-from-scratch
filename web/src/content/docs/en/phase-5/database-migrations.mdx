Ana wants the API to say how many units of each product are left: a new column, `stock`, in `products`. In [lesson 4](/en/phase-5/data-modeling-normalization/) and [lesson 5](/en/phase-5/node-postgres/), to change a table you edited `db/schema.sql` and ran `npm run db:create`, which drops the tables and creates them again.

## The analogy

<Analogy>

Imagine renovating a house with the family living in it. Nobody tears it down to add an outlet. Each job goes on a numbered sheet: “1. Put up the walls,” “2. An outlet in the kitchen.” On the fridge, a list of the jobs already done.

The contractor looks at the list, does the missing jobs in order and writes each one down when it's finished. If a job that was done turns out wrong, its sheet isn't rewritten: another one is added, “3. Move the outlet.”

<div slot="limits">

- A job can be left half-done. A migration in your runner can't: if it fails, nothing of it is left.
- In a house you can see whether the outlet is there. In a database you can't: that's why the list of what's done lives inside it, in a table.

</div>

## How it really works

### A migration is a change, not the whole schema

`db/schema.sql` goes away. In its place, a folder with two files:

<FileTree>

- db/
  - migrations/
    - 001-shop.sql the tables from lessons 4 and 5
    - 002-stock.sql the stock column
  - seed.sql

</FileTree>

Each file is a **<Term id="migration">migration</Term>**: one change to your tables, in <Term id="sql">SQL</Term>. 001 is your `schema.sql` with `IF NOT EXISTS` after each `CREATE TABLE`:

<ProjectCode file="shop-api/20-migrations/db/migrations/001-shop.sql" region="products" />

In an empty database, it creates the table. In yours, which already has it, it does nothing, and your data stays. From here on, **tables only change with new migrations**: 002, 003…

### Only forward, and a table that records it

A program, the **migration runner**, applies the missing ones. To know which, it keeps a table in the database itself, `migrations`, with one row for each one applied:

```
     name      |          applied_at
---------------+-------------------------------
 001-shop.sql  | 2026-10-13 23:47:47.898577+00
 002-stock.sql | 2026-10-13 23:47:47.902611+00
(2 rows)
```

Three rules make it work:

- **The number decides the order.** 002 adds a column to a table that 001 creates: the other way around wouldn't work.
- **Each one is applied only once.** If its name is in the table, it's skipped.
- **Only forward.** To undo a change, you write another migration. The history of your tables is the list of files, and it travels in Git with the code ([Phase 1](/en/phase-1/git-internals/)).

Why `001` and not `1`? The runner sorts the names as text, character by character, and that way `10-…` comes before `2-…`. With three digits, `002` comes before `010`.

### Each migration, all or nothing

A migration with several commands can fail halfway. If the first one had already changed the table, your database would be left in a state that isn't in any file. That's why the runner puts each migration in a **<Term id="transaction">transaction</Term>**: a group of commands that PostgreSQL saves all together or not at all.

- `BEGIN` opens the transaction.
- `COMMIT` saves everything done since the `BEGIN`.
- `ROLLBACK` undoes all of it, as if it had never happened.

In PostgreSQL, even an `ALTER TABLE` is undone with `ROLLBACK`; in MySQL, it isn't: it's saved on the spot. You'll see transactions in depth in [lesson 8](/en/phase-5/acid-transactions/).

### The runner, piece by piece

The runner is `scripts/migrate.ts`, and you write it yourself, without libraries, to see there's no magic: like [`node:http` before Hono](/en/phase-3/node-http-server/) in Phase 3. The beginning:

<ProjectCode file="shop-api/20-migrations/scripts/migrate.ts" region="folder" />

- `pool` is the <Term id="connection-pool">connection pool</Term> from `src/db.ts`, the one from [lesson 5](/en/phase-5/node-postgres/).
- `process.argv[2]` is whatever you write after the script's name. If you write nothing, it's `undefined`, and `??` uses what's on its right: the `db/migrations` folder. `join` joins the pieces of the path starting from `import.meta.dirname`, this file's folder.

Next, what's left to apply:

<ProjectCode file="shop-api/20-migrations/scripts/migrate.ts" region="record" />

- `CREATE TABLE IF NOT EXISTS migrations` creates the record table the first time. `name` is the <Term id="primary-key">primary key</Term>, so it doesn't repeat, and `applied_at` fills itself in with the time (`DEFAULT now()`).
- `SELECT name FROM migrations` reads the applied ones, and `new Set(…)` keeps them in a set: a list you can ask “is this one here?” with `.has()`.
- `readdir` reads the names of the files in the folder. `filter` keeps the `.sql` ones, `sort()` sorts them by name, and the second `filter` keeps the ones that aren't in the set ([`filter` and `map`, in Phase 3](/en/phase-3/javascript-for-backend/#choosing-and-transforming-a-list-filter-and-map)).

And applying them, each one in its own transaction:

<ProjectCode file="shop-api/20-migrations/scripts/migrate.ts" region="apply" mark={[6, 10, 14]} />

- `pool.connect()` asks the pool for a connection and keeps it: a transaction lives on a single connection.
- Inside the `for`, it reads each file, sends it whole to PostgreSQL and writes its name down in `migrations`, with a parameter (`$1`), as in lesson 5.
- **The change and its record go in the same transaction:** both stay, or neither does.
- If something fails, the `catch` does a `ROLLBACK`, writes the error, leaves an <Term id="exit-code">exit code</Term> of 1 and stops with `break`: the next one may depend on the one that failed.
- `finally` runs no matter what: it gives the connection back (`release`) and closes the pool, so the program ends. `try` and `catch` are the ones from [lesson 8 of Phase 3](/en/phase-3/node-errors-and-logging/#throw-throws-an-error-try-and-catch-catch-it).

About 35 lines, without the comments. In `package.json`, `db:create` makes way for `"db:migrate": "node --env-file-if-exists=.env scripts/migrate.ts"`.

### Adding stock to a table that already has rows

The first thing anyone thinks of is a single command: the `stock` column, a whole number (`integer`) that can't be missing (`NOT NULL`). Try it: since it fails, it changes nothing:

<TryIt
  title="A NOT NULL column, all at once"
  lang="sql"
  cmd="ALTER TABLE products ADD COLUMN stock integer NOT NULL;"
  output={`ERROR:  column "stock" of relation "products" contains null values`}
>

Inside `psql -d shop`, as in the [introduction](/en/phase-5/). The `stock` column of the table (“*relation*”) `products` would have `NULL` values.

</TryIt>

A new column reaches the four products with no value, `NULL`, and `NOT NULL` forbids it. The treacherous part: on an empty table, like your tests' one, the same command works. **It fails where there's data, which is usually production.**

The safe way is three steps, in `002-stock.sql`. First, the column without the rule:

<ProjectCode file="shop-api/20-migrations/db/migrations/002-stock.sql" region="column" />

`ALTER TABLE products` (“change the products table”) and `ADD COLUMN stock integer` (“add the stock column, a whole number”). The rows already there get it empty, and for now that's allowed.

Second, a value for each row that was already there:

<ProjectCode file="shop-api/20-migrations/db/migrations/002-stock.sql" region="backfill" />

The `UPDATE` from [lesson 1](/en/phase-5/what-is-sql/), only on the rows without a value. Ten is a starting stock, until Ana counts her warehouse.

Third, now that no row is empty, the rules:

<ProjectCode file="shop-api/20-migrations/db/migrations/002-stock.sql" region="rules" />

Word by word:

- `ALTER COLUMN stock SET DEFAULT 0`: a new product starts with 0 unless someone says otherwise.
- `ALTER COLUMN stock SET NOT NULL`: from now on it can't be missing. PostgreSQL checks it on every row, and it passes: step 2 filled them in.
- `ADD CONSTRAINT stock_not_negative CHECK (stock >= 0)`: a <Term id="constraint">constraint</Term> with a name: the stock is never negative.
- All three go in one command, separated by commas.

What about `ADD COLUMN stock integer NOT NULL DEFAULT 10`, in one go? In PostgreSQL it works, but new products would also start with 10. The three steps always work, even if each row's value is calculated from other columns.

### Renaming without breaking: expand and contract

Renaming a column is something else: `ALTER TABLE products RENAME COLUMN name TO title` takes an instant, but the running server keeps asking for `name`, and fails until the new code arrives. With two servers that are updated one after the other, the old code and the new code live side by side for a while.

The solution is **expand and contract**: first you widen, then you trim, and each step is a different migration or <Term id="deployment">deployment</Term>:

| Step | What changes | Who works |
|---|---|---|
| 1. Expand | A migration adds `title` and copies each `name` into it | The old code, which doesn't see it |
| 2. New code | It reads `title` (if it's empty, `name`) and writes to both columns | The old and the new, at the same time |
| 3. Contract | With no old code running, a migration copies into `title` whatever the old code wrote only in `name`, and drops `name` | The new code |

There's never code asking for a column that doesn't exist.

### An applied migration is never edited

Imagine that, after migrating, you change the `DEFAULT 0` in `002-stock.sql` to `DEFAULT 5`. Your database doesn't notice: 002 is already recorded, and the runner skips it. Your colleague's, freshly created, does apply it, with 5. **Same files, different databases**, and nothing warns you.

That's why a migration that has left your computer is never touched: if it was wrong, you write another one, 003.

### What the tools add

Migration tools do the same as your runner, and a bit more:

- **Generating the SQL.** drizzle-kit compares your tables, described in TypeScript, with their previous version and writes the migration. You'll see it in [lesson 9](/en/phase-5/orm-drizzle-prisma/), with your runner applying it.
- **Detecting edits.** Flyway, widely used with Java, keeps a fingerprint of each applied migration and refuses to go on if a file has changed.
- **Undoing and waiting their turn.** node-pg-migrate, for Node, lets you write how to undo each migration, and uses a lock so that two servers starting at the same time don't apply the same one.

## You have already seen it

- **The apps on your phone** keep your data in a small database inside the phone. If an update changes their tables, it brings migrations, and your notes are still there.
- **WordPress**, after updating, sometimes asks you to press a button to update the database: those are its migrations.
- **Rails, Django or Laravel**, frameworks for other languages, have their migrations folder and a command to apply them.

## Common mistakes

- **Editing a migration that's already applied.** The databases that already had it don't change: write another one.
- **Adding a `NOT NULL` column without a value to a table with rows.** It works on your empty table and fails in production: three steps.
- **Renaming or dropping a column at the same time the new code arrives.** The old code, still running, asks for it: expand and contract.
- **Changing the tables by hand with `psql` in production.** That change isn't in any file: no other database will have it.
- **Numbering `1`, `2`… `10`.** Sorted as text, `10` comes before `2`: use three digits.

## Summary

- Dropping the tables and creating them again only works when there's no data to keep.
- A migration is a numbered file with one change. The runner applies the missing ones, in order, and records them in a table in the database itself.
- Each migration goes in a transaction, together with its record: if something fails, `ROLLBACK`, and nothing is left half-done.
- A `NOT NULL` column on a table with rows takes three steps: the column, a value for each row and the rules. A rename, expand and contract.
- An applied migration is never edited: you write another one.

<QuizOption text="The ALTER TABLE’s change, but not the UPDATE’s: you have to undo it by hand before migrating again.">

That would happen without a transaction. With one, PostgreSQL undoes the `ALTER TABLE` too.

</QuizOption>

<QuizOption text="004, recorded as failed in migrations, and the runner will never try it again.">

The table only keeps the applied ones, and the record is undone with the rest. Next time, 004 is still pending.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Your API runs on two servers that are updated one after the other, and you want the name column to be called title. Which plan doesn’t break any request?"
  review="Renaming without breaking: expand and contract"
>

<QuizOption text="A migration with RENAME COLUMN and, right after, the new code: the rename is instant.">

The change is instant, but the old code keeps running for a while and asks for `name`, which no longer exists.

</QuizOption>

<QuizOption text="Add title, code that reads title and writes to both, and drop name at the end." correct>

It's expand and contract: at every moment, the columns the running code asks for exist.

</QuizOption>

<QuizOption text="Stop the API, rename and start it with the new code: it’s the only way not to break anything.">

While the API is stopped, every request fails: it does break things. And it's not the only way: expand and contract stops nothing.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="A teammate names his migrations 1-shop.sql, 2-stock.sql… and reaches 10-shipping.sql. What happens with this runner on an empty database?"
  review="Only forward, and a table that records it"
>

<QuizOption text="Nothing strange: sort() understands the number at the start of each name.">

`sort()` compares texts, character by character. It doesn't know `10` is a number.

</QuizOption>

<QuizOption text="The runner refuses: the names have to start with three digits.">

This runner doesn't check the names: it accepts any `.sql`. That's why the mistake goes unnoticed.

</QuizOption>

<QuizOption text="10 is applied right after 1, before 2." correct>

As text, `10-…` comes before `2-…`, because `1` comes before `2`. With three digits, `002` comes before `010`.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="A colleague clones the project and has her PostgreSQL with an empty shop database. What does she run to have the shop with its sample data?"
  review="A new database: migrate and load the data"
>

<QuizOption text="Only npm run db:seed: it creates the tables and fills them.">

`db:seed` only adds rows: without the tables, it fails with `relation "products" does not exist`. The migrations create the tables.

</QuizOption>

<QuizOption text="npm run db:migrate and then npm run db:seed." correct>

The migrations create the tables starting from 001, and `db:seed` fills them, because they're still empty.

</QuizOption>

<QuizOption text="A copy of your database: migrations only work for one that already has tables.">

In an empty one, 001 creates the tables: that's how the tests and any new server start from scratch.

</QuizOption>

</QuizQuestion>
