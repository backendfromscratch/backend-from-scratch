## The problem

At the end of [lesson 4, “OAuth”](/en/phase-6/oauth-openid-connect/), the shop already knows who it's talking to: Marta signs in with her password or with the provider, and Fast Delivery, with its key. But knowing who you are hasn't changed what you can do. The API still hands all the orders to anyone, and creating products still asks for the shared `ADMIN_TOKEN` from the [introduction](/en/phase-6/#the-admin-token-one-key-for-everyone).

Imagine that Carmen, a customer, looks at her order at `/v2/orders/27` and tries 26. If the API answers, Carmen is reading Marta's order. She hasn't broken anything: she has changed a number.

This isn't a textbook case. In 2018, an API of the United States Postal Service let any user with a session look up other users' data: about 60 million accounts ([KrebsOnSecurity](https://krebsonsecurity.com/2018/11/usps-site-exposed-data-on-60-million-users/)). **How does the shop decide what each person can do, and whose each piece of data is?**

## The analogy

<Analogy>

In a company, keys aren't handed out person by person: they're handed out by job. Whoever joins as a courier gets the courier key ring, which opens the warehouse and the loading dock, but not the safe. Whoever joins as an accountant gets a different one. The job is the role; each key on the ring, a permission.

And each employee has a locker. They're all the same and numbered, and your key opens yours, not the one next to it. Being able to open lockers isn't enough: it has to be yours.

<div slot="limits">

- A key ring once handed out is hard to get back. In the shop, the role lives in the database and is looked up on every request: if you change someone's role, their next request already notices.
- Someone else's locker can be seen, even if it can't be opened. The API goes further: to whoever asks for someone else's order, it answers that it doesn't exist.

</div>

</Analogy>

## How it really works

### Three roles, and a list of permissions for each one

Start with what each one should be able to do in the shop:

| | Customer (Marta, Carmen) | Delivery (Fast Delivery's key) | Admin (Ana, Luis) |
|---|---|---|---|
| Place orders | Yes | No | No |
| See orders | Their own | All | All |
| Change or cancel orders | Their own | No | All |
| Mark an order as shipped | No | Yes | Yes |
| Create and delete products | No | No | Yes |

Each row is a **permission** and each column, a **role**. Organizing authorization this way is called **<Term id="rbac">RBAC</Term>**, role-based access control. In the code, `src/permissions.ts`:

<ProjectCode file="shop-api/28-roles/src/permissions.ts" region="permissions" />

- **`Role` and `Permission`** are TypeScript types ([lesson 3 of Phase 3](/en/phase-3/typescript-with-node/)): if you write `'order:view-all'`, without the `s`, `npm run check` fails.
- **The names, `resource:action`**, are a common habit: they read on their own.
- **`PERMISSIONS`** is the table above: each role, with its list.

Admin doesn't have `orders:create`: in this shop, an order always belongs to a customer, and Ana doesn't shop with her admin account.

### The code asks about permissions, not roles

The tempting thing is to write `if (role !== 'admin')` in every route. The day a new role arrives, “customer support,” which must see all the orders without touching the products, you'll have to find every `if` and decide one by one. With permissions, you add a line to `PERMISSIONS`, and the routes don't change.

<ProjectCode file="shop-api/28-roles/src/permissions.ts" region="can" />

- **`roleOf`** takes the role from the session's account or, if there's no session, from the API key.
- **`can`** answers yes or no: does their role's list include that permission?

Each route says what it needs with `requirePermission`, a <Term id="middleware">middleware</Term>:

<ProjectCode file="shop-api/28-roles/src/permissions.ts" region="require-permission" />

- **`...permissions`** accepts one or several, and having any of them is enough. The routes that show orders use `requirePermission('orders:view-own', 'orders:view-all')`.
- **In `src/contract.ts`**, each route carries it in its list: `middleware: [requirePermission('products:manage')]`. It goes before validating the body, like the guard in the [middleware lesson](/en/phase-3/what-is-middleware/#a-guard-that-answers-401).

### 401, 403 or 404

`requirePermission` gives two different responses, the ones from the [status codes lesson](/en/phase-2/http-status-codes/#401-or-403-i-dont-know-who-you-are-or-you-cant) in Phase 2:

- **With no identity, `401`**, with `WWW-Authenticate`: the same response from `requireIdentity` you saw in [lesson 2](/en/phase-6/sessions-and-cookies/#400-when-signing-in-401-afterwards-with-www-authenticate), now in a function, `notIdentified` (`src/middleware/session.ts`), which both use. Identifying yourself can fix it.
- **With an identity and no permission, `403`**, without `WWW-Authenticate`: identifying yourself again changes nothing.

And there's a third case, which `requirePermission` doesn't see: the order exists, but it belongs to someone else. There the shop answers `404`, because [the 404 also hides things](/en/phase-2/http-status-codes/#the-404-also-hides-things): a `403` would confirm to Carmen that order 26 exists.

### Each customer, their own orders: BOLA

`requirePermission` lets Carmen through on `GET /v2/orders/:id`, because she has `orders:view-own`. But which order is she asking for? **The role says what kind of things you can do; only the data says whose it is.** Forgetting that second check is called **<Term id="bola">BOLA</Term>** (*Broken Object Level Authorization*).

It's the first in the [<Term id="owasp">OWASP</Term> API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10) of 2023, the list of the most serious flaws in APIs. The fifth, *Broken Function Level Authorization*, is the other half: a route without its `requirePermission`.

First, each order needs an owner. It's the second part of migration 009:

<ProjectCode file="shop-api/28-roles/db/migrations/009-roles.sql" region="customer-orders" />

- **`customer_id` can be `NULL`:** the 25 sample orders were placed when the shop had no accounts, and nobody knows whose they are. Only admin and delivery see them.
- **The index starts with the customer:** a customer's list comes out fast, as in the [indexes lesson](/en/phase-5/database-indexes-explain/).

Then, every route that receives an id checks it, in `src/v2.ts`:

<ProjectCode file="shop-api/28-roles/src/v2.ts" region="visible-order" />

- **With the “all” permission**, any order; if not, only one whose `customerId` is the session's.
- **Someone else's comes back as `undefined`**, just like one that doesn't exist, and the route answers the same `404`.
- **The same function** is used to see, change and cancel an order, and for its event stream: one check, in a single place.

The list doesn't receive an id, but it filters too:

<ProjectCode file="shop-api/28-roles/src/v2.ts" region="only-their-own" />

`customerId` stays `undefined` for whoever sees all of them; for a customer, it's their id, and `src/pagination.ts` adds the condition `customer_id = …` to the query.

When an order is created, the owner comes from the session (`c.var.user`), **never from the request body**: if the JSON could carry a `customerId`, anyone could place orders in someone else's name.

### Goodbye to the ADMIN_TOKEN: being an admin is an account's role

The first part of the migration gives a role to each account and to each key:

<ProjectCode file="shop-api/28-roles/db/migrations/009-roles.sql" region="roles" />

- **`DEFAULT 'customer'`:** Marta, and whoever signs up tomorrow, are customers.
- **`CHECK`** only accepts the roles that exist, and a key is never `customer`: a program has no orders of its own.
- **Making someone an admin is an `UPDATE` by hand**, never an API route.

`ADMIN_TOKEN` disappears from `src/config.ts` and `.env.example`, and `src/middleware/admin-only.ts` goes with it. The introduction's problems go with it too: Ana and Luis each sign in with their own account, so the shop knows who makes each request; taking access away from one of them is changing their role, without touching the other; and the delivery key isn't an admin key.

### Least privilege, for the delivery key too

Fast Delivery needs to see the orders and mark them as shipped, and nothing else. For that it has a new route, `POST /v2/orders/{id}/shipment`, with `requirePermission('orders:ship')`.

If its key leaks, in a log or in a repository, whoever finds it sees orders and marks them as shipped, but doesn't create products or cancel anything. It's the <Term id="least-privilege">least privilege</Term> from the [permissions lesson in Phase 1](/en/phase-1/linux-users-and-permissions/), applied to the API. **Every extra permission is possible damage if the key leaks.**

It could be tightened further: delivery also sees the pending orders, which it doesn't need. A stricter shop would give it only the paid ones.

### A breaking change, on purpose

Until today, `GET /v2/orders` answered anyone. From this lesson on, with no identity, it answers `401`, and a program that listed orders without identifying itself stops working: a <Term id="breaking-change">breaking change</Term>.

In the [versioning lesson](/en/phase-4/api-versioning/#warn-before-switching-off-deprecation-sunset-and-link) you learned to warn first, with `Deprecation` and `Sunset`, and to leave months of margin. Here there's no warning, and `/v1`, which uses the same routes, closes the same way. The warning protects the convenience of whoever uses the API; here, what's at stake is the customers' data, and **every day of warning is a day when anyone can read all the orders**.

A security hole is closed as soon as it's seen. Afterwards, the partners are told and given a way to identify themselves: Fast Delivery already has its key.

## Try it

The goal: make the same requests as five identities (nobody, Marta, Carmen, Fast Delivery and Ana) and check that each one sees and does only what's theirs.

You're going to try to read another person's order in your own shop, on `localhost`. Doing it on a system that isn't yours, without permission, is a crime.

## You have already seen it

- **A shared document.** When you share a document in Google Drive you choose “Viewer”, “Commenter” or “Editor”: a role, not a list of permissions for each person.
- **Linux groups.** In the [permissions lesson in Phase 1](/en/phase-1/linux-users-and-permissions/), a file gives permissions to a group, and adding someone to the group is enough: the same idea as a role.
- **Your order number in the URL.** Many shops show `/orders/12345`. If changing that number showed another person's order, it would be BOLA: don't try it on other people's sites.

## Common mistakes

- **Checking permissions only in the frontend,** by hiding the button: anyone can call the API with `curl`.
- **Checking that there's a session and forgetting whose the data is.** Every route that receives an id needs its check, including the events one and the `/v1` one.
- **Taking the owner from the request body** instead of from the session.
- **Asking about roles in the code** (`role === 'admin'`) instead of about permissions.
- **Answering `403` to someone else's order,** which confirms it exists, or `401` to someone who is identified and isn't allowed.
- **Sharing something stored by key between accounts.** With the same `Idempotency-Key`, Pablo would get Carmen's order; that's why `idempotency.ts` stores each key with its account.
- **Relying on random ids instead of checking.** An id that's hard to guess helps, but it ends up in links, logs and screenshots.
- **Giving a program more permissions “just in case.”**

## Summary

- Authorization decides what someone who is already identified can do. With RBAC, each account has a role and each role, a list of permissions.
- The code asks about permissions (`requirePermission('products:manage')`), never about role names: a new role is one more line in the table.
- The role isn't enough: every route that receives an id checks whose the data is. Forgetting it is BOLA, the first flaw in the OWASP API Security Top 10.
- With no identity, `401`; identified and not allowed, `403`; someone else's data, `404`, so as not to confirm it exists.
- Each role and each key, with just what it needs. And a security hole is closed as soon as it's seen, even if it breaks a client of the API.

The routes don't change: the new role is one line in `PERMISSIONS`, with `orders:view-all` and without `products:manage`.

</QuizOption>

<QuizOption text="Make whoever works in customer support an admin: you have to be an admin to see all the orders.">

Seeing all the orders is a permission, not a role. As admins they could also delete products: the opposite of least privilege.
