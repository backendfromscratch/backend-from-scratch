## The problem

The delivery company from [Phase 4](/en/phase-4/), Fast Delivery, wants its program to mark orders as shipped. But a program has no browser and doesn't type passwords into a form. How does it tell the shop who it is? Today, the only way would be to give it the `ADMIN_TOKEN`, and in the [introduction](/en/phase-6/) you saw what that means.

While you think about it, Luis reads on a forum: “Sessions in the database are outdated. Use JWT: the server doesn't store anything.” Is he right?

This lesson answers both.

## The analogy

<Analogy>

At a theater's coat check they give you a ticket with a number, 47. The ticket says nothing: the coat, and whose it is, are in the coat check. If you lose it and tell them, they cancel it on the spot. That's the session from [lesson 2](/en/phase-6/sessions-and-cookies/).

At a festival they put a wristband on you that says it all, “VIP Area · Saturday,” with a hologram only the organizers make. Every bar checks it by looking at it, without calling anyone. But anyone who sees it reads what it says, and if it's stolen, it works until Sunday: no bar finds out. That's a JWT.

<div slot="limits">

- A hologram can be imitated with patience. A JWT's signature can't be made without the secret, if it's long and random.
- A wristband can be read at a glance. A JWT looks like gibberish, but it isn't encrypted: one command reads it.
- The wristband is tied to your wrist. A JWT isn't: whoever copies it gets in.

## How it really works

### Three parts separated by dots

This is a JWT made by this lesson's example, `examples/jwt.ts`:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJyb2xlIjoiY3VzdG9tZXIiLCJzdWIiOiJjYXJtZW4iLCJpc3MiOiJzaG9wLWFwaSIsImF1ZCI6InNob3AtYXBpIiwiaWF0IjoxNzkxOTUyOTI0LCJleHAiOjE3OTE5NTM4MjR9.YquKMDhnqilUifK7j_2mf9FUwANwm8OwJjsSAR68VNE
```

It has three parts, separated by dots:

| Part | What it carries | In this token |
|---|---|---|
| Header | How it's signed | `{"alg":"HS256","typ":"JWT"}` |
| Payload | What the token claims | `{"role":"customer",` `"sub":"carmen",` `"iss":"shop-api",` `"aud":"shop-api",` `"iat":1791952924,` `"exp":1791953824}` |
| Signature | 32 bytes that prove nobody has changed the other two | It can't be read: it's bytes |

A <Term id="jwt">JWT</Term> (*JSON Web Token*, pronounced like the word *jot*) is just that: signed <Term id="json">JSON</Term> that fits in a header. The names in the payload are short because they travel in every request, and RFC 7519 defines them:

- **`sub`** (*subject*): who the token is about.
- **`iss`** (*issuer*): who issued it.
- **`aud`** (*audience*): who it's for, which server should accept it.
- **`iat`** and **`exp`** (*issued at*, *expiration*): when it was made and when it expires, in seconds since January 1, 1970. `1791952924` is October 14, 2026, at 04:42:04 UTC, and `exp`, fifteen minutes later.

`role` isn't standard: whoever issues the token adds whatever data they want.

### Signed, not encrypted

The first two parts are in **base64url**. Base64 writes any data with 64 printable characters: letters, digits, `+` and `/`. The url variant swaps those two for `-` and `_`, which fit in a URL, and drops the `=` at the end. That's why every JWT starts with `eyJ`: it's `{"` in base64.

There's no key at all: any program undoes it. **A JWT is signed, not <Term id="encryption">encrypted</Term>: whoever has it reads everything it carries.** There's an encrypted variant, JWE, but the JWTs you'll see are like this one. Never put anything in one that the person carrying it can't see.

The signature hides nothing. It guarantees two things: that it was issued by whoever has the key, and that nobody has changed a single letter.

### Signing and checking: a secret or a key pair

The header says in `alg` how it was signed. There are two families:

- **HS256:** an <Term id="hmac">HMAC</Term>-SHA256 of the first two parts with a <Term id="secret">secret</Term>, like the signature of the [webhooks in Phase 4](/en/phase-4/webhooks-idempotency/#the-signature-an-hmac-of-the-body-with-a-secret). The same secret signs and checks: whoever can check can forge.
- **RS256 or ES256:** a <Term id="digital-signature">digital signature</Term> with a <Term id="private-key">private key</Term>, which anyone checks with the <Term id="public-key">public</Term> one, as in [TLS](/en/phase-0/tls-and-https/#two-keys-public-key-cryptography). Only the issuer signs. That's how Google signs the tokens for “Sign in with Google,” and it publishes its public keys so any website can check them ([lesson 4, “OAuth”](/en/phase-6/oauth-openid-connect/)).

The example uses HS256 with `jose`, the most widely used JWT library in Node, with no dependencies:

- `new SignJWT({ role: 'customer' })` starts the token with a piece of data of its own.
- `setProtectedHeader` writes the header, and each `set…`, a standard field. `'15m'` is fifteen minutes.
- `.sign(secret)` computes the signature. The secret comes from the <Term id="environment-variable">environment variable</Term> `JWT_SECRET` or, if it doesn't exist, it's 32 random bytes, different on every run.

Checking is more than reading:

<ProjectCode file="shop-api/26-jwt-keys/examples/jwt.ts" region="check" />

- `jwtVerify` recomputes the signature with the secret and compares it. If it matches, it looks at `exp`, `iss` and `aud`.
- **`algorithms: ['HS256']`: the algorithm is decided by whoever checks, never by the token.** You'll see why in a moment.
- If something fails, `jose` throws an error with a code that says what, like `ERR_JWT_EXPIRED`.

### What goes wrong

RFC 8725 collects the mistakes seen in real life. The ones that matter most:

- **`alg: none`.** The standard allows unsigned tokens, with `"alg":"none"`. A library that obeys the header accepts one forged by anyone, with an empty signature. In 2015, [several accepted it](https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/). The defense: the `algorithms` list.
- **Reading without checking.** Libraries come with a function to read the payload without looking at the signature (in `jose`, `decodeJwt`). Deciding with it means believing whatever the sender of the token says.
- **Not looking at `exp` or `aud`.** Without an expiry, a stolen token works forever. Without an audience, a token the shop made for the payment gateway would also work at the shop. `jose` looks at `exp` if the token has it, but at `aud` and `iss` only if you ask it to.
- **A short secret.** With a token in hand, secrets are tried on another computer, millions per second, as with the passwords in [lesson 1](/en/phase-6/how-to-store-passwords/#sha-256-is-too-fast). `jose` accepts a three-letter one without complaining. Use 32 random bytes.
- **Storing it where JavaScript can read it.** Many websites keep it in localStorage. If someone runs their JavaScript on the page (the <Term id="xss">XSS</Term> from [lesson 6](/en/phase-6/sql-injection-xss/)), they take it. An `HttpOnly` cookie [can't be read from JavaScript](/en/phase-2/cookies-httponly-secure-samesite/#cookies-or-localstorage).

And the biggest one, which isn't a code mistake: **it can't be canceled**.

### Sessions vs JWT

The argument Luis read on the forum is half true: with JWT, the server doesn't store anything. Look at what it costs:

| | Session (lesson 2) | JWT |
|---|---|---|
| What the client carries | A random 43-character id that says nothing | The signed data: 217 characters in the example, in every request |
| What the server stores | One row per session | Nothing, only the secret or the key to check it |
| How it's checked | A query by <Term id="primary-key">primary key</Term> | A calculation, with no database |
| Signing out or canceling it | The row is deleted: it doesn't work on the next request | Impossible: it works until `exp` |
| If you take a permission away from someone | On the next request | When their token expires |

To cancel a JWT early, the server has to note down the canceled ones and look them up on every request: a table and a query, what the JWT promised to save. The usual fix, a fifteen-minute JWT plus a second token to renew it stored in the database, turns back into a session with more pieces.

And the savings are small: the shop already talks to PostgreSQL on almost every request, and looking up by primary key is one of the fastest things it does ([indexes lesson](/en/phase-5/database-indexes-explain/)).

**The course's answer: sessions for people in a browser; JWT between services.** A JWT fits when one server has to trust another without asking it. For example, the shop could give the payment gateway a one-minute token with `aud: payment-gateway`. And an identity provider tells you who you are with a JWT, the OpenID Connect `id_token` from lesson 4.

### API keys: how a program identifies itself

And Fast Delivery? Its program runs on a server, day and night, with nobody in front of it. A JWT that never expires would be a key that's impossible to take back. It needs an **<Term id="api-key">API key</Term>**: a long, random piece of text that identifies it, like a session that doesn't expire and is canceled by deleting it. This is how it's created, in `src/api-keys.ts`:

<ProjectCode file="shop-api/26-jwt-keys/src/api-keys.ts" region="create-key" />

- **`randomBytes(32)`**: 256 random bits, like the session id. Nobody guesses it.
- **`shop_` in front:** whoever finds it in a log or in a repository knows where it's from. That's how GitHub recognizes other companies' keys and warns if they're pushed: `ghp_` ones are GitHub's, and `sk_live_` ones, Stripe's.
- **The table stores its <Term id="hash">hash</Term>, never the key:** the key is shown once, when it's created. SHA-256, a fast one, is enough: argon2 slows down whoever tries likely passwords (lesson 1), and for a random key there's no list to try.

On every request a new <Term id="middleware">middleware</Term> looks it up, `src/middleware/api-key.ts`:

<ProjectCode file="shop-api/26-jwt-keys/src/middleware/api-key.ts" region="load-api-key" />

- It reads `Authorization: Bearer …`, the [header from Phase 2](/en/phase-2/http-headers/#authorization-who-you-are). The prefix tells it apart from a session id, which can also arrive that way.
- `findKey` looks it up by its hash and notes in `used_at` when it was used: a forgotten key can be deleted.

With no session and no key, `requireIdentity` answers `401` with `WWW-Authenticate: Bearer realm="shop-api"`, the challenge RFC 6750 describes. For now, the key only identifies: `GET /v2/me` says who you are. What Fast Delivery can do with it comes in [lesson 5, “Authorization”](/en/phase-6/rbac-roles-permissions/).

>

It needs neither PostgreSQL nor the server. Your token and your times will be different. Look at the four tricks:

- **Payload changed:** `sub` goes from `carmen` to `pablo` with the old signature, which no longer matches.
- **`alg: none`:** `none` isn't in `algorithms`.
- **Expired:** a good signature, but `exp` has already passed.
- **Another audience:** a good signature, but it's for `payment-gateway`.

If you get `Cannot find package 'jose'`, step 1 is missing.

</TryIt>

Now read it without the secret and without `jose`, as anyone who copies it would:

<TryIt
  title="5. Read it with base64"
  cmd={`TOKEN=$(node examples/jwt.ts | sed -n 2p)
echo "$TOKEN" | cut -d. -f1 | base64 -d
echo
echo "$TOKEN" | cut -d. -f2 | base64 -d
echo`}
  output={`{"alg":"HS256","typ":"JWT"}
{"role":"customer","sub":"carmen","iss":"shop-api","aud":"shop-api","iat":1791952952,"exp":1791953852}`}
>

`sed -n 2p` keeps the second line, the token, and `cut -d. -f1`, the first part between dots ([pipes lesson in Phase 1](/en/phase-1/pipes-and-redirection/)). `base64 -d` decodes it. Each lone `echo` adds a line break.

And the `=` that base64 usually ends with? base64url drops that padding, and this token's header and payload need none: each is a multiple of four characters long. Other data may need one or two, and without them macOS's `base64` eats the last characters, like the closing `}`: add them at the end. On Linux it comes out right with or without them.

</TryIt>

<SelfCheck question="Challenge: HS256 is the HMAC from Phase 4. Compute a token’s signature yourself with openssl and compare it with its third part.">

Set the secret yourself and sign the first two parts, with the dot in between:

```sh
export JWT_SECRET=the-shop-secret
TOKEN=$(node examples/jwt.ts | sed -n 2p)
echo "$TOKEN" | cut -d. -f3
printf '%s' "$(echo "$TOKEN" | cut -d. -f1-2)" | openssl dgst -sha256 -hmac "$JWT_SECRET" -binary | base64 | tr '+/' '-_' | tr -d '='
```

```text
LgFyGQ2jelblGQP0CIN0RfxLhGrtphV39MC3owfsiGA
LgFyGQ2jelblGQP0CIN0RfxLhGrtphV39MC3owfsiGA
```

The two lines are the same. `-binary` gives the HMAC's 32 bytes, and `tr` turns them from base64 into base64url. **With the secret, anyone can sign whatever they want**: that's why it lives in the `.env`, and it's never a password.

</SelfCheck>

## You have already seen it

- **“Sign in with Google.”** The website receives from Google a JWT signed with its private key: the `id_token` from lesson 4.
- **A header that starts with `eyJ`.** In the *Network* tab of DevTools, many websites send `Authorization: Bearer eyJ…`: a JWT, which you read with `base64` as here. Don't paste it into a website that “decodes tokens”: [a real token isn't shown to anyone](/en/phase-2/http-headers/#authorization-who-you-are).
- **The keys of the services you use.** A maps or payments service gives you a key, and shows it to you only once.

## Common mistakes

- **Putting in the JWT what nobody should read.** It's in base64url, not encrypted.
- **Letting the token choose the algorithm, or reading it without checking it.** Set `algorithms` and use `jwtVerify`, never `decodeJwt`, to decide.
- **Using JWTs that last days as a session.** They can't be canceled. For people in a browser, a session.
- **A short secret, or the same one for two things.** 32 random bytes, one per use: don't reuse the `WEBHOOK_SECRET`.
- **The API key in the URL or in the frontend.** URLs end up in logs, and anyone can read a page's JavaScript. It goes in `Authorization`, from a server.
- **Storing the key as is.** Store its hash, and show it only once.

## Summary

- A JWT is three parts in base64url: header, payload and signature. It's signed, not encrypted: anyone can read it.
- HS256 signs with a shared secret, an HMAC; RS256 and ES256, with a private key that's checked with the public one.
- Checking means looking at the signature with a fixed algorithm, `exp`, `iss` and `aud`. `alg: none` and reading without checking are the classic mistakes.
- A JWT can't be canceled before `exp`. Sessions for people in a browser; JWT between services and as an `id_token`.
- A program identifies itself with an API key: long, random, stored as a hash, sent in `Authorization: Bearer` and canceled by deleting it.

No library does that. The expiry and the signature are checked separately, and both have to be right.

</QuizOption>

<QuizOption text="In the API: it accepts the algorithm the token says, instead of setting it itself." correct>

Whoever checks decides the algorithm, like `algorithms: ['HS256']` in the example, and `none` isn't on the list.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="The shop gives its customers a JWT that lasts a week. Carmen’s laptop is stolen with her session open. What can the shop do today?"
  review="Sessions vs JWT"
>

<QuizOption text="Nothing, unless it keeps a list of canceled tokens and checks it on every request." correct>

The token is valid until its `exp`: its signature doesn't change. Canceling it early takes a table and a query, like a session.

</QuizOption>

<QuizOption text="Delete Carmen’s token from the database.">

A JWT isn't in the database: that's its promise. With a session, deleting the row would be enough.

</QuizOption>

<QuizOption text="Change the stolen token’s exp from the server to a date that has already passed.">

The token is on the stolen laptop, not on the server, and changing its payload would break the signature.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="In DevTools you see Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiI0MiJ9.k3Hq… What can you learn without any key?"
  review="Three parts separated by dots"
>

<QuizOption text="Nothing: an RS256 token can only be read with the public key of whoever signed it.">

The public key is for checking the signature, not for reading. Header and payload are base64url.

</QuizOption>

<QuizOption text="What the header and the payload say: that it was signed with RS256 and that sub is 42." correct>

They're JSON in base64url: `base64 -d` decodes them. What you can't do is make another signature.

</QuizOption>

<QuizOption text="Everything, including the private key: base64 decodes the signature and the key comes out of it.">

The decoded signature is meaningless bytes. The private key can't be extracted from a signature.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="The shop stores passwords with argon2 and API keys with SHA-256. Why not argon2 for the keys too?"
  review="API keys: how a program identifies itself"
>

<QuizOption text="Because SHA-256 can be undone, so the shop can show the key again.">

No hash can be undone, SHA-256 included. That's why `create-key` shows it only once.

</QuizOption>

<QuizOption text="Because argon2 only works with the short texts a person types, like a password.">

argon2 computes the hash of any text. The reason is a different one: what can be tried.

</QuizOption>

<QuizOption text="Because a random key has no list of likely ones, and a slow hash would slow down every request." correct>

argon2 is slow to hold back whoever tries likely passwords. With 256 random bits there's nothing to try.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Fast Delivery suggests sending its key in the URL, /v2/orders?key=shop_…, because it’s easier to program. What do you answer?"
  review="Common mistakes"
>

<QuizOption text="That it goes in Authorization: Bearer, because URLs get recorded in logs and histories." correct>

Servers, proxies and browsers store full URLs. An `Authorization` header isn't usually recorded.

</QuizOption>

<QuizOption text="That it doesn’t matter: with HTTPS, the URL isn’t stored anywhere.">

HTTPS encrypts it on the way, but the server receives it whole and writes it to its log.

</QuizOption>

<QuizOption text="That a cookie is better, because programs can only send secrets in cookies.">

A program sends whatever headers it wants, and `Authorization` is the standard one. Cookies are a browser thing.

</QuizOption>

</QuizQuestion>
