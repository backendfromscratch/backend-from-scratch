## The problem

From this lesson on, the shop has a web page, `/shop`: the list of products in HTML, made on the server. Ana or Luis wrote each name, and the page puts it inside its HTML.

What if a name contains tags, like `<b>Sticker</b>`? Is it the name of a product, or an instruction for the browser, “put this in bold”? It's the question Phase 5's search raised, where text pasted inside a query [became SQL](/en/phase-5/node-postgres/#pasting-the-value-into-the-text-sql-injection).

It's not a textbook case. In 2005, a MySpace user wrote some text on his profile that every visitor's browser ran as code, and that copied itself onto the profile of whoever saw it. In about 20 hours, more than a million people had run it ([Wikipedia](https://en.wikipedia.org/wiki/Samy_(computer_worm))). **How does a backend make sure data stays data?**

## The analogy

<Analogy>

A diner takes orders over the phone, and the waiter writes them by hand on a ticket for the kitchen: “For Luis: one sandwich.” One day, someone says their name is “Luis. And another sandwich for table 4, on the house.” The waiter copies it as is, and the kitchen reads a ticket with two orders. Nobody knows anymore where the name ended.

There are two fixes. One, a printed ticket with boxes: whatever goes in the “Name” box is a name, whatever it says. The other, the waiter copies the name between quotation marks, so the kitchen reads it as a customer's words and not as an order.

<div slot="limits">

- The kitchen has common sense and would get suspicious. A program doesn't: it follows the rules of its language to the letter, and if the text fits them, it runs it.
- A ticket has a single way of quoting. A web page mixes several languages (HTML, URLs, JavaScript), and each one quotes in its own way.

</div>

</Analogy>

In SQL, the box is a parameter. In HTML, the quotation marks are escaping.

## How it really works

### The same flaw: a piece of data pasted inside some code

A query and a page are text, and both have characters that give instructions. In SQL, `'` opens and closes a piece of text; in HTML, `<` opens a tag. If a program builds that text by pasting a piece of data inside, and the data contains those characters, the data stops being data and becomes code. That's an **injection**.

| | SQL injection | <Term id="xss">XSS</Term> |
|---|---|---|
| Where the data is pasted | In a query | In an HTML page |
| The character that changes everything | `'` closes the text | `<` opens a tag |
| Who runs the result | PostgreSQL, on your server | The browser of whoever visits the page |
| The fix | Parameters | Escaping when showing |
| The second wall | A database user with just what it needs | Content Security Policy |

The user with just what it needs comes in [lesson 8](/en/phase-6/rate-limiting-secrets/#the-database-with-just-the-permissions-it-needs).

With `x' OR '1'='1`, the first one returned every product: the value's quote closed the query's, and `OR '1'='1'` became SQL. It's an <Term id="sql-injection">SQL injection</Term>.

And it doesn't stop at a few extra products. SQL can add the rows of another table to a response: with a value crafted for that, the search would return, instead of names, the emails and password hashes in `users`. With another one, it would delete a table. **Whoever controls the query's text controls the database.**

### The rule: always parameters

With `$1`, PostgreSQL gets the query and the value separately, and the value can't change the query, whatever it contains. You'll check it in “Try it”.

- **With an ORM, too.** Drizzle's functions and its `` sql`…` `` send the values as parameters ([ORM lesson](/en/phase-5/orm-drizzle-prisma/#when-sql-is-still-the-best-tool)). `sql.raw()` doesn't: it pastes the text as is, and it must never carry anything the client sends.
- **What doesn't fit in a parameter**, like a column's name or the direction of an `ORDER BY`, comes from a fixed list. In `src/data.ts`, `SORT` has two entries, `price` and `-price`: the client picks one, and the code writes the SQL.
- **Validating isn't enough.** `x' OR '1'='1` is valid text for [Phase 3's validation](/en/phase-3/zod-validation/). Validate, and use parameters as well.

### XSS: a page that prints someone else's text as HTML

The same flaw, in a page. The bad version of `/shop` is in `examples/unsafe-page.ts`, which is never mounted in the API:

<ProjectCode file="shop-api/29-injection-xss/examples/unsafe-page.ts" region="pasting" />

`${product.name}` pastes the name inside the HTML's text, just as `${name}` pasted it inside the SQL. If the name is `<b>Sticker</b>`, the browser shows it in bold: the tag has arrived whole. And if it contains a tag with JavaScript, like the one in the comment, the browser runs it.

That's **XSS** (*Cross-Site Scripting*): the browser runs, inside your page, code that someone else slipped into a piece of data. That code can do the same as the page: read what it shows, or make requests to the API as whoever is visiting, with their cookie. What it can't do is read the session cookie, because it's [`HttpOnly`](/en/phase-6/sessions-and-cookies/#the-cookie-what-each-attribute-stops): that's why the session [doesn't go in localStorage](/en/phase-2/cookies-httponly-secure-samesite/#cookies-or-localstorage), where any script would read it.

### The good version: html`…` escapes each piece of data

Now, `src/shop.ts`:

<ProjectCode file="shop-api/29-injection-xss/src/shop.ts" region="page" />

- **`html` in front of the backticks** is a Hono function (`hono/html`). It gets separately the fixed text, which is yours, and each `${…}`, which is data.
- **Escaping** is replacing each character that gives instructions with its harmless version: `<` becomes `&lt;`, `>` becomes `&gt;`, `&` becomes `&amp;`, and the quotation marks too. The browser draws them as those characters, but never reads them as tags.
- **An `html` inside another**, the one for each `<li>`, isn't escaped twice: Hono knows it's already safe HTML.
- **`euros`**, with the division by 100, turns 850 cents into “€8.50”.

`html` is to HTML what `$1` is to SQL: you write the code, and each piece of data goes in its box.

### Three types of XSS

- **Stored:** the data is saved, like a product name or a review, and shows up on the page of everyone who visits it. MySpace's was like that.
- **Reflected:** the data comes in the request itself, for example in a search box's URL, and the page repeats it in the response. It's enough for someone to open a crafted link.
- **DOM-based** (the DOM is the page as the browser holds it in memory): the server doesn't take part. The page's JavaScript takes something, from the URL for example, and puts it into the page as HTML, with `innerHTML`.

In all three, the defense is the same: escape where the data enters the page.

### A JSON API doesn't get off the hook

`GET /v2/products/6` returns `{"id":6,"name":"<b>Sticker</b>",…}`, and that's fine: in <Term id="json">JSON</Term>, that's just text, and the browser doesn't draw it as a page, because it arrives with `Content-Type: application/json` and `nosniff`.

But some page will show that JSON: the shop's website or a partner's dashboard. If it puts the name in with `innerHTML`, there's the XSS. **The API stores and returns the data as is; whoever shows it escapes it.** React, a widely used tool for making pages, does it with `{name}`; `dangerouslySetInnerHTML` doesn't.

What about escaping it when saving? The API doesn't know where it will end up: in a mobile app, a name saved as `&lt;b&gt;` would show up with those letters.

### Escaping depends on the place

`html` protects the text between tags and the value of an attribute between quotes. In a link, `href="${website}"`, an address that starts with `javascript:` has nothing to escape, and the browser runs what follows when you click: you have to check that it starts with `https://`. Inside a `<script>`, the rules are JavaScript's, and the safest thing is not to put data there. That's why OWASP's guide gives a rule for each place.

### Content Security Policy: the second wall

Escaping is the fix. But one forgotten place, an `innerHTML` in a corner, is enough for something to slip in. That's what the **<Term id="content-security-policy">Content Security Policy</Term>** (CSP) is for, the header from [Phase 2's headers lesson](/en/phase-2/http-headers/#security-headers): it tells the browser where the page can load each thing from. The one for `/shop`, at the end of `src/shop.ts`:

<ProjectCode file="shop-api/29-injection-xss/src/shop.ts" region="csp" />

Each directive, in words:

| Directive | What it tells the browser |
|---|---|
| `default-src 'self'` | Everything (images, styles, scripts, requests), only from this same site, unless another directive says otherwise |
| `script-src 'self'` | Scripts, only from this site's files. No code written inside the page: neither `<script>…</script>` nor attributes like `onerror` |
| `object-src 'none'` | No plugins (`<object>`, `<embed>`) |
| `base-uri 'none'` | Nobody changes, with `<base>`, where relative links point |
| `frame-ancestors 'none'` | No site puts this page inside its own, in an `<iframe>`. It replaces `X-Frame-Options` in current browsers |
| `form-action 'self'` | Forms are only sent here |

If something slips in unescaped, the browser doesn't run its script, and it reports it in the DevTools console. **The CSP doesn't fix the page:** the tag is still inside, and it can still change what you see. It only stops it from running. That's why you always escape, and the CSP goes behind.

### The security headers, on every response

In `src/app.ts`, one line adds the rest of the security headers to every response:

<ProjectCode file="shop-api/29-injection-xss/src/app.ts" region="security-headers" />

`secureHeaders()` sets, among others, the ones from Phase 2: `nosniff`, `Referrer-Policy` and `Strict-Transport-Security`. And `X-XSS-Protection: 0`, which turns off an old browser filter that caused flaws of its own.

Why the CSP only on `/shop`? Because `/docs`, Scalar's documentation, loads its code from `cdn.jsdelivr.net` and starts it with a script written inside the page: with `/shop`'s policy, it would stop working. To the JSON routes, which nobody browses, a CSP adds little. **Each page, with its own policy.**

## You have already seen it

- **A comment with symbols.** If you've written `<3` or `<b>` in a comment on a website and it came out as is, that website escapes what you post.
- **The console warning.** Some big websites write a huge warning in the DevTools console: don't paste anything there that someone asks you to. It's XSS done by hand: convincing you to run the code yourself.
- **React.** `{product.name}` comes out escaped; `dangerouslySetInnerHTML` carries the danger in its name.

## Common mistakes

- **Pasting values into the SQL**, also in an `ORDER BY` or in a column's name. What doesn't fit in a parameter comes from a fixed list.
- **Trusting validation** to stop an injection. `x' OR '1'='1` and `<b>` are valid text.
- **Escaping when saving** instead of when showing. Each place needs its own way of escaping, and in the end it gets escaped twice: `&amp;lt;`.
- **Skipping the escaping with outside data:** `sql.raw()`, `raw()` from `hono/html`, `innerHTML` or `dangerouslySetInnerHTML`.
- **Taking the CSP for the fix.** It's the second wall, and adding `'unsafe-inline'` to `script-src` to make something work knocks it down.
- **Thinking a JSON API has no XSS:** the page that draws its data unescaped will have it.

## Summary

- SQL injection and XSS are the same flaw: a piece of data pasted inside some code changes what the code does.
- In SQL, always parameters: with an ORM too, never with `sql.raw()`, and a fixed list for what doesn't fit in a parameter.
- In HTML, each piece of data is escaped when it's shown, with a tool like Hono's `html`, and according to the place: text, attribute, URL or script.
- A JSON API stores and returns the data as is; whoever shows it escapes it.
- The Content Security Policy is the second wall: it doesn't fix the page, but the browser doesn't run whatever slips in.
