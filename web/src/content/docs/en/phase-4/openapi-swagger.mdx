## The problem

The delivery company that is going to use the shop's API writes to Ana: “What fields does an order have? What do you answer if it doesn't exist? Is the price in euros?” Ana answers by email. A week later, whoever is building the mobile app asks the same thing.

Imagine that, to avoid repeating herself, Ana writes a README (the text file that explains a project) with every route, back in the days of version 1, with `price` in euros. In lesson 4, “Versioning,” version 2 switched to `priceCents`, and nobody touched the README. Now it lies, and nobody notices: **nothing checks that a text written by hand says the same as the code.**

Besides, a README is only read by people: no program can use it to check that the API does what it promises. You need a description that both people and programs read, and that comes from the code itself.

## The analogy

<Analogy>

Think of the blueprints of a building. They use symbols that any architect, electrician or plumber understands, and with them the plumber knows where the pipes go without calling the architect.

An OpenAPI document is the blueprint of an API: in a format everyone knows, it says which routes there are, what data goes in and what comes out. Like a blueprint, it can be drawn before building or taken from what is already built.

<div slot="limits">

- A blueprint drawn by hand may not match the building. The one in this lesson is generated from the code: what it says about the requests is always true; about the responses, not entirely.
- You can't turn on a tap with a blueprint. With the documentation page you can: it sends real requests to the API.

</div>

</Analogy>

## How it really works

### A document that describes every route

This is what the shop's API will say, by the end of the lesson, about `GET /v2/products/{id}`. `jq`, from [lesson 8 of Phase 3](/en/phase-3/node-errors-and-logging/), pulls that part out of the document:

```sh
curl -s localhost:3000/v2/openapi.json | jq '.paths["/products/{id}"].get'
```

```json
{
  "tags": [
    "Products"
  ],
  "summary": "A product",
  "parameters": [
    {
      "schema": {
        "type": "integer",
        "example": 2
      },
      "required": true,
      "name": "id",
      "in": "path"
    }
  ],
  "responses": {
    "200": {
      "description": "The product",
      "content": {
        "application/json": {
          "schema": {
            "$ref": "#/components/schemas/Product"
          }
        }
      }
    },
    "404": {
      "description": "No such product",
      "content": {
        "application/problem+json": {
          "schema": {
            "$ref": "#/components/schemas/Problem"
          }
        }
      }
    },
    "422": {
      "description": "The data is not valid: \"errors\" says what is wrong",
      "content": {
        "application/problem+json": {
          "schema": {
            "$ref": "#/components/schemas/Problem"
          }
        }
      }
    }
  }
}
```

Without reading the code, you know what the delivery company was asking:

- **`parameters`:** the route takes an `id` (`"in": "path"`), a whole number and required.
- **`responses`:** every <Term id="status-code">status code</Term> that can come out: a `200` with a `Product`, or a `404` and a `422` with a `Problem`, the error format from lesson 2.
- **`$ref`:** “the shape is somewhere else in the document.” `Product` is described once, in `components`, and every route uses it.

This document follows **<Term id="openapi">OpenAPI</Term>**, a standard format for describing <Term id="http">HTTP</Term> APIs. It's written in <Term id="json">JSON</Term> or in YAML (another text format, with indentation instead of braces). The version the project uses is 3.1, from 2021; 3.2 came out in September 2025.

That document is the API's **<Term id="api-contract">contract</Term>**: what it promises to whoever uses it.

### OpenAPI and Swagger: one format, two names

You'll see “Swagger” everywhere, sometimes as if it were the same as OpenAPI. It was:

1. **2010:** Tony Tam, at the online dictionary Wordnik, creates Swagger: a format for describing its API and tools that read it.
2. **2015:** SmartBear buys Swagger and donates the format to the new OpenAPI Initiative, part of the Linux Foundation.
3. **2016:** the format is renamed the OpenAPI Specification. Swagger 2.0 was the last version with the old name.

Since then, **OpenAPI is the format and Swagger is a brand of tools** from SmartBear: Swagger UI (a page that shows the document), Swagger Editor and Swagger Codegen.

| If you read… | It means… |
|---|---|
| A `swagger.json` with `"swagger": "2.0"` | A document in the old version of the format |
| An `openapi.json` with `"openapi": "3.1.0"` | A document in today's format (3.0, 3.1 or 3.2) |
| “We have Swagger at `/swagger`” | A Swagger UI page, which reads an OpenAPI document |

### Code-first: the contract comes from the schemas

The document can be written by hand or generated from the code. The shop generates it, and that's called ***code-first***: it comes from the same Zod <Term id="schema">schemas</Term> that have been validating since [lesson 7 of Phase 3](/en/phase-3/zod-validation/), thanks to `@hono/zod-openapi`. This is how `src/schemas.ts` starts:

- **`import { z } from '@hono/zod-openapi'`**, at the top of the file: Zod's usual `z`, with one more method, `.openapi()`.
- **`.openapi({ example: 2 })`** adds something that is only for the document: a sample value.
- **`.openapi('NewOrder')`** gives the schema a name, the one that shows up in `components` and in the `$ref`s.

`z.enum([…])` means “one of these texts.” Look at the comment: these schemas don't check anything while the program runs.

### Every route, with what it receives and what it answers

Each route is described in a new file, `src/contract.ts`. This is the one for getting a product:

<ProjectCode file="shop-api/14-openapi/src/contract.ts" region="get-product" />

- **`createRoute`** describes a route without the code that handles it: what it receives (`request`) and what it answers (`responses`).
- **`path: '/products/{id}'`** writes the parameter with braces, the OpenAPI way, not with `:id`.
- **`tags`** groups the routes on the documentation page; **`summary`** is the route's name there.
- **`request: { params: idSchema }`:** the `id` is validated with `idSchema`, the one from Phase 3.

`asJson` and `withProblem` are two helper <Term id="function">functions</Term>, from the top of the file:

<ProjectCode file="shop-api/14-openapi/src/contract.ts" region="pieces" />

`withProblem` says the error goes as `application/problem+json`. `jsonBody` describes a required JSON <Term id="request-body">body</Term>. This is how the route that creates a product uses it:

<ProjectCode file="shop-api/14-openapi/src/contract.ts" region="create-product" />

- **`security`** announces in the document that the route asks for a token. `adminOnly` checks it, and **`middleware`** puts it in front, before the body is validated.
- **`headers: withLocation`:** the `201` carries the `Location` header, and the contract says so.

### OpenAPIHono validates every route and writes it down

In `src/v2.ts`, version 2 stops being a `Hono` and becomes an `OpenAPIHono`:

<ProjectCode file="shop-api/14-openapi/src/v2.ts" region="create-v2" />

- **`OpenAPIHono`** is a `Hono` that also writes every route down in the document.
- **`defaultHook`** is what answers if the request doesn't match the schema. `ifInvalid` is the function that used to live inside `validate`, now with a name, in `src/middleware/validate.ts`. Without it, `OpenAPIHono` would answer a `400` with the whole Zod error; with it, the usual `422`.
- **`registerComponent(…)`** says how the token is sent, `Authorization: Bearer <token>` ([lesson 4 of Phase 2](/en/phase-2/http-headers/)): it's the `Bearer` in the `security` from before.

And every route goes from `v2.get(…)` to `v2.openapi(…)`:

<ProjectCode file="shop-api/14-openapi/src/v2.ts" region="get-product" />

`v2.openapi(contract.getProduct, …)` registers the route, validates the request with the contract and writes it down in the document. The function is the same as before, except that `c.json(product, 200)` carries the status code. That's needed for what comes next.

### TypeScript checks that the code keeps the contract

`@hono/zod-openapi` gives TypeScript the contract of every route. If the function returns a status code that isn't in `responses`, `npm run check` fails. You'll cause it in “Try it,” by removing the `404` from `getProduct`'s contract. The last line of the error:

```
Type '404' is not assignable to type '422'.
```

TypeScript looks in the contract for a status code that matches the `404` from `httpProblem`, and there isn't one. A `c.json(product)` without a status code fails too, and a product without `priceCents` doesn't compile. **What the contract promises, the code can't forget.**

### What the contract doesn't check

There are two holes:

- **Zod doesn't validate the responses,** only what comes in. What goes out is only reviewed by TypeScript, before running.
- **TypeScript doesn't mind an extra field.** A product with an extra field, like what it cost the shop, compiles, and reaches the <Term id="client">client</Term> without the contract saying so.

They're closed by tests that look at the real responses, like the project's, which compare the whole product.

### The document and its page: /v2/openapi.json and /docs

The document is published on one more route, in `src/app.ts`:

<ProjectCode file="shop-api/14-openapi/src/app.ts" region="json-contract" />

- **`getOpenAPI31Document`** writes the document with v2's routes every time someone asks for it: it's always the one from the running code.
- **`info`** is the API's ID card, and **`servers`** says that its routes, like `/products`, hang from `/v2`.

For people, below it, a page:

<ProjectCode file="shop-api/14-openapi/src/app.ts" region="docs-page" />

`Scalar` answers at `/docs` with an HTML page that, in the browser, downloads `/v2/openapi.json` and shows it, with a button to try every route. The classic alternative is Swagger UI.

The browser downloads the page's code from jsDelivr, a <Term id="cdn">CDN</Term>. That's why `cdn` carries the exact version, like the npm packages: without it, every visit would load the latest one, code nobody has reviewed. Besides, jsDelivr serves an exact version with `Cache-Control: immutable`, the [cache](/en/phase-2/http-caching/) that never asks.

### Code-first or contract-first

The other way is ***contract-first***: the document is written, agreed with whoever is going to use the API, and then the code is written.

| | Code-first | Contract-first |
|---|---|---|
| What's written first | The code; the contract comes from it | The contract; the code keeps it |
| For | A single source: what comes in can't drift | Clients start earlier, and the design is discussed without code |
| Against | The design is decided while coding | Contract and code can drift apart if nothing compares them |
| Fits when | The API already exists and a single team builds it | Several teams start at the same time |

The shop already had its API: code-first fits.

### What a contract lets you generate

Since programs read it, the contract is good for more than a page:

- **Clients:** `openapi-typescript` takes its TypeScript types from it, and OpenAPI Generator writes clients in dozens of languages.
- **Fake servers** (*mocks*): Prism answers what the contract says before the API exists.
- **Contract tests:** Schemathesis sends hundreds of generated requests and warns you if a response doesn't match its schema. It closes the first of the two holes from before.

## You have already seen it

- **Big APIs publish their contract.** GitHub, in [github/rest-api-description](https://github.com/github/rest-api-description), and Stripe, in [stripe/openapi](https://github.com/stripe/openapi).
- **A `/swagger` or `/api-docs` address** with a page full of colored routes: Swagger UI reading an OpenAPI document.
- **Postman, Insomnia and Bruno**, programs for trying out APIs, import an OpenAPI document and create all its requests at once.

## Common mistakes

- **Writing the documentation apart from the code.** It goes out of date without anyone noticing, like the README at the start.
- **Forgetting `required: true` on the body.** Without it, a request without a body isn't validated: removing it from the shop, a `PATCH /v2/orders/25` without a body answers `{"id":25,"productId":2,"status":"pending"}`. The order has lost its `quantity`.
- **A parameter with `z.coerce` without its `.openapi()`.** `z.coerce` accepts anything, and the document doesn't know what type it is. Without `.openapi({ type: 'integer', param: { required: true } })`, the `id` comes out as `"type": ["integer", "null"]` and `"required": false`.
- **Mixing up the versions.** A `swagger.json` with `"swagger": "2.0"` is in the old format: check which version a tool accepts before handing it over.

## Summary

- OpenAPI is a standard format for describing an API: routes, parameters, bodies and responses, the error ones too. Swagger was its name until 2016, and today it's a brand of tools.
- The document is the API's contract: people read it, on pages like `/docs`, and so do programs, which generate clients, fake servers and tests.
- Code-first generates the contract from the code; contract-first writes it first. The shop generates it from the schemas that validate, so it doesn't go out of date.
- `npm run check` fails if a route answers a status code or a shape that its contract doesn't have. What goes out isn't checked while running, and neither is an extra field: that's what tests are for.
