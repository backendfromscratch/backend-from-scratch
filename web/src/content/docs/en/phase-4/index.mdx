In Phase 3 you wrote an <Term id="api">API</Term> that works. It had a single <Term id="client">client</Term>, the shop's website, and if something wasn't clear, the person using it could ask you. In this phase, other people use it: people you don't know, who can't ask you and who can't break every time you change something.

You don't switch projects. You keep working on the same shop API, and each lesson adds something it needs once it leaves home.

## What changes when other people use your API

Ana and Luis's shop is doing well, and two new clients come along. Imagine:

- **A phone app,** made by an outside studio. It shows the products, creates orders and lets you know when one is on its way.
- **A delivery company,** which every morning asks for the orders ready to be picked up and wants to hear about new ones without asking all the time.

Neither of them has seen your code. They only see your responses. That changes many things that didn't matter until now:

| When only your website used it | When other people use it |
|---|---|
| If you rename a field, you change the website that same day | The app people have installed doesn't update itself: a renamed field breaks it for months |
| If something fails, you look at your <Term id="log">logs</Term> | The delivery company only sees your response, and has to understand the error from it |
| You know by heart what each address returns | Nobody can ask you: what isn't written down doesn't exist for them |
| Three products and a few orders fit in one response | Thousands of orders don't fit: they have to come in parts |
| If you want to know whether there's a new order, you look | The delivery company wants you to tell it, not to ask you every minute |

**Each row is a lesson in this phase.** Your API will learn a few new things, but what matters is something else: that other people can use it without you.

## What makes an API good

A good API can be used without asking the people who made it. For that it needs three things:

- **Predictable.** If `GET /orders/7` returns an order, someone who doesn't know you guesses that `GET /products/2` returns a product, and that an error will have the same shape in both. The addresses, the <Term id="http-method">methods</Term> and the <Term id="status-code">status codes</Term> follow rules that many people already know. That's what the REST, errors and pagination lessons are about.
- **Documented.** What each address accepts and returns is written down, and not in a separate document nobody updates, but in a contract that comes from the same code that checks the data. That's the OpenAPI lesson.
- **Stable.** It changes without breaking anyone: new things are added, and what can't be added goes in a new version, with a farewell date for the old one. That's the versioning lesson.

All three will sound familiar from any app: a good interface is understood without a manual and doesn't move the buttons around every week. Here, the interface is your URLs, your codes and your <Term id="json">JSON</Term>, and whoever uses it is another program.

## What you will build

An example of what changes. If you ask the Phase 3 API for an order of zero mugs, it answers in a format you made up:

```text
HTTP/1.1 422 Unprocessable Entity
content-type: application/json
…

{"error":"The data is not valid","details":[{"field":"quantity","problem":"At least 1"}]}
```

By the end of this phase, it answers like this (we captured it with the final version of the project and Node 26, and trimmed some headers with `…`):

```text
HTTP/1.1 422 Unprocessable Entity
content-type: application/problem+json
…

{"type":"https://shop.example/problems/invalid-data","title":"The data is not valid","status":422,"detail":"See \"errors\" for what is wrong with each field.","errors":[{"field":"quantity","problem":"At least 1"}]}
```

It says the same thing, but in a format that isn't yours: a standard's, Problem Details, written in an <Term id="rfc">RFC</Term>. The delivery company already knows it from other APIs, and its program can read it without you explaining anything. Look at the `content-type` <Term id="header">header</Term> too: it announces that format before anyone reads the body.

The list of orders, on the other hand, no longer comes whole. It comes in pages, and each one says where the next one is:

```text
HTTP/1.1 200 OK
content-type: application/json
link: <http://localhost:3000/v2/orders?limit=2&cursor=MjQ>; rel="next"
…

[{"id":25,"productId":2,"quantity":2,"status":"pending","createdAt":"2026-10-08T09:00:00.000Z"},{"id":24,"productId":1,"quantity":1,"status":"pending","createdAt":"2026-10-08T02:00:00.000Z"}]
```

Lesson by lesson, the API gains this:

| Lesson | What the shop's API gains |
|---|---|
| 1. REST | Changing an order (`PATCH`), cancelling it and removing a product (`DELETE`), each with its own method and its own code |
| 2. Errors | Every error with the same shape, the one from the Problem Details standard |
| 3. Pagination | Orders in pages, filtered by status, and products sorted by price |
| 4. Versioning | `/v1/` and `/v2/` at the same time: the price moves to cents without breaking whoever read it in euros |
| 5. OpenAPI | A contract, `openapi.json`, and a documentation page at `/docs` |
| 6. Serialization | Each order's date, written properly, and the same order in JSON and in a binary format, Protobuf |
| 7. Webhooks | An address where the payment gateway reports each payment, with a signature, and orders that aren't duplicated if someone repeats the request |
| 8. Real time | An order's status, live, without asking every minute |
| 9. Alternatives | Nothing new in the project: you compare REST with GraphQL and gRPC |

The data is still kept in the program's memory. Storing it in a database is Phase 5.

## What you will learn

By the end of this phase you'll know how to design an API that other people use without asking you. You'll know:

- How to name an API's addresses around its resources, so they can be guessed, and what REST really means.
- How to answer errors always the same way, with a standard format.
- How to hand out a long list in pages without skipping or repeating anything, even if new data arrives in the meantime.
- How to change an API without breaking its clients, and what counts as breaking.
- How to document it with OpenAPI, as a contract that both people and programs read.
- The traps of JSON: dates, money, very large numbers and `null`.
- How to let others know when something happens, with webhooks, and how to send data live with Server-Sent Events and WebSockets.
- When GraphQL or gRPC is worth it, and why REST is still the norm for a public API.

## Try it: read an API that isn't yours

The goal: **without opening GitHub's documentation, find the open issues of the Node.js repository in its API.** An *issue* is a report someone opens on a repository: a bug, a proposal or a question. If the API is well designed, you should be able to guess the addresses.

GitHub's API lives at `https://api.github.com`, and without an account it allows 60 requests per hour from each IP address. This exercise uses five.

### 1. A user

Start with `octocat`, the account of GitHub's mascot, which exists for examples:

<TryIt
  title="The octocat user"
  cmd={`curl -s https://api.github.com/users/octocat | grep -E '"(login|url|repos_url|name|public_repos)"'`}
  output={`  "login": "octocat",
  "url": "https://api.github.com/users/octocat",
  "repos_url": "https://api.github.com/users/octocat/repos",
  "name": "The Octocat",
  "public_repos": 8,`}
>

The response has more than thirty lines of JSON. `grep -E` keeps the five we care about: the ones with one of those names in quotes ([lesson 2 of Phase 1](/en/phase-1/linux-file-commands/)). If nothing comes out, remove the `| grep …` and look at the whole response.

Look at the address: `/users` is all the accounts, and `/users/octocat`, one of them. First the collection, then which one. And the response gives you the next address without you looking for it: `repos_url`, that account's repositories.

</TryIt>

### 2. A repository

On the website, Node.js is at `github.com/nodejs/node`: the account `nodejs` and the repository `node`.

<SelfCheck question="Challenge: from what you’ve seen, which API address do you think gives you the Node.js repository? Try it with curl before you look.">

Accounts are under `/users/…`; repositories, under `/repos/…`, with the account and the name, as on the website:

```sh
curl -s https://api.github.com/repos/nodejs/node | grep -E '^  "(full_name|url|issues_url|open_issues_count)"'
```

```text
  "full_name": "nodejs/node",
  "url": "https://api.github.com/repos/nodejs/node",
  "issues_url": "https://api.github.com/repos/nodejs/node/issues{/number}",
  "open_issues_count": 1197,
```

The `^  ` in the `grep` asks for the name to start the line with two spaces, to keep the repository's data and not its owner's, which is nested further in. `issues_url` gives you the clue: `{/number}` is an optional slot. Without it, the list of issues; with a number, just one. Your `open_issues_count` will be different: it changes every hour.

</SelfCheck>

### 3. Its issues, two at a time

With the clue from `issues_url`, the list is at `/repos/nodejs/node/issues`. There are more than a thousand, so ask for just two:

<TryIt
  title="The two latest issues"
  cmd={`curl -s "https://api.github.com/repos/nodejs/node/issues?per_page=2" | grep -E '^    "(number|title|state)"'`}
  output={`    "number": 66705,
    "title": "test: deflake test-net-autoselectfamily-local-port",
    "state": "open",
    "number": 66704,
    "title": "tools: update OpenSSL on the selected branch",
    "state": "open",`}
>

`?per_page=2` is a <Term id="query-string">query string</Term> ([lesson 1 of Phase 2](/en/phase-2/http-request-and-response/)): “two per page.” The quotes around the address are needed because of the `?`, which the shell could take for something else. Your numbers and titles will be different: you get the most recent ones.

Goal achieved, without documentation: the addresses can be guessed because they follow a rule.

</TryIt>

### 4. What the headers say

The two issues are the first page. Where's the second one? Not in the body, but in the headers:

<TryIt
  title="The list's headers"
  cmd={`curl -sI "https://api.github.com/repos/nodejs/node/issues?per_page=2" | grep -iE '^(HTTP|link|etag|x-ratelimit-(limit|remaining))'`}
  output={`HTTP/2 200 
etag: W/"497c2c4cfa9a2028b33819cd12088d3c4d9b7be36b32686dc1ee8eed07535c10"
link: <https://api.github.com/repositories/27193779/issues?per_page=2&after=Y3Vyc29yOnYyOpLPAAABoTU4rEjPAAAAAVuCfJw%3D&page=2>; rel="next"
x-ratelimit-limit: 60
x-ratelimit-remaining: 50`}
>

`curl -sI` sends a `HEAD`, which asks for the headers only ([lesson 2 of Phase 2](/en/phase-2/http-methods/)), and `grep -iE` keeps four of them, ignoring upper and lower case. Line by line:

- **`link`** is the address of the next page, with `rel="next"`. Look at `after=…`: it's a bookmark that says “carry on after this one,” and you'll see it in the pagination lesson. The `27193779` is the Node repository's number: another way of naming it.
- **`etag`** is this response's fingerprint, the one from the [Phase 2 caching lesson](/en/phase-2/http-caching/): with it, the client asks whether something has changed without downloading it again.
- **`x-ratelimit-limit`** and **`x-ratelimit-remaining`** are your limit per hour and what you have left. Each request in this exercise has taken one away; your number will be different. If you reach zero, GitHub answers with an error until the hour is up. Setting limits like this is Phase 6.

</TryIt>

A browser didn't need any of these headers. They're there for the program that uses the API: how to carry on, when to ask again and how much it has left. **An API designed for others also answers what its client is going to ask next.**

### 5. An address that doesn't exist

What if you guess wrong? Try asking for the repositories in Spanish:

<TryIt
  title="A made-up address"
  cmd={`curl -s -w '\\n' https://api.github.com/users/octocat/repositorios`}
  output={`{
  "message": "Not Found",
  "documentation_url": "https://docs.github.com/rest",
  "status": "404"
}`}
>

A `404`, with the same shape as the `401` you saw in the [Phase 2 headers lesson](/en/phase-2/http-headers/): `message`, `documentation_url` and `status`. GitHub answers all its errors the same way, and the program that uses it reads them all with the same code. That's what your API will do from lesson 2 on. `-w '\n'` adds a line break at the end, so the prompt doesn't come out stuck to the response.

</TryIt>

In this phase, your API will learn to do all of this: addresses that can be guessed, lists with their next page and errors that look alike.
