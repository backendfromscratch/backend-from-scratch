## The problem

Luis wants to try the shop's API on his laptop. All he has is Docker: no Node 26, no dependencies. In [lesson 1](/en/phase-7/docker-image-vs-container/) you started nginx with one command because someone had made its <Term id="image">image</Term>. There's no image of your API: you have to make it yourself.

For that you write a <Term id="dockerfile">Dockerfile</Term>: a text file with the steps you did by hand in Phase 3, one per line. `docker build` reads it and produces the image. From then on, Luis, a server or you yourself a year from now all start exactly the same API.

## The analogy

<Analogy>

Imagine Ana leaves a recipe for a cook who has never seen her kitchen. It has to be exact: “start from this kitchen, already equipped; work on this counter; take these ingredients from the basket; cook them like this; when the restaurant opens, serve this dish.”

The cook only uses what's in the basket. That's why Ana chooses what goes into it, and her wallet, with her house keys, stays out.

<div slot="limits">

- The cook cooks every time someone orders. Docker runs the recipe once, when it builds the image; each container starts the dish already made.
- “This kitchen” may change if the owner remodels it. In a Dockerfile, the starting image can be pinned by its fingerprint, and then it never changes.
- The cook remembers what they did last time: that's the cache from lesson 2.

</div>

## How it really works

### The shop's Dockerfile

This is the whole file, `Dockerfile`, with no extension, in the project folder:

<ProjectCode file="shop-api/32-dockerfile/Dockerfile" />

The lines with `#` are comments. Each instruction starts with a word in capitals, and Docker runs them from top to bottom. It's the same recipe as in the lab of [lesson 2](/en/phase-7/docker-layers/). Now, piece by piece.

### FROM: the starting image, pinned by its fingerprint

**`FROM`** says which image you start from: everything else is built on top of its layers. `node:26-slim` is Node 26 on a minimal Debian, the one you looked at with `docker history`. [Lesson 4](/en/phase-7/docker-multi-stage-build/) compares it with smaller ones.

After it comes `@sha256:193f…`, its fingerprint (*digest*). The `26-slim` tag moves to another image with each new version of Node or Debian; the fingerprint always names exactly the same one. It's the idea behind the `save-exact` in your [`.npmrc`](/en/phase-3/what-is-node-js/#the-npmrc-three-lines-against-the-2025-attacks): **the version changes when you decide**, not when someone publishes. Lesson 8 tells you how to update it.

### WORKDIR: the working folder

**`WORKDIR /app`** creates the folder `/app` inside the image and goes into it, like a `mkdir` and a `cd`. The following instructions work there, and the container will start in it.

### COPY and RUN: the dependencies first

**`COPY source destination`** copies files from your folder into the image. Here it copies three to `./`, that is, to `/app`:

- **`package.json` and `package-lock.json`**: what `npm ci` needs. They go on their own, before the code, because of the cache: changing `src/` won't repeat the install (lesson 2).
- **`.npmrc`**: the project's rules for npm. Without it, `npm ci` inside the image would run each package's install scripts, exactly what your `.npmrc` turns off with `ignore-scripts`, and as `root`, the user `RUN` runs as.

**`RUN npm ci`** runs a command **when the image is built**, not when it starts. `npm ci` installs exactly what the *lockfile* says, inside a Linux: the dependencies are Linux ones, even if you build on a Mac. It's the biggest layer: 161 MB.

### COPY . . and the .dockerignore: what goes into the image

**`COPY . .`** copies the rest of the project to `/app`. The first dot is the folder you gave `docker build`, the **context**: Docker packs it up and sends it to the engine. What isn't in the context, `COPY` can't find.

A **`.dockerignore`** file, next to the Dockerfile, says what stays out, like `.gitignore` for Git:

<ProjectCode file="shop-api/32-dockerfile/.dockerignore" />

Line by line:

- **`node_modules`**: your dependencies, maybe installed for macOS. The image has its own, from `npm ci`; copying yours on top would overwrite them.
- **`.env`**: your <Term id="secret">secrets</Term>. An image gets shared, and whoever has it can read all its files. It's the rule from [Phase 1](/en/phase-1/environment-variables/#keeping-secrets-out-of-the-code) and from [lesson 8 of Phase 6](/en/phase-6/rate-limiting-secrets/): a secret that travels in an image is as leaked as one that made it into Git.
- **`.git`, `*.log`, `Dockerfile` and `.dockerignore`**: the Git history, the logs and Docker's own files. The API doesn't use them.

The tests, `test/`, do go in: in lesson 4, the type check done during the build checks them too.

### ENV HOST=0.0.0.0: listening on every address

**`ENV`** leaves an <Term id="environment-variable">environment variable</Term> in the image's record: all its containers start with it. From this step on, `src/config.ts` reads `HOST`, the address the server listens on, and `src/server.ts` uses it:

<ProjectCode file="shop-api/32-dockerfile/src/server.ts" region="server" />

Without `HOST`, the server listens on `127.0.0.1`, as it has since [Phase 3](/en/phase-3/node-http-server/): only your computer reaches it. Inside a container, **`127.0.0.1` is the container itself**. What arrives through the published port comes in through the container's network, not through its `127.0.0.1`, so nobody would reach it. `0.0.0.0` means “all my addresses.”

Does that break the rule from Phase 3? No: who reaches the container is decided by the published port. With `-p 127.0.0.1:3000:3000`, only your computer. [Lesson 6](/en/phase-7/docker-networking/) goes into it in depth.

`ENV` is for default values, never for secrets: `docker history` shows every `ENV` to whoever has the image.

### EXPOSE: it only documents

**`EXPOSE 3000`** notes in the record that the program listens on 3000. It doesn't open or publish anything: `docker run -p` does that. It's there for whoever reads the Dockerfile, and for some tools.

### CMD in exec form: node is PID 1

**`CMD`** says which program each container starts. It goes in **exec form**, a list in square brackets: `["node", "src/server.ts"]`. Docker starts `node` directly, and `node` is <Term id="pid">PID</Term> 1.

There's another form, the **shell form**: `CMD node src/server.ts`, without brackets. Docker turns it into `sh -c "node src/server.ts"`. Then PID 1 is `sh`, and `node` is its child. `docker stop` sends `SIGTERM` to PID 1, `sh` doesn't pass it on to `node`, and ten seconds later `SIGKILL` arrives. You'll check it in the challenge in “Try it.”

The Node image first starts a script of its own, `docker-entrypoint.sh`, which replaces itself with your `CMD` without leaving a trace: `node` is still number 1.

### Shutting down properly: PID 1 and signals

As you saw in [lesson 1](/en/phase-7/docker-image-vs-container/#docker-stop-first-a-signal-then-sigkill), Linux doesn't end PID 1 with a <Term id="signal">signal</Term> it hasn't prepared for. That's why `server.ts` prepares for two:

<ProjectCode file="shop-api/32-dockerfile/src/server.ts" region="shut-down" />

- **`for (const signal of ['SIGTERM', 'SIGINT'])`**: the same for `SIGTERM`, the one from `docker stop`, and `SIGINT`, the one from <kbd>Ctrl</kbd> + <kbd>C</kbd> ([Phase 1](/en/phase-1/linux-processes-and-signals/)).
- **`process.once(signal, …)`**: the function runs the first time that signal arrives.
- **`server.close(…)`**: stops accepting connections and waits for the requests halfway through to finish. Then `pool.end()` closes the connections to PostgreSQL and `process.exit(0)` ends with code 0, “all good.”
- **`setTimeout(…, 5000).unref()`**: if a connection never ends, like an open <Term id="websocket">WebSocket</Term>, it exits anyway after 5 seconds. `unref()` stops that timer, on its own, from keeping the program alive.

Without this, `docker stop` takes ten seconds and cuts off whatever was halfway done. With it, less than two tenths of a second.

### The database is outside the container

Your `.env` says `DATABASE_URL=postgres://shop:shop@localhost:5432/shop`. Inside the container, `localhost` is the container, and there's no PostgreSQL there: the API would answer `500` and its log would say `connect ECONNREFUSED 127.0.0.1:5432`.

How to reach the PostgreSQL on your computer depends on your Docker:

- **Docker Desktop** gives containers a name for the computer they run on: **`host.docker.internal`**. All you need is to change `localhost` to that name.
- **On Linux, with Docker Engine,** that name doesn't exist, and even if you added it, your PostgreSQL only accepts connections from `localhost`. Opening it to Docker's network means touching its configuration. **`--network host`** is easier: the container has no network of its own, it uses your Linux's, and its `localhost` is yours. Since the server ends up on your network, `HOST` goes back to `127.0.0.1`.

In lessons [5](/en/phase-7/docker-volumes/) and [6](/en/phase-7/docker-networking/), PostgreSQL moves into a container and the API finds it by its name, the same on every system.

## You have already seen it

- **`npm ci` and `npm start`.** They're the steps from Phase 3: `RUN npm ci` is your install, and `CMD` is what your `npm start` does, without npm in between.
- **`.gitignore`.** `.dockerignore` is its partner: both leave out `node_modules` and `.env`.
- **The `pid` in your logs.** pino has written it on every line since [Phase 3](/en/phase-3/node-errors-and-logging/). On your computer it's a big number; in the container, 1.

## Common mistakes

- **The server listens on `127.0.0.1` inside.** The log says it's listening, but `curl` answers `curl: (52) Empty reply from server`, or a similar connection error. `ENV HOST=0.0.0.0` is missing.
- **`localhost` in `DATABASE_URL`.** The API answers `500`, and `docker logs` says `connect ECONNREFUSED 127.0.0.1:5432`: it's looking for PostgreSQL inside the container. On Windows, if it doesn't get through with `host.docker.internal` either, carry on with `curl -s 127.0.0.1:3000/`, which doesn't use the database; lesson 6 solves it.
- **Secrets in the image.** A `.env` without `.dockerignore`, or an `ENV KEY=…`, travels with the image to whoever receives it.
- **`CMD` in shell form.** `docker stop` takes ten seconds and ends with `137`.
- **Changing the code and not rebuilding.** The container runs the image, not your folder: after `docker build`, delete the container and start another one.
- **`port is already allocated`.** Another program, maybe your `npm start`, is using 3000: stop it.

## Summary

- A Dockerfile is the recipe of an image: `FROM` the base, `WORKDIR` the folder, `COPY` your files, `RUN` commands at build time, `ENV` and `EXPOSE` data for the record, and `CMD` the container's program.
- The base is pinned by its fingerprint, and `.npmrc` goes with `package.json` so that `npm ci` follows its rules inside.
- `.dockerignore` leaves out `node_modules` and `.env`: the secrets arrive at startup, with `--env-file` or `-e`.
- Inside a container, the server listens on `0.0.0.0` and `localhost` is the container; `-p 127.0.0.1:` decides who gets in.
- `CMD` in exec form makes `node` PID 1, and handling `SIGTERM` lets it stop in tenths of a second, not in ten seconds.

`ECONNREFUSED 127.0.0.1` says that nobody is listening at that address. The API hasn't even reached your PostgreSQL.

</QuizOption>

<QuizOption text="--env-file doesn’t read DATABASE_URL: URLs have to go with -e.">

`--env-file` creates one variable per line, whatever its value. The variable arrived: it points somewhere else.

</QuizOption>

<QuizOption text="localhost, inside the container, is the container itself." correct>

The `DATABASE_URL` in your `.env` says `localhost`, and there's no PostgreSQL there. With Docker Desktop, change it with `-e` to `host.docker.internal`.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Next month a new version of node:26-slim comes out. Your Dockerfile says FROM node:26-slim@sha256:193fe51b…. What happens when you rebuild?"
  review="FROM: the starting image, pinned by its fingerprint"
>

<QuizOption text="It uses the same image as always, until you change the line." correct>

The fingerprint names a specific content. The `26-slim` tag moves to the new image, but your `FROM` doesn't follow it: you update when you decide.

</QuizOption>

<QuizOption text="It uses the new one: the fingerprint only checks that the download arrived complete.">

With `@sha256:…`, Docker asks for exactly that image, not whichever one the tag points to today. The tag stays as a note for whoever reads it.

</QuizOption>

<QuizOption text="It fails: the fingerprint no longer matches the 26-slim tag.">

Docker uses the fingerprint and doesn't compare it with the tag. The build works the same as on the first day.

</QuizOption>

</QuizQuestion>
