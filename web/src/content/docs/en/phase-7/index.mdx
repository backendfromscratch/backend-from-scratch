At the end of Phase 6, the shop's API keeps its data in PostgreSQL, knows who you are and stops anyone who keeps trying passwords. It works on your computer. This phase's question is a different one: would it work on someone else's, or on a server, without an afternoon of installing things?

In this phase you put it in **<Term id="container">containers</Term>** with **<Term id="docker">Docker</Term>**: the API, its database and everything they need, packaged to start the same way anywhere. By the end, the whole shop starts up with one command.

## “It works on my machine”

Picture Luis, your partner in the shop, wanting to start the API on his laptop. You hand him the project and tell him “run `npm start`”. It doesn't start. To make it work, he has to repeat what you did over three phases, and it isn't the same on every system:

| What he needs | On the Mac | On Ubuntu and WSL | Where you did it |
|---|---|---|---|
| Node 26 | nvm | nvm, and first `libatomic1` with `apt`: without it, `node` won't start | [Phase 3](/en/phase-3/) |
| The dependencies | `npm ci` | `npm ci` | [Phase 3](/en/phase-3/) |
| PostgreSQL 18 | Homebrew, and a line in `~/.zshrc` for the `PATH` | PostgreSQL's repository, because Ubuntu's comes with version 16 | [Phase 5](/en/phase-5/) |
| The `shop` role and its two databases | `createuser`, without `sudo`: you are the superuser | `sudo -u postgres createuser` | [Phase 5](/en/phase-5/) |
| The configuration | `.env` with `DATABASE_URL` and the secrets, and the migrations | The same | [Phases 5](/en/phase-5/) and [6](/en/phase-6/) |

That's five things, each with its versions and its differences. One forgotten step, or a different version, is enough for the API to fail on one computer and not on another. That phrase, **“it works on my machine”**, is so common that it's a running joke among people who code.

And it isn't only Luis. In Phase 8 you'll rent a server, which starts out empty: you'd have to repeat the whole table there, without a mistake, and again every time something changes.

## What a container is

**A container is a program that runs isolated and carries everything it needs inside:** its files, its version of Node, its dependencies, even the pieces of the system. What's on your computer doesn't affect it, and it doesn't touch your computer. Docker is the program that creates containers and starts them.

Instead of handing Luis five steps, you hand him the API already packaged, with Node 26 inside. All he needs is Docker.

<Analogy>

Until the 1950s, loading a ship took days. Every sack, every crate and every barrel had its own shape, and the dockworkers placed them one by one. At every port, all over again.

Then came the shipping container: a steel box of fixed size. What goes inside doesn't matter, bananas or washing machines. The cranes, ships and trucks of the whole world know how to move that box, and nobody opens it along the way.

A Docker container is that box for a program. Inside goes the API with everything it needs; outside, any computer with Docker knows how to start it.

<div slot="limits">

- A steel box is closed and still. A Docker container is a running program: it starts, it stops and it writes on the screen.
- From a Docker container you can get many identical copies at once, from the same template. That template is the image, from lesson 1.
- The boxes on a ship share nothing. Docker containers share the system's kernel, as you'll see now, and that's why their isolation is weaker than a virtual machine's.
- “Starts anywhere” has fine print: a Linux container needs a Linux kernel, and one built for one processor doesn't always work on another.

</div>

</Analogy>

### A container is not a virtual machine

In [lesson 4 of Phase 1](/en/phase-1/linux-users-and-permissions/) you created a <Term id="virtual-machine">virtual machine</Term> with Multipass: a simulated computer, with its own whole Ubuntu. A container also gives you an isolated Linux, but inside it's something else.

Every system has a **kernel**: the part that talks to the computer's hardware and shares time among the programs, as you saw in [lesson 6 of Phase 1](/en/phase-1/systemd-services-and-apt/). A virtual machine boots its own kernel. **A container has no kernel: it uses the one of the system it runs on.** It's one more <Term id="process">process</Term>, like the ones in [lesson 5 of Phase 1](/en/phase-1/linux-processes-and-signals/), to which the kernel shows only its own files, its own network and its own processes.

| | Virtual machine (Multipass) | Container (Docker) |
|---|---|---|
| Kernel | Its very own | The one of the system it runs on, shared |
| What starts | A whole operating system | A program |
| Time to start | Tens of seconds | Less than a second |
| Size | Gigabytes | From a few megabytes |
| Isolation | Strong: another simulated computer | Weaker: processes kept apart by the same kernel |

And on a Mac or on Windows, which have no Linux kernel? **Docker Desktop starts a small virtual machine with Linux, without you seeing it**, and all your containers share its kernel. On Linux it isn't needed: containers use your own system's.

You'll check this at the end of this introduction, with Docker already installed.

## Before you start: install Docker

Docker has two pieces: the **engine** (*Docker Engine*), which creates the containers, and the `docker` command, with which you ask it to. How they're installed depends on your system.

### On the Mac and on Windows: Docker Desktop

**Docker Desktop** is an app that brings the engine inside its Linux virtual machine, the `docker` command and a window to see your containers. You install it like any other app, from Docker's website:

- **On the Mac:** [Install Docker Desktop on Mac](https://docs.docker.com/desktop/setup/install/mac-install/). Choose the installer for your processor (Apple or Intel), drag Docker to Applications and open it. The first time, it asks you to accept its terms: without that, it doesn't start.
- **On Windows:** [Install Docker Desktop on Windows](https://docs.docker.com/desktop/setup/install/windows-install/). It needs Windows 10 22H2 or Windows 11 23H2, or later, and WSL 2, which you already have. Leave the option to use WSL 2 checked. Then, in *Settings* › *Resources* › *WSL Integration*, check that your Ubuntu is turned on: that way the `docker` command works inside your WSL terminal ([Docker's guide](https://docs.docker.com/desktop/features/wsl/)).

With Docker Desktop, **don't also install Docker Engine inside WSL**: the two at once clash.

<Aside type="note" title="Docker Desktop's license">

Docker Desktop isn't free for everyone. According to [Docker's terms](https://docs.docker.com/subscription/desktop-license/), checked on October 14, 2026, it's free for personal use, for education, for non-commercial open source projects and for small businesses: fewer than 250 employees **and** less than 10 million dollars in annual revenue. A larger company, or a government agency, needs a paid subscription. The terms can change: review them before using it at work.

Docker Engine, the engine, is free for everyone. If you can't use Docker Desktop, there are alternatives: **OrbStack** and **Colima** on the Mac, and **Podman**, from Red Hat, on any system. The course doesn't use them, and some commands may be different.

</Aside>

### On Ubuntu and on WSL: Docker Engine

On Linux, Docker is installed like the PostgreSQL of [Phase 5](/en/phase-5/): with `apt`, from Docker's own repository, because Ubuntu's comes with an older version under another name. On WSL, do this only if you don't use Docker Desktop (for example, because of the license).

First, the key Docker signs its packages with. These are the commands from [Docker's guide for Ubuntu](https://docs.docker.com/engine/install/ubuntu/):

<TryIt
  title="The Docker repository's key"
  cmd={`sudo apt update\nsudo apt install -y ca-certificates curl\nsudo install -m 0755 -d /etc/apt/keyrings\nsudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc\nsudo chmod a+r /etc/apt/keyrings/docker.asc`}
>

- **The first two** update the catalog and install `curl` and the certificates to download over HTTPS, if you didn't have them.
- **`install -m 0755 -d`** creates the `/etc/apt/keyrings` folder, where `apt` keeps the keys of other repositories.
- **`curl -fsSL … -o`** downloads Docker's public key to that folder, without writing anything on the screen.
- **`chmod a+r`** lets every user read it, with the permissions from [lesson 4 of Phase 1](/en/phase-1/linux-users-and-permissions/).

</TryIt>

Then, where the repository is:

<TryIt
  title="Add Docker's repository"
  cmd={`sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "\${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update`}
  output={`Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: arm64
Signed-By: /etc/apt/keyrings/docker.asc

Get:1 https://download.docker.com/linux/ubuntu noble InRelease [48.5 kB]
Get:2 https://download.docker.com/linux/ubuntu noble/stable arm64 Packages [80.4 kB]
…
Reading package lists...`}
>

`tee` writes every line up to `EOF` to the file, and also on the screen. The two `$(…)` fill themselves in: your Ubuntu's name (`noble`, 24.04) and your processor (`arm64`; on most PCs, `amd64`). `Signed-By` says which key to check each package with.

Look at the `Get:` lines from `download.docker.com`: `apt` already reads Docker's catalog. If you see `NO_PUBKEY` or `not signed`, the key is missing: repeat the previous step. We trimmed the output (`…`).

</TryIt>

Now, Docker:

<TryIt
  title="Install Docker Engine"
  cmd="sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin"
  output={`…
Setting up containerd.io (2.4.1-2~ubuntu.24.04~noble) ...
…
Setting up docker-ce-cli (5:29.9.0-1~ubuntu.24.04~noble) ...

That's five packages:

- **`docker-ce`**, the engine: a <Term id="daemon">daemon</Term>, `dockerd`, that creates and watches over the containers.
- **`docker-ce-cli`**, the `docker` command.
- **`containerd.io`**, the piece the engine uses underneath to start each container.
- **`docker-buildx-plugin`** builds images ([lesson 3](/en/phase-7/dockerfile/)) and **`docker-compose-plugin`** adds `docker compose` (lesson 7).

The `Created symlink` lines say that the engine is set up as a systemd service, which starts on its own when the machine boots, like nginx in [lesson 6 of Phase 1](/en/phase-1/systemd-services-and-apt/). We captured the output in an Ubuntu 24.04 container, where the service can't start: we removed two lines that only show up there. Your versions may be newer.

</TryIt>

Check that it's running with `sudo systemctl status docker`, as you did with nginx: look for `Active: active (running)`. If it says `inactive`, start it with `sudo systemctl start docker`.

### Without sudo: the docker group

Now try Docker with your user, without `sudo`:

<TryIt
  title="Docker without sudo, not yet"
  cmd="docker run hello-world"
  output="permission denied while trying to connect to the docker API at unix:///var/run/docker.sock"
>

The `docker` command doesn't create containers itself: it asks the engine to. It talks to it through **`/var/run/docker.sock`**, a Unix *socket*: a file through which two programs on the same machine talk, as through a port, but without a network. Only `root` and the `docker` group can use that file, and you're not in it.

</TryIt>

The installation created the `docker` group, empty. Add yourself with `usermod`, from [lesson 4 of Phase 1](/en/phase-1/linux-users-and-permissions/), and open a shell that already has it:

<TryIt
  title="Join the docker group"
  cmd={`sudo usermod -aG docker $USER\nnewgrp docker\nid`}
  output="uid=1001(ana) gid=995(docker) groups=995(docker),1001(ana)"
>

`usermod -aG docker` adds you (`-a`, *append*) to the `docker` group (`-G`) without taking you out of the others. A new group only counts in new sessions: `newgrp docker` opens a shell that already has it, and that's why `id` shows it as your main group (`gid`).

For it to count in all of them, log out and back in, as Docker's guide asks; on WSL, type `wsl --shutdown` in PowerShell, like the `wsl --install` from [Phase 0](/en/phase-0/), and open “Ubuntu” again. After that, your main group is `ana` again, with `docker` in the list.

Look for `docker` in `id`. Your numbers will be different, and you'll see more groups, like `sudo`.

</TryIt>

<Aside type="caution" title="The docker group is as good as being root">

Whoever can ask the engine for things can ask it for a container that sees the machine's whole disk, and inside that container they're `root`. That's why [Docker's documentation](https://docs.docker.com/engine/install/linux-postinstall/) warns: being in the `docker` group gives the same powers as `root`. On your computer, where you already use `sudo`, it doesn't change much. On a server, put in the group only people who could already be root.

</Aside>

Two programs show up, because Docker is two:

- **`Client`** is the `docker` command you type. Its `OS/Arch` is your system and your processor.
- **`Server`** is the engine, and below it, the pieces it uses: `containerd` and `runc`, which creates each container.
- **`API version`**: the client talks to the engine through an API, like the ones in [Phase 4](/en/phase-4/), and both have to understand the same version.

The output is from Ubuntu. **On the Mac,** the client says `darwin/arm64` and `Context: desktop-linux`, and the `Server` line says `Docker Desktop` and its version. But the engine says `linux`: it runs in Docker Desktop's virtual machine.

If you only see `Client` and then `failed to connect to the docker API`, the engine isn't running: open Docker Desktop, or start it with `systemctl` on Linux. If it says `permission denied`, you're missing the `docker` group.

</TryIt>

Now, your first container:

<TryIt
  title="Hello, Docker"
  cmd="docker run hello-world"
  output={`Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
58dee6a49ef1: Pull complete

Digest: sha256:5e23090353324d887c48ad5e5c56d294eab81588df9605b07d1afe895f9cc8f8

>

Word by word:

- **`docker`** is the client.
- **`run`** asks the engine to create a container and start it.
- **`hello-world`** is the <Term id="image">image</Term> it comes from: the template with the program inside.

</TryIt>

The output has two parts. The first six lines are Docker's, as it prepares the container:

1. **`Unable to find image 'hello-world:latest' locally`:** you don't have that image on your computer. `latest` is the tag Docker adds when you don't give one (lesson 8).
2. **`Pulling from library/hello-world`:** the download from Docker Hub, the public catalog of images. `library/` is the folder of the official images.
3. **The two lines with a code in front** are the pieces of the image, which download separately. [Lesson 2](/en/phase-7/docker-layers/) tells you what they are.
4. **`Digest: sha256:…`** is the image's fingerprint: a <Term id="hash">hash</Term> of its contents, like the one that names each Git commit. Lesson 8 uses it to pin versions.
5. **`Status: Downloaded newer image`:** the image is now on your computer.

The rest is written by **the program inside the container**. Its four steps are what just happened: the client talks to the engine, the engine downloads the image, creates a container and passes you what the program writes. `(arm64v8)` is the processor it was downloaded for: on most PCs you'll see `amd64`.

After writing, the program ends, and the container stops with it: a container lives as long as its program does. Run the command again: this time it downloads nothing, and `Hello from Docker!` comes out right away. The image was already there.

If instead you get `failed to connect` or `permission denied`, go back to the explanation of `docker version`.

### One kernel for everyone

Now you can check what you read earlier: that containers use someone else's kernel. `uname -sr` prints the system's name and its kernel version. Ask your Mac and two containers for it, one with Ubuntu and another with Alpine, another version of Linux:

<TryIt
  title="Which kernel is underneath?"
  cmd={`uname -sr\ndocker run --rm ubuntu:24.04 uname -sr\ndocker run --rm alpine:3 uname -sr`}
  output={`Darwin 25.6.0
…
Linux 6.8.0-117-generic
…
Linux 6.8.0-117-generic`}
>

`docker run` accepts a command after the image's name: the container runs that command instead of its own, and ends. `--rm` deletes it when it ends; [lesson 1](/en/phase-7/docker-image-vs-container/) tells you why that's a good idea.

The Mac says `Darwin`, its own kernel. The two containers, with different systems, say **the same Linux kernel**: the one of the virtual machine where Docker runs. We captured the output on a Mac with a different virtual machine; with Docker Desktop, yours usually ends in `linuxkit`, the minimal Linux its virtual machine carries. On Linux and on WSL, the containers say the same as your `uname -sr`, because they share your system's kernel.

The first time, each `docker run` downloads its image, with lines like the ones from `hello-world`: we removed them (`…`). Your versions will be different.

</TryIt>
