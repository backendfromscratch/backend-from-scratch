## The problem

On March 19, 2026, attackers with stolen credentials moved 76 of the 77 version tags of `trivy-action`, a GitHub action for finding vulnerabilities in images. Anyone using it with a version number got, under the usual name, code made to steal the CI's secrets ([Aqua Security](https://www.aquasec.com/blog/trivy-supply-chain-attack-what-you-need-to-know)). They also published infected versions of Trivy, among them images on Docker Hub.

Those who had pinned the action by its commit SHA weren't affected by the moved tags: that name can't be moved.

The same goes for images: `node:26-slim` or `latest` are names that their owner, or whoever steals their password, can point to another image tomorrow. This lesson teaches you to name them so they don't change, and to publish yours.

## The analogy

<Analogy>

You call a clinic and ask for an appointment with “the doctor on call on Monday.” Whoever is on call that day sees you: this week, Dr. Ruiz; next week, maybe someone else. The words don't change; the person does.

If you ask for an appointment with Dr. Ruiz by her medical license number, she sees you, whatever the day.

The clinic is the registry; “the doctor on call,” the tag; the license number, the digest.

<div slot="limits">

- Someone assigns the license number. The digest is calculated from the content: no other image can have it, and Docker checks it when downloading.
- In a registry, anyone with write permission moves a tag, including whoever steals your token.
- A digest's image never changes, not even to get fixes: to have them, you change digests.

</div>

</Analogy>

## How it really works

### A registry is an image store that speaks HTTP

A <Term id="registry">registry</Term> stores images so they can be downloaded with `docker pull` and uploaded with `docker push`. The ones you'll see most:

- **Docker Hub** (`docker.io`): the one Docker uses if you don't name another. The official images, like `node` or `postgres`, live in its `library` folder.
- **GitHub Container Registry** (`ghcr.io`): GitHub's, next to your code.
- **Each cloud's** (Amazon, Google, Azure) and others, like GitLab's. The `gcr.io` of the distroless image in [lesson 4](/en/phase-7/docker-multi-stage-build/) is Google's.

They all speak the same language: an HTTP API with routes that start with `/v2/`. You'll see it with `curl` in “Try it.”

### An image's name, piece by piece

A full name, with all its pieces:

```text
ghcr.io/ana/shop-api:1.0.0@sha256:d4ec32335b6a2a0c72672ab1e51da505dfa861968bd624f33ef51d2b1420780e
```

| Piece | Here | What it is | If you don't write it |
|---|---|---|---|
| Registry | `ghcr.io` | Where it's stored | `docker.io`, Docker Hub |
| User or organization | `ana` | Whose it is | `library`, the official ones (on Docker Hub) |
| Name | `shop-api` | Which image it is | It's required |
| Tag | `:1.0.0` | Which version, according to its owner | `latest` |
| Digest | `@sha256:d4ec…` | Exactly which content | Docker uses the tag |

That's why `nginx:1.31`, in [lesson 1](/en/phase-7/docker-image-vs-container/), was `docker.io/library/nginx:1.31`. Docker knows the first piece is a registry because it has a dot (`ghcr.io`), a port (`localhost:5000`) or is `localhost`.

### The tag moves; the digest doesn't

A <Term id="tag">tag</Term> is a name the image's owner puts on and takes off whenever they want. In Node, `26.1.0-slim` is an exact version; `26-slim`, the latest of Node 26.

But **`latest` is a tag like any other**: it points to the last thing someone uploaded with that name, which isn't necessarily the newest. And it's the one an image without a tag gets: your `shop-api` is `shop-api:latest`.

`26-slim` moves with each new Node 26 and with each Debian fix. What doesn't move is the <Term id="image-digest">digest</Term>, the SHA-256 <Term id="hash">hash</Term> (the fingerprint) from [lesson 2](/en/phase-7/docker-layers/). Ask Docker for the one of your `node:26-slim`:

<TryIt
  title="The digest of an image you already have"
  cmd="docker image inspect --format '{{index .RepoDigests 0}}' node:26-slim"
  output="node@sha256:193fe51b64e77981119c98c2002c9e32a70e2f006fb4d25068ce0558998917f0"
>

`RepoDigests` is the list of digests the registry knows the image by, and `index … 0` takes the first one. If you downloaded `node:26-slim` later than we did, your digest will be different: the tag will have moved.

</TryIt>

**Same content, same digest.** When downloading by digest, Docker calculates the digest of what it receives and compares them: if someone changes one byte in the registry, the download fails.

### One digest for each processor

Your laptop may have an ARM processor (a Mac with an Apple chip) and your server an Intel one. How does the same digest work for both?

<TryIt
  title="What's behind a tag"
  cmd="docker buildx imagetools inspect node:26-slim | grep -E '^(Name|Digest)|Platform'"
  output={`Name:      docker.io/library/node:26-slim
Digest:    sha256:193fe51b64e77981119c98c2002c9e32a70e2f006fb4d25068ce0558998917f0
  Platform:    linux/amd64
  Platform:    unknown/unknown
  Platform:    linux/arm64/v8
  Platform:    unknown/unknown
  Platform:    linux/ppc64le
  Platform:    unknown/unknown
  Platform:    linux/s390x
  Platform:    unknown/unknown`}
>

`docker buildx imagetools inspect` reads the image in the registry, without downloading it; the `grep` keeps the lines that matter.

The `193f…` digest is an **index**'s: a list with one image per processor (`amd64` for Intel and AMD, `arm64` for ARM…), each with its own digest. Each `unknown/unknown` is a note that goes with the image above it: what code it was built from and how.

</TryIt>

With the index's digest, each machine downloads the image for its processor. It's the one in the `FROM` lines of your Dockerfile.

### Publishing to Docker Hub or ghcr.io

Uploading an image takes two commands:

```sh
docker tag shop-api ghcr.io/ana/shop-api:1.0.0
docker push ghcr.io/ana/shop-api:1.0.0
```

- **`docker tag`** gives the image another name, with the registry in front, without copying it. It's lesson 4's `docker image tag`.
- **`docker push`** uploads the layers the registry is missing, and the registry answers with the digest.

First, the registry has to know who you are, with `docker login`. Use a **token**, not your password: it's created on the registry's website with just the permissions it needs, and it can be deleted without touching anything else. It's the <Term id="least-privilege">least privilege</Term> from Phase 6.

- **Docker Hub:** in your account, *Personal access tokens*. For a server that only downloads, a read-only one.
- **ghcr.io:** a GitHub token with the `write:packages` permission. In GitHub Actions, each run brings its own, the `GITHUB_TOKEN` ([Phase 8](/en/phase-8/ci-cd-github-actions/#the-github_token-a-key-that-lasts-one-run)).

```sh
docker login ghcr.io -u ana --password-stdin < token.txt
```

**`--password-stdin`** reads the token from standard input: written in the command, it would stay in your terminal's history. Afterwards, delete the file.

A token is a <Term id="secret">secret</Term>: out of Git, and rotated if it leaks ([lesson 8 of Phase 6](/en/phase-6/rate-limiting-secrets/#generating-a-secret-and-rotating-it)). Docker Desktop keeps it in the system keychain; Docker Engine on Linux, by default, unencrypted in `~/.docker/config.json`, and it warns you with a `WARNING!`.

And check **who will see it**: on Docker Hub, a new repository is public; on ghcr.io, private.

### Pinning by digest, and letting a robot update it

Pinning an image is writing its digest after the tag: `node:26-slim@sha256:193f…`. Docker downloads the digest's image, and the tag stays as a note for whoever reads it. This course does it everywhere:

- **Your Dockerfile:** the `FROM` lines carry `node:26-slim@sha256:193f…` ([lesson 3](/en/phase-7/dockerfile/)).
- **Your `compose.yaml`:** `postgres:18@sha256:7493…` and `redis:8@sha256:2c2d…` ([lesson 7](/en/phase-7/docker-compose/)).
- **This course's CI:** it tests the guided projects with PostgreSQL and Redis pinned by the same digests, and pins each GitHub action by its commit SHA, the defense that worked against the Trivy attack.

It's the `save-exact` from [Phase 3](/en/phase-3/what-is-node-js/#the-npmrc-three-lines-against-the-2025-attacks): **the version changes when you decide**. The price: fixes don't arrive on their own either.

That's why pinning goes with a robot that proposes the new digests:

- **Dependabot**, from GitHub, checks the `FROM` lines of your Dockerfiles (`package-ecosystem: docker` in its configuration) and the images in your `compose.yaml` (`docker-compose`). When the tag moves, it opens a *pull request* with the new digest. The course's repository uses it for npm and the GitHub actions.
- **Renovate** does the same, also with the images in GitHub Actions files.

Your CI tests the new digest, and you decide whether to accept it.

### Finding known vulnerabilities in an image

`npm audit`, in the [Phase 6 OWASP lesson](/en/phase-6/owasp-top-10/#npm-audit-packages-with-known-vulnerabilities), looked at your npm packages. An image also carries a whole Debian and npm itself. Two tools compare all of it with the public databases of known vulnerabilities (the CVEs):

- **Docker Scout**, which comes with Docker Desktop: `docker scout cves shop-api`.
- **Trivy**, from Aqua Security, free: you'll use it in “Try it,” from its image.

Yes, Trivy is the tool from the attack at the beginning. That's why you'll use it pinned by its digest.

### What a registry isn't

**A registry isn't a backup of your code.** Your image carries what the final stage copied (`src/`, `db/`, two scripts and `node_modules`), without tests, without the `Dockerfile` and without the Git history. The code lives in Git, and the image is built again from it. Nor is it a place for secrets: whatever goes into an image can be read by whoever downloads it.

### Move the latest tag

Imagine you fix something. So as not to touch the API, add a comment at the end of `src/server.ts`, in your project's folder, and rebuild:

```sh
echo '// version 1.0.1' >> src/server.ts
docker build -t shop-api .
```

### Find known vulnerabilities with Trivy

Word by word:

- **`-v /var/run/docker.sock:/var/run/docker.sock`** gives Trivy the *socket* through which the `docker` command talks to the engine. **Whoever has it is in charge of your Docker**, almost like `root`: only give it to images you trust, pinned by their digest.
- **`-v trivy-cache:/root/.cache`** keeps its vulnerability database in a volume: it downloads about 130 MB and takes up 1.5 GB.
- **`image --scanners vuln`** looks for known vulnerabilities in an image. Without `--scanners`, it also looks for secrets left behind in its files.

The first time it takes half a minute. We've removed (`…`) the download, the table of each vulnerability and about 200 rows of the summary.

</TryIt>

The report, read calmly:

- **Your shop's packages** (`app/node_modules`): no known vulnerabilities, as `npm audit --omit=dev` said in Phase 6.
- **Debian:** 164 vulnerabilities, 43 serious (`HIGH`) and none critical. None of them has a fix today: in its table, `Status` says `affected` (Debian hasn't fixed it yet) or `fix_deferred` (it leaves it for later). And 36 of the 43 serious ones are 4 `util-linux` vulnerabilities counted across its 9 packages: tools for mounting disks or logging in, which your API doesn't use.
- **npm:** 12 vulnerabilities, 4 serious, in the npm that comes with `node:26-slim`. Your server starts with `node`, but npm is in the image.

Your numbers will be different: the database changes every few hours. To see only the serious ones that have a fix:

## You have already seen it

- **Git.** In [Phase 1](/en/phase-1/git-internals/), a commit is named by its hash, and a Git tag points to one. The Trivy attack moved Git tags: with write permission, they move too.
- **The lockfile.** `package-lock.json` records the hash of each package. Pinning an image is the same, for the whole system.
- **The `ETag` from [Phase 2](/en/phase-2/http-caching/).** The registry uses the digest as its `Etag`: naming a content by its fingerprint.

## Common mistakes

- **`latest` on a server.** Each new server, or each `docker compose pull`, downloads the last thing someone uploaded: two servers with the same file can run different images. In production, an exact version and its digest.
- **Pinning and forgetting.** A year-old digest is an image with a year of unfixed vulnerabilities. Let a robot propose the new ones.
- **Pushing without the registry in the name.** `docker push shop-api` tries to upload to `docker.io/library/shop-api`, which isn't yours, and Docker Hub rejects it (`denied`). Name it with `docker tag`.
- **Logging in with your password.** Use a token with just the permissions it needs, and never in Git or in an `ENV` in the Dockerfile.
- **Port 5000 on a Mac.** The macOS AirPlay receiver uses it. If you get `address already in use`, or `curl` answers `403 Forbidden` with `AirTunes` in the `Server` header, use another port outside: `-p 127.0.0.1:5001:5000` and `localhost:5001/…`.

## Summary

- A registry stores images and speaks HTTP: Docker Hub (`docker.io`), ghcr.io and others. `docker push` uploads; `docker pull` downloads.
- The full name is `registry/user/name:tag@sha256:…`; without a registry, it's Docker Hub, and without a user, `library`.
- A tag, whether `latest` or `1.0.0`, is moved by whoever can write to the registry. A digest names an exact content, and Docker checks it.
- Pin your images by their digest, and let Dependabot or Renovate propose the new ones.
- Trivy or Docker Scout look for known vulnerabilities in the whole image: look first at the ones that have a fix and reach what you run.
