## The problem

The shop's image you built in [lesson 3](/en/phase-7/dockerfile/) works, but it carries everything. Inside are TypeScript and `drizzle-kit`, which are only for development; the cache `npm` left behind when installing, 34 MB; the tests and the scripts. That's **145 MB that get downloaded** every time a server needs it.

And its program runs as <Term id="root">root</Term>. If someone finds a flaw in the API and manages to run commands inside the container, they do it as the administrator: they can change the shop's code or install whatever they want.

In this lesson you bring it down to 92 MB, with no development tools, no `root` and a health check.

## The analogy

<Analogy>

In a restaurant, the kitchen is full of things: knives, pots, peelings, the recipe book. The cook tastes the sauce before serving it. But the kitchen doesn't reach the customer: the dish does, clean, with just what it needs.

A multi-stage Dockerfile does the same. The first stages are the kitchen: they install everything and check that the code is right. The last one is the dish: only what the API needs to work.

<div slot="limits">

- The kitchen isn't thrown away: the stages stay in your computer's cache, for next time. What they don't do is travel in the image.
- The cook tastes the sauce without anyone asking. Docker only runs a stage if the final one copies something from it: if not, it skips it, as you'll see.
- The dish has no knives, but the final image does carry a minimal Linux with Node and `npm`: small, not empty.

</div>

</Analogy>

## How it really works

### What an image doesn't need weighs and can be attacked

Every file in an image costs twice:

- **In megabytes.** Every server that starts your API downloads the image, and every deployment (Phase 8) waits for that download.
- **In risk.** Every program inside is one more tool for whoever breaks in, and one more place where there can be a known security flaw. All of that is the **attack surface**: the fewer pieces, the smaller the surface.

Compare two Node 26 images, the full one and `slim`. `dpkg -l` lists the installed Debian packages, and `grep -c ^ii` counts them:

<TryIt
  title="How many packages does each one bring?"
  cmd={`docker run --rm node:26 sh -c 'dpkg -l | grep -c ^ii'\ndocker run --rm node:26-slim sh -c 'dpkg -l | grep -c ^ii'`}
  output={`453
80`}
>

`node:26` brings 453 packages, among them `gcc` (a compiler), `git`, `python3` and `curl`: they're there to compile almost anything inside. `node:26-slim` brings 80, and none of those four. Your API uses none of them.

`node:26` downloads 452 MB: if you'd rather not, look at our output. Your numbers may vary.

</TryIt>

The same goes for `npm`. When it installs, it checks the packages against a list of known flaws: with the development dependencies, it warns of **4 moderate vulnerabilities**; with only the production ones, of **none**. You'll see it in "Try it."

| Base image | What it brings | Download |
|---|---|---|

The two smallest ones come with fine print.

### Alpine uses another C library

Almost every Linux program relies on a **C library**: the shared code to open files, reserve memory or use the network. Debian uses *glibc*; Alpine, a smaller one, *musl*. `docker run --rm node:26-alpine ldd --version` confirms it: `musl libc`.

For your API it makes no difference: it's JavaScript. But some `npm` packages bring **native code**, almost always compiled for *glibc*. On *musl* they may have no version, try to compile themselves when installing (the course's `.npmrc` doesn't let those scripts run) or fail in strange ways. The shop uses none; your next project might.

### Distroless doesn't even have a shell

*Distroless* images ("without a distribution") only carry the program and what it needs. Node works; a <Term id="shell">shell</Term> doesn't:

<TryIt
  title="An image without a shell"
  cmd={`docker run --rm gcr.io/distroless/nodejs26-debian13 -e "console.log(process.version)"\ndocker run --rm --entrypoint sh gcr.io/distroless/nodejs26-debian13`}
  output={`v26.11.0
docker: Error response from daemon: failed to create task for container: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: exec: "sh": executable file not found in $PATH

Run 'docker run --help' for more information`}
>

- The first one works: this image starts `node`, and `-e` passes it code.
- **`--entrypoint sh`** changes the program the container starts to `sh`, which doesn't exist.

</TryIt>

Whoever breaks in has no shell. Neither do you: you can't get in with `docker exec -it … sh` to look around.

**The course uses `node:26-slim`:** almost as small, with *glibc*, and with a shell to look inside. With alpine, the shop would come down to a 74 MB download, and with distroless, to 66 MB, against 92 MB.

### One Dockerfile, three stages

This is the shop's new Dockerfile. It has three `FROM`s, and each one starts a **stage**:

<ProjectCode file="shop-api/33-small-image/Dockerfile" />

It's a <Term id="multi-stage-build">multi-stage build</Term>: several stages, and **only the last one becomes the image**. Word by word:

- **`FROM … AS dependencies`**: `AS` gives the stage a name. This is the one from lesson 3: it installs all the dependencies, the development ones too (`devDependencies`, from [Phase 3](/en/phase-3/typescript-with-node/)).
- **`FROM dependencies AS check`**: a stage can start from another one. This one copies the project and runs **`npm run check`**, the `tsc --noEmit` from [Phase 3](/en/phase-3/typescript-with-node/), which goes over the whole project, tests included. If a type is wrong, `tsc` ends with an error and the build stops: there's no image.
- **`FROM node:26-slim… AS final`**: starts again from scratch, from the base image. Nothing from the earlier stages gets here unless you copy it.
- **`npm ci --omit=dev`**: installs only the production dependencies. `&& npm cache clean --force` deletes `npm`'s cache **in the same `RUN`**: deleted in another step, it would still take up space in its <Term id="image-layer">layer</Term>, as you saw in [lesson 2](/en/phase-7/docker-layers/). `npm` asks for `--force` as a precaution, and that's why it warns.
- **`COPY --from=check /app/src ./src`**: copies the `src` folder from the `check` stage, not from your computer. You'll see why in a moment.
- **`ENV NODE_ENV=production`**: this way many Node libraries know they're in production.

`USER` and `HEALTHCHECK` have their own sections. The final image keeps `package.json`, its *lockfile*, `.npmrc`, the production dependencies and `src/`: no tests, no scripts, no TypeScript.

### Why the final stage copies from check

BuildKit, Docker's builder, **only builds the stages the final one needs**. If the last one copies nothing from `check`, it doesn't run it.

We tested it with a deliberate mistake: in `src/app.ts`, `pool.querry` instead of `pool.query`, and the last `COPY` line changed to `COPY src ./src`, which copies from your computer. This is the build log, trimmed:

```text
#5 [final 1/5] FROM docker.io/library/node:26-slim@sha256:193fe51b…
#6 [final 2/5] WORKDIR /app
#6 CACHED
#7 [final 3/5] COPY package.json package-lock.json .npmrc ./
#7 CACHED
#8 [final 4/5] RUN npm ci --omit=dev && npm cache clean --force
#8 CACHED
#9 [final 5/5] COPY src ./src
#9 DONE 0.0s
#10 naming to docker.io/library/shop-api:latest done
```

**The build finishes fine, with the mistake inside**, and with no trace of `check` or `dependencies`. With `COPY --from=check`, the final stage depends on that stage, and Docker has to build it: the types are always checked. (We captured it with another image name, changed to `shop-api`.)

### USER node: no root inside the container

Inside a container, the program is `root` unless you say otherwise. In [lesson 1](/en/phase-7/docker-image-vs-container/) you saw it with `whoami` in nginx.

It looks harmless, but it's user 0 of the kernel all containers share. Docker takes away some of its powers, and even so:

- **Inside**, it can change the API's code, install programs with `apt` or read any file.
- **Outside**, if a flaw shows up in Docker or in the kernel that lets it escape the container, it escapes as the machine's `root`.

It's the <Term id="least-privilege">least privilege</Term> from the [users lesson of Phase 1](/en/phase-1/linux-users-and-permissions/): the API only needs to read its code and open port 3000. **`USER node`** makes what comes after it, and the container when it starts, run as `node`, an unprivileged <Term id="user">user</Term> that comes with the base image. The code was copied by `root`: `node` can read it, but not change it.

`USER node` goes at the end, after installing: `npm ci` needs to write in `/app`, which belongs to `root`.

### HEALTHCHECK: is the shop fine?

`docker ps` says `Up` as long as the process is alive, but the API can be running and not serving: without PostgreSQL, almost all its routes fail. For that, the new route, **`GET /health`**:

<ProjectCode file="shop-api/33-small-image/src/app.ts" region="health" />

It runs the smallest query, `SELECT 1`. If PostgreSQL replies, `200` and `{"status":"ok"}`; if not, `503 Service Unavailable`, with the error format from [Phase 4](/en/phase-4/api-errors-problem-details/). To use `pool`, `src/app.ts` also gains a line at the top: `import { pool } from './db.ts';`.

The **`HEALTHCHECK`** instruction tells Docker how to ask. It's a <Term id="healthcheck">health check</Term>:

- **`--interval=10s`**: it asks every 10 seconds. **`--timeout=3s`**: if it takes more than 3, it counts as a failure.
- **`CMD [...]`**: the command it runs inside the container. If its <Term id="exit-code">exit code</Term> is 0, all good; if it's 1, not good. The image doesn't bring `curl`, so it asks with Node's `fetch`: `r.ok` is true with a `200`.
- After **three failures in a row** (the default value), Docker marks the container `unhealthy`.

Docker only notes it down: it doesn't restart an `unhealthy` container. Others use it: Compose, in [lesson 7](/en/phase-7/docker-compose/), and in Phase 8 the deployment script, which waits for the new API to be `healthy`. nginx, in front, doesn't look at it: it sets a copy aside when a real request fails, as you'll see in Phase 8's reverse proxy lesson.

### Your secrets stay out

An image gets shared: you push it to a <Term id="registry">registry</Term> ([lesson 8](/en/phase-7/docker-registry/)) or you hand it to Luis. **Whoever has the image can read every file in every layer**, even if a layer above deletes it. If your `.env` gets in, your secrets get in.

That's why lesson 3's `.dockerignore` leaves out `.env` and `node_modules`: `docker build` doesn't send them, and `COPY . .` doesn't find them. The final stage adds another barrier: it only copies `src/`.

## You have already seen it

- **`devDependencies`.** In [Phase 3](/en/phase-3/typescript-with-node/), `--save-dev` set apart what's only for development. `--omit=dev` uses that list.
- **`www-data` and `postgres`.** In [Phase 1](/en/phase-1/linux-users-and-permissions/), each server had its own user. `USER node` is the same thing.
- **The missing `ps`.** In [lesson 1](/en/phase-7/docker-image-vs-container/), `docker exec web ps` didn't find `ps`: images already come trimmed down.

## Common mistakes

- **Deleting in another `RUN`.** `RUN npm cache clean --force` on its own line saves nothing: the cache is still in `npm ci`'s layer.
- **Copying `node_modules` from the install stage.** `COPY --from=dependencies /app/node_modules` brings the development ones along too.
- **`USER node` too early.** Right after `WORKDIR /app`, `npm ci` runs as `node` and can't write in `/app`, which belongs to `root`: `EACCES: permission denied, mkdir '/app/node_modules'`.
- **A `HEALTHCHECK` with `curl` in an image without `curl`.** The command always fails, and the container comes out `unhealthy` even though the API works fine.

## Summary

- What an image doesn't need costs in download and in attack surface: fewer programs, fewer known flaws and fewer tools for an attacker.
- `slim` is the course's base: minimal Debian, with *glibc* and a shell. Alpine uses *musl*, which can break native packages; distroless has no shell.
- In a multi-stage Dockerfile, only the last stage is the image. The others install and check, and the final one copies what it needs from them; if it copies nothing from one, BuildKit skips it.
- `npm ci --omit=dev && npm cache clean --force`, in the same `RUN`, leaves only the production dependencies.
- `USER node` runs the API without privileges, and `HEALTHCHECK` makes `docker ps` say `healthy` or `unhealthy` depending on `/health`.

`tsc` works the same inside, as you saw in the challenge. What happens is that it doesn't run.

<QuizOption text="Because BuildKit skips check: the final stage no longer copies anything from it." correct>

BuildKit only builds the stages the final one depends on. Without `--from=check`, the check isn't needed, and it doesn't run.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Your API uses an npm package that brings compiled native code. You change FROM node:26-slim to node:26-alpine to save 20 MB, and the image no longer starts. What’s the most likely cause?"
  review="Alpine uses another C library"
>

<QuizOption text="That alpine doesn’t bring Node 26, but an older version of Node.">

`node:26-alpine` brings Node 26, as its name says. What changes is the C library underneath.

</QuizOption>

<QuizOption text="That the native code is compiled for glibc and alpine uses musl." correct>

Many native packages are published compiled for *glibc*, and on *musl* they may have no version or fail when loading.

</QuizOption>

<QuizOption text="That alpine has no shell, and Node needs one to be able to start.">

The one without a shell is distroless, and even so Node starts in it. Alpine does bring one, `sh`.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Your container shows (unhealthy) in docker ps, but curl to /v2/products answers fine from your computer. What do you look at first?"
  review="HEALTHCHECK: is the shop fine?"
>

<QuizOption text="Nothing: unhealthy is only a warning, and Docker will restart the container on its own.">

Docker doesn't restart a container for being `unhealthy`: it only notes it down. And something is wrong: either the database or the check itself.

</QuizOption>

<QuizOption text="Giving the API more memory: unhealthy means it’s slow.">

`unhealthy` doesn't measure memory: it says the `HEALTHCHECK` command failed three times in a row, because of an error or because it went over `--timeout`.

</QuizOption>

<QuizOption text="The HEALTHCHECK command and what /health answers inside the container." correct>

If `/v2/products` works, the database is answering: most likely the check itself fails, for example with `curl` in an image that doesn't bring it, or with the wrong port. `docker inspect shop` keeps the last checks and their result.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Someone manages to run commands inside your container, which has USER node. What can they do?"
  review="USER node: no root inside the container"
>

<QuizOption text="Read the API’s code and configuration, but not change it." correct>

`node` reads `/app`, but can't write in it or install anything. Whatever the API knows, they know too: least privilege reduces the damage, it doesn't remove it.

</QuizOption>

<QuizOption text="Nothing: an unprivileged user can’t run commands.">

They can run everything that doesn't ask for special permissions: read files, make requests…

</QuizOption>

<QuizOption text="The same as with root: inside a container, users don’t count.">

Linux permissions work the same inside: `touch` answered `Permission denied`.

</QuizOption>

</QuizQuestion>

<QuizQuestion
  question="Luis removes .env from your .dockerignore “because the final image only copies src/.” Is your .env safe?"
  review="Your secrets stay out"
>

<QuizOption text="Yes: what doesn’t reach the final image can’t be read.">

It won't be in the final one, but `COPY . .` puts it in the `check` stage, which is kept in the cache. All it takes is someone changing the final stage without thinking.

</QuizOption>

<QuizOption text="No: Docker publishes all the stages when you push the image to a registry.">

Only the final image goes to the registry. The stages stay in your cache, which isn't a good place for a secret either.

</QuizOption>

<QuizOption text="Not entirely: it gets into the check stage, in your cache." correct>

With `.dockerignore`, the `.env` doesn't even leave your folder; without it, the only thing protecting you is that the final stage copies `src/`. A secret shouldn't depend on a single barrier.

</QuizOption>

</QuizQuestion>

</Quiz>
