## El problema

La imagen de la tienda que construiste en la [lección 3](/fase-7/dockerfile/) funciona, pero lleva de todo. Dentro están TypeScript y `drizzle-kit`, que solo sirven para desarrollar; la caché que `npm` dejó al instalar, 34 MB; los tests y los scripts. Son **145 MB que se descargan** cada vez que un servidor la necesita.

Y su programa se ejecuta como <Term id="root">root</Term>. Si alguien encuentra un fallo en la API y consigue ejecutar órdenes dentro del contenedor, lo hace como administrador: puede cambiar el código de la tienda o instalar lo que quiera.

En esta lección la dejas en 92 MB, sin herramientas de desarrollo, sin `root` y con un chequeo de salud.

## La analogía

<Analogy>

En un restaurante, la cocina está llena de cosas: cuchillos, ollas, peladuras, el libro de recetas. El cocinero prueba la salsa antes de servirla. Pero al cliente no le llega la cocina: le llega el plato, limpio, con lo justo.

Un Dockerfile multi-stage hace lo mismo. Las primeras etapas son la cocina: instalan todo y comprueban que el código está bien. La última es el plato: solo lo que la API necesita para funcionar.

<div slot="limits">

- La cocina no se tira: las etapas se quedan en la caché de tu ordenador, para la próxima vez. Lo que no hacen es viajar en la imagen.
- El cocinero prueba la salsa sin que nadie se lo pida. Docker solo ejecuta una etapa si la final copia algo de ella: si no, se la salta, como verás.
- El plato no lleva cuchillos, pero la imagen final sí lleva un Linux mínimo con Node y `npm`: pequeño, no vacío.

</div>

</Analogy>

## Cómo funciona de verdad

### Lo que sobra en una imagen pesa y se puede atacar

Cada fichero de una imagen cuesta dos veces:

- **En megas.** Cada servidor que arranca tu API descarga la imagen, y cada despliegue (Fase 8) espera a esa descarga.
- **En riesgo.** Cada programa que va dentro es una herramienta más para quien se cuele, y un sitio más donde puede haber un fallo de seguridad conocido. Todo eso es la **superficie de ataque**: cuantas menos piezas, menos superficie.

Compara dos imágenes de Node 26, la completa y la `slim`. `dpkg -l` lista los paquetes de Debian instalados, y `grep -c ^ii` los cuenta:

<TryIt
  title="¿Cuántos paquetes trae cada una?"
  cmd={`docker run --rm node:26 sh -c 'dpkg -l | grep -c ^ii'\ndocker run --rm node:26-slim sh -c 'dpkg -l | grep -c ^ii'`}
  output={`453
80`}
>

`node:26` trae 453 paquetes, entre ellos `gcc` (un compilador), `git`, `python3` y `curl`: sirven para compilar casi cualquier cosa dentro. `node:26-slim` trae 80, y ninguno de esos cuatro. Tu API no usa ninguno.

`node:26` descarga 452 MB: si no quieres, mira nuestra salida. Tus números pueden variar.

</TryIt>

Con `npm` pasa igual. Al instalar, revisa los paquetes contra una lista de fallos conocidos: con las dependencias de desarrollo, avisa de **4 vulnerabilidades moderadas**; solo con las de producción, de **ninguna**. Lo verás en «Pruébalo».

### Cuatro imágenes base para Node 26

La <Term id="base-image">imagen base</Term> es la del `FROM`: pone el sistema que hay debajo de tus capas, y con él, la mayor parte del tamaño. Para Node hay cuatro habituales:

  output={`IMAGE                                        ID             DISK USAGE   CONTENT SIZE   EXTRA
gcr.io/distroless/nodejs26-debian13:latest   c85d869757a6        253MB         60.2MB

`--filter reference=…` deja las imágenes cuyo nombre encaja con cualquiera de los filtros. Para verlas, antes tienes que descargarlas con `docker pull`: unos 670 MB entre las cuatro. Mira `CONTENT SIZE`, lo que se descarga. Tus tamaños e IDs serán otros.

</TryIt>

| Imagen base | Qué trae | Se descarga |
|---|---|---|
| `node:26` | Debian completo, con herramientas para compilar | 452 MB |
| `node:26-slim` | Debian mínimo y Node | 88 MB |
| `node:26-alpine` | Alpine, otro Linux mínimo, y Node | 68 MB |
| `nodejs26-debian13` (*distroless*, de Google) | Node y las bibliotecas que necesita; ni shell ni `apt` | 60 MB |

Las dos más pequeñas tienen letra pequeña.

### Alpine usa otra biblioteca de C

Casi todo programa de Linux se apoya en una **biblioteca de C**: el código común para abrir ficheros, reservar memoria o usar la red. Debian usa *glibc*; Alpine, una más pequeña, *musl*. `docker run --rm node:26-alpine ldd --version` lo confirma: `musl libc`.

Para tu API da igual: es JavaScript. Pero algunos paquetes de `npm` traen **código nativo**, compilado casi siempre para *glibc*. Sobre *musl* pueden no tener versión, intentar compilarse al instalar (el `.npmrc` del curso no deja ejecutar esos scripts) o fallar de formas raras. La tienda no usa ninguno; tu próximo proyecto puede.

### Distroless no trae ni una shell

Las imágenes *distroless* («sin distribución») solo llevan el programa y lo que necesita. Node funciona; una <Term id="shell">shell</Term>, no:

<TryIt
  title="Una imagen sin shell"
  cmd={`docker run --rm gcr.io/distroless/nodejs26-debian13 -e "console.log(process.version)"\ndocker run --rm --entrypoint sh gcr.io/distroless/nodejs26-debian13`}
  output={`v26.11.0
docker: Error response from daemon: failed to create task for container: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: exec: "sh": executable file not found in $PATH

Run 'docker run --help' for more information`}
>

- La primera funciona: esta imagen arranca `node`, y `-e` le pasa código.
- **`--entrypoint sh`** cambia el programa que arranca el contenedor por `sh`, que no existe.

</TryIt>

Quien se cuele no tiene shell. Tú tampoco: no puedes entrar con `docker exec -it … sh` a mirar.

**El curso usa `node:26-slim`:** casi tan pequeña, con *glibc*, y con una shell para mirar dentro. Con alpine, la tienda se quedaría en 74 MB de descarga, y con distroless, en 66 MB, frente a 92 MB.

### Un Dockerfile, tres etapas

Este es el Dockerfile nuevo de la tienda. Tiene tres `FROM`, y cada uno empieza una **etapa**:

<ProjectCode file="tienda-api/33-imagen-pequena/Dockerfile" />

Es una <Term id="multi-stage-build">construcción multi-stage</Term>: varias etapas, y **solo la última se convierte en la imagen**. Palabra a palabra:

- **`FROM … AS dependencias`**: `AS` le da nombre a la etapa. Esta es la de la lección 3: instala todas las dependencias, también las de desarrollo (`devDependencies`, de la [Fase 3](/fase-3/typescript-con-node/)).
- **`FROM dependencias AS comprobar`**: una etapa puede partir de otra. Esta copia el proyecto y ejecuta **`npm run check`**, el `tsc --noEmit` de la [Fase 3](/fase-3/typescript-con-node/), que revisa todo el proyecto, tests incluidos. Si un tipo está mal, `tsc` termina con error y la construcción se para: no hay imagen.
- **`FROM node:26-slim… AS final`**: empieza otra vez de cero, desde la imagen base. Nada de las etapas anteriores llega aquí si no lo copias.
- **`npm ci --omit=dev`**: instala solo las dependencias de producción. `&& npm cache clean --force` borra la caché de `npm` **en el mismo `RUN`**: borrada en otro paso, seguiría ocupando su <Term id="image-layer">capa</Term>, como viste en la [lección 2](/fase-7/capas-docker/). `npm` pide `--force` como precaución, y por eso avisa.
- **`COPY --from=comprobar /app/src ./src`**: copia la carpeta `src` de la etapa `comprobar`, no de tu ordenador. Ahora verás por qué.
- **`ENV NODE_ENV=production`**: así muchas bibliotecas de Node saben que están en producción.

`USER` y `HEALTHCHECK` tienen sección propia. La imagen final se queda con `package.json`, su *lockfile*, `.npmrc`, las dependencias de producción y `src/`: ni tests, ni scripts, ni TypeScript.

### Por qué la final copia de comprobar

BuildKit, el constructor de Docker, **solo construye las etapas que la final necesita**. Si la última no copia nada de `comprobar`, no la ejecuta.

Lo probamos con un fallo a propósito: en `src/app.ts`, `pool.querry` en lugar de `pool.query`, y la última línea `COPY` cambiada por `COPY src ./src`, que copia de tu ordenador. Este es el registro de la construcción, recortado:

```text
#5 [final 1/5] FROM docker.io/library/node:26-slim@sha256:193fe51b…
#6 [final 2/5] WORKDIR /app
#6 CACHED
#7 [final 3/5] COPY package.json package-lock.json .npmrc ./
#7 CACHED
#8 [final 4/5] RUN npm ci --omit=dev && npm cache clean --force
#8 CACHED
#9 [final 5/5] COPY src ./src
#9 DONE 0.0s
#10 naming to docker.io/library/tienda-api:latest done
```

**La construcción termina bien, con el fallo dentro**, y sin rastro de `comprobar` ni de `dependencias`. Con `COPY --from=comprobar`, la final depende de esa etapa, y Docker tiene que construirla: los tipos se comprueban siempre. (La capturamos con otro nombre de imagen, cambiado por `tienda-api`.)

### USER node: sin root dentro del contenedor

Dentro de un contenedor, el programa es `root` salvo que digas otra cosa. En la [lección 1](/fase-7/imagen-contenedor-docker/) lo viste con `whoami` en nginx.

Parece inofensivo, pero es el usuario 0 del núcleo que comparten todos los contenedores. Docker le quita poderes, y aun así:

- **Dentro**, puede cambiar el código de la API, instalar programas con `apt` o leer cualquier fichero.
- **Fuera**, si aparece un fallo en Docker o en el núcleo que permite escapar del contenedor, escapa como `root` de la máquina.

Es el <Term id="least-privilege">mínimo privilegio</Term> de la [lección de usuarios de la Fase 1](/fase-1/usuarios-y-permisos-linux/): la API solo necesita leer su código y abrir el puerto 3000. **`USER node`** hace que lo de detrás, y el contenedor al arrancar, se ejecute como `node`, un <Term id="user">usuario</Term> sin privilegios que trae la imagen base. El código lo copió `root`: `node` puede leerlo, pero no cambiarlo.

`USER node` va al final, después de instalar: `npm ci` necesita escribir en `/app`, que es de `root`.

### HEALTHCHECK: ¿la tienda está bien?

`docker ps` dice `Up` mientras el proceso viva, pero la API puede estar en marcha y no servir: sin PostgreSQL, casi todas sus rutas fallan. Para eso, la ruta nueva, **`GET /salud`**:

<ProjectCode file="tienda-api/33-imagen-pequena/src/app.ts" region="salud" />

Hace la consulta más pequeña, `SELECT 1`. Si PostgreSQL contesta, `200` y `{"estado":"ok"}`; si no, `503 Service Unavailable`, con el formato de errores de la [Fase 4](/fase-4/errores-api-problem-details/). Para usar `pool`, `src/app.ts` gana también una línea arriba: `import { pool } from './bd.ts';`.

La instrucción **`HEALTHCHECK`** le dice a Docker cómo preguntar. Es un <Term id="healthcheck">healthcheck</Term>, un chequeo de salud:

- **`--interval=10s`**: pregunta cada 10 segundos. **`--timeout=3s`**: si tarda más de 3, cuenta como fallo.
- **`CMD [...]`**: la orden que ejecuta dentro del contenedor. Si su <Term id="exit-code">código de salida</Term> es 0, todo bien; si es 1, mal. La imagen no trae `curl`, así que pregunta con el `fetch` de Node: `r.ok` es cierto con un `200`.
- Tras **tres fallos seguidos** (el valor por defecto), Docker marca el contenedor `unhealthy`.

Docker solo lo apunta: no reinicia un contenedor `unhealthy`. Lo usan otros: Compose, en la [lección 7](/fase-7/docker-compose/), y el balanceador, en la Fase 8.

### Tus secretos no entran

Una imagen se comparte: la subes a un <Term id="registry">registro</Term> ([lección 8](/fase-7/docker-hub-registro/)) o se la pasas a Luis. **Quien tiene la imagen puede leer cada fichero de cada capa**, aunque una capa de arriba lo borre. Si tu `.env` entra, entran tus secretos.

Por eso el `.dockerignore` de la lección 3 deja fuera `.env` y `node_modules`: `docker build` no los manda, y `COPY . .` no los encuentra. La etapa final añade otra barrera: solo copia `src/`.

## Ya lo has visto

- **`devDependencies`.** En la [Fase 3](/fase-3/typescript-con-node/), `--save-dev` separó lo que solo sirve para desarrollar. `--omit=dev` usa esa lista.
- **`www-data` y `postgres`.** En la [Fase 1](/fase-1/usuarios-y-permisos-linux/), cada servidor tenía su usuario. `USER node` es lo mismo.
- **`ps` que no está.** En la [lección 1](/fase-7/imagen-contenedor-docker/), `docker exec web ps` no encontró `ps`: las imágenes ya vienen recortadas.

## Errores comunes

- **Borrar en otro `RUN`.** `RUN npm cache clean --force` en su propia línea no ahorra nada: la caché sigue en la capa de `npm ci`.
- **Copiar `node_modules` de la etapa de instalación.** `COPY --from=dependencias /app/node_modules` se lleva también las de desarrollo.
- **`USER node` demasiado pronto.** Justo después de `WORKDIR /app`, `npm ci` se ejecuta como `node` y no puede escribir en `/app`, que es de `root`: `EACCES: permission denied, mkdir '/app/node_modules'`.
- **Un `HEALTHCHECK` con `curl` en una imagen sin `curl`.** La orden falla siempre, y el contenedor sale `unhealthy` aunque la API vaya bien.

## Resumen

- Lo que sobra en una imagen cuesta en descarga y en superficie de ataque: menos programas, menos fallos conocidos y menos herramientas para un atacante.
- `slim` es la base del curso: Debian mínimo, con *glibc* y una shell. Alpine usa *musl*, que puede romper paquetes nativos; distroless no tiene shell.
- En un Dockerfile multi-stage, solo la última etapa es la imagen. Las otras instalan y comprueban, y la final copia de ellas lo que necesita; si no copia nada de una, BuildKit se la salta.
- `npm ci --omit=dev && npm cache clean --force`, en el mismo `RUN`, deja solo las dependencias de producción.
- `USER node` ejecuta la API sin privilegios, y `HEALTHCHECK` hace que `docker ps` diga `healthy` o `unhealthy` según `/salud`.
