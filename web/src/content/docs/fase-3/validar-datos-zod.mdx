## El problema

Imagina que alguien le manda pedidos raros a la API de la tienda con `curl`. Esto contesta la API de la [lección 6, «Middleware»](/fase-3/que-es-middleware/):

```sh
curl -w '\n' --json '{"productoId":1,"cantidad":-3}' localhost:3000/pedidos
curl -w '\n' --json '{"productoId":1,"cantidad":"muchas"}' localhost:3000/pedidos
curl -w '\n' --json '{"productoId":1}' localhost:3000/pedidos
```

```
{"id":1,"productoId":1,"cantidad":-3,"estado":"pendiente"}
{"id":2,"productoId":1,"cantidad":"muchas","estado":"pendiente"}
{"id":3,"productoId":1,"estado":"pendiente"}
```

Tres pedidos guardados: menos tres camisetas, «muchas» camisetas y uno sin cantidad. Ninguno tiene sentido, y la API los ha aceptado todos.

En la [Fase 0](/fase-0/que-es-el-backend/#por-qué-no-puede-hacerlo-todo-el-frontend) viste la regla de oro del backend: **nunca te fíes del <Term id="client">cliente</Term>**. El formulario de la web puede comprobar la cantidad, pero cualquiera puede saltárselo y escribir la petición a mano, como acabas de ver. En esta lección, tu servidor empieza a cumplir esa regla.

## La analogía

<Analogy>

En la [lección 3](/fase-3/typescript-con-node/#la-analogía), el impreso lo rellenabas tú. Ahora estás al otro lado de la ventanilla, donde llegan los impresos de otros. Antes de tramitar uno, el empleado lo revisa con una lista: que estén las casillas obligatorias, que la fecha sea una fecha y que en «número de hijos» no ponga «muchos». Si algo falla, te lo devuelve con cada casilla mal rellenada marcada y el porqué.

Esa lista es un esquema, y esa revisión, la validación. Y fíjate en que un impreso bien rellenado no es una solicitud concedida: si tienes derecho o no, lo decide después el departamento, con sus propios datos.

<div slot="limits">

- El empleado usa el sentido común: entiende «dos» escrito con letras. Un esquema solo comprueba lo que pone en él, ni más ni menos: si olvidas una regla, lo que la incumple pasa.
- El empleado no te corrige el impreso. Un esquema puede arreglar algunas cosas por el camino, si se lo pides: quitar espacios de sobra o convertir el texto `"2"` en el número `2`.

## Cómo funciona de verdad

### Los tipos de TypeScript desaparecen al ejecutarse

En la [lección 4](/fase-3/servidor-http-node/), al cuerpo de un pedido le añadiste `as { productoId: number; cantidad: number }`, y en las lecciones 5 y 6, la anotación `datos: { … }`. Las dos le prometen a TypeScript que el cuerpo tiene esa forma, y TypeScript te cree sin comprobarlo.

Y Node [borra los tipos antes de ejecutar](/fase-3/typescript-con-node/#node-borra-los-tipos-al-ejecutar). Por eso `npm run check` no se queja de la API de la lección 6, que aun así guarda `"muchas"` como cantidad.

| | TypeScript | Un esquema |
|---|---|---|
| Cuándo comprueba | Mientras escribes el código | Cada vez que llega una petición |
| Qué comprueba | Que tu código use bien los datos | Que los datos que llegan sean como esperas |
| Si algo falla | El editor lo marca en rojo | El servidor responde con un error |

Los dos hacen falta. **TypeScript vigila tu código; el esquema vigila los datos de fuera.**

### Un esquema describe la forma de los datos

Un <Term id="schema">esquema</Term> es una descripción de cómo tienen que ser unos datos: qué campos llevan, si cada uno es un número o un texto, y qué valores se aceptan. Un programa compara con él lo que llega y te dice si cumple o qué falla. Eso es la <Term id="validation">validación</Term>.

Una de las herramientas más usadas para esto en TypeScript es Zod. Instálala en la carpeta del proyecto, `~/curso-backend/fase-3/tienda-api`, junto con su conector para Hono, el <Term id="framework">framework</Term> de la [lección 5](/fase-3/express-hono-fastify/):

Antes de tocar el servidor, prueba Zod en el <Term id="repl">REPL</Term>. Abre la terminal en la carpeta del proyecto y escribe `node`. En el REPL, `import … from` no funciona: se usa `await import('zod')`, que hace lo mismo.

<TryIt
  title="En el REPL: un esquema y dos pedidos"
  lang="js"
  cmd={`const { z } = await import('zod')
const esquemaPedido = z.object({ productoId: z.number(), cantidad: z.number().int().min(1) })
esquemaPedido.safeParse({ productoId: 1, cantidad: 2 })
esquemaPedido.safeParse({ productoId: 'uno', cantidad: -3 }).error.issues`}
  output={`undefined
undefined
{ success: true, data: { productoId: 1, cantidad: 2 } }
[

    expected: 'number',
    code: 'invalid_type',
    path: [ 'productoId' ],
    message: 'Invalid input: expected number, received string'
  },
  {
    origin: 'number',
    code: 'too_small',
    minimum: 1,
    inclusive: true,
    path: [ 'cantidad' ],
    message: 'Too small: expected number to be >=1'
  }
]`}
>

Palabra a palabra:

- `const { z } = …` saca de Zod la pieza llamada `z` y la guarda con ese nombre. `z` es todo Zod: cada pieza de un esquema se pide con `z.algo`.
- `z.object({ … })` describe un <Term id="object">objeto</Term> y sus campos. `z.number()` dice «un número», y cada punto añade una regla: `.int()`, entero, y `.min(1)`, como mínimo 1.
- `safeParse` compara unos datos con el esquema. Si cumplen, devuelve `success: true` y los datos en `data`.
- Si no cumplen, `success` es `false` y `error.issues` es la lista de problemas: uno por campo que falla.

Cada problema dice qué ha pasado (`code`), un mensaje (`message`) y, sobre todo, **dónde**: `path`, el campo que falla.

Zod también tiene `parse`, que devuelve los datos o, si no cumplen, lanza un error, una <Term id="exception">excepción</Term>: lo verás en la [lección 8](/fase-3/errores-y-logs-node/). En un servidor, `safeParse` te deja decidir qué responder.

</TryIt>

Palabra a palabra:

- `export` deja usar el esquema desde otros ficheros, como en la [lección 3](/fase-3/typescript-con-node/).
- `z.number({ error: '…' })` es «un número», con el mensaje para cuando no lo es. Un campo que falta tampoco es un número, así que recibe el mismo mensaje.
- `.int('…')`, `.min(1, '…')` y `.max(10, '…')` son las reglas, cada una con su mensaje. El máximo de 10 lo decide la tienda: nadie pide cien sudaderas de una vez.
- `z.infer<typeof esquemaPedido>` saca del esquema el tipo de TypeScript: `{ productoId: number; cantidad: number }`. Entre `<` y `>` va de dónde sale el tipo, y `typeof` significa aquí «el tipo de este valor».

La última línea evita escribir la forma dos veces, una para TypeScript y otra para Zod. **El esquema es la única fuente**: si le añades un campo, el tipo lo tiene también.

### Un middleware valida antes de que llegue la ruta

En la [lección 6](/fase-3/que-es-middleware/) viste que un <Term id="middleware">middleware</Term> es una capa por la que pasa la petición antes de llegar a la ruta, y que puede responder sin dejarla seguir. Validar es justo eso. Este es el middleware del proyecto, en `src/middleware/validar.ts`:

<ProjectCode file="tienda-api/07-validacion/src/middleware/validar.ts" region="validar" />

Palabra a palabra:

- `zValidator` es el conector de Hono con Zod. Lee la parte de la petición que le digas (`donde`), la compara con el esquema, como `safeParse`, y te da el resultado.
- `donde` puede ser `'json'` (el <Term id="request-body">cuerpo</Term>), `'param'` (los <Term id="route-parameter">parámetros de la ruta</Term>, como el `:id`), `'query'` (la <Term id="query-string">query string</Term>), y también las cabeceras o las cookies.
- Lo que va entre `<` y `>`, con los dos tipos del `import type`, le dice a TypeScript qué pueden ser `donde` y `esquema`: una parte de la petición y un esquema de Zod. Gracias a eso, la ruta sabrá después qué tipo tienen los datos. Puedes leerlo como `validar(donde, esquema)`.
- La función del final recibe el `resultado`. Si no es un éxito, convierte cada problema en `{ campo, problema }`, con `path.join('.')` para que un campo dentro de otro, como `[ 'direccion', 'calle' ]`, se lea `direccion.calle`. Y responde `422`: ha podido leer la petición, pero los datos no valen.
- Si todo cumple, no devuelve nada, y la petición sigue hacia la ruta.

Sin esa función, `zValidator` respondería `400` con el error de Zod entero, `{"success":false,"error":{"name":"ZodError",…`, con los mensajes en inglés.

### La ruta recibe los datos ya comprobados

Con `validar`, la ruta de los pedidos queda así:

<ProjectCode file="tienda-api/07-validacion/src/app.ts" region="nuevo-pedido" />

- `validar('json', esquemaPedido)` va entre la ruta y su función, como `soloAdmin` en la lección 6. Si el cuerpo no cumple, la función de la ruta ni se ejecuta.
- `c.req.valid('json')` devuelve los datos ya comprobados, y TypeScript conoce su tipo: ya no hace falta `as` ni anotación. Esta vez la promesa es verdad. `const { productoId, cantidad } = …` saca esos dos datos, como `const { z }` en el REPL.

Fíjate en la comprobación que queda: `buscarProducto`. Un pedido del producto 99 tiene la forma perfecta y pasa el esquema. Pero la tienda no tiene producto 99, y la ruta responde `422`, como a un dato que no vale. No es un `404`: `/pedidos` existe, y lo que falla es un dato del cuerpo.

Son dos preguntas distintas:

- **¿Tienen los datos la forma correcta?** La responde el esquema, sin saber nada de la tienda.
- **¿Tienen sentido para la tienda ahora?** Que el producto exista o que haya stock depende de los datos del momento. La responde la ruta.

### Lo que llega en la ruta y en la query string siempre es texto

En `/productos/2`, el `2` llega como el texto `"2"`, y en `?max=10`, el `10` también. Una URL es texto. Así que `z.number()` rechazaría siempre los parámetros. Para eso está `z.coerce`:

<TryIt
  title="En el REPL: el texto «2» y el número 2"
  lang="js"
  cmd={`z.number().safeParse('2').success
z.coerce.number().safeParse('2')
z.coerce.number().safeParse('abc').success`}
  output={`false
{ success: true, data: 2 }
false`}
>

`z.coerce.number()` convierte el texto en número antes de comprobarlo: `'2'` pasa y llega como `2`. `'abc'` no es ningún número, y falla.

</TryIt>

### 422 si los datos no valen; 400 si ni se pueden leer

Esta API sigue la regla de la [lección 3 de la Fase 2](/fase-2/codigos-de-estado-http/#los-códigos-que-importan): con un `400`, el servidor ni siquiera ha podido leer la petición; con un `422`, la ha leído, y lo que pide no tiene sentido.

| Lo que llega a `POST /pedidos` | Código | Quién responde |
|---|---|---|
| Un cuerpo que no es JSON | `400` | Hono, antes de que el esquema lo vea |
| `{"productoId":1,"cantidad":-3}` | `422` | `validar`, con `detalles` |
| `{"productoId":99,"cantidad":1}` | `422` | La ruta, sin `detalles` |

El `400` de un cuerpo roto lo escribe Hono por su cuenta, y en texto, no en JSON: `Malformed JSON in request body`. En la [lección 8](/fase-3/errores-y-logs-node/) lo convertirás en JSON, como el resto de la API.

No todas las APIs distinguen: [Stripe](https://docs.stripe.com/api/errors), o el propio `zValidator` sin tu función, responden `400` a cualquier dato que no vale, porque el `400` es el error general del cliente. Lo que importa es seguir siempre el mismo criterio y que el cuerpo diga qué falla.

## Ya lo has visto

- **Los formularios que marcan un campo en rojo** antes de enviar («Este campo es obligatorio») validan en el navegador. Es cómodo para quien escribe, pero el servidor lo repite, porque esa comprobación se puede saltar.
- **Los errores que llegan después de enviar**, como «Ese código postal no existe», vienen del servidor. Si abres DevTools ([cómo abrirlo](/fase-2/#antes-de-empezar-devtools)), en la pestaña **Red** (*Network*) verás un `400` o un `422` con una lista de campos, como tus `detalles`, que la página usa para marcar cada uno.

## Errores comunes

- **Validar solo en el formulario.** Cualquiera puede enviar la petición con `curl`, sin pasar por la web.
- **`z.number()` para un parámetro de la ruta o de la query string.** Siempre llegan como texto y fallarían siempre. Usa `z.coerce.number()`.
- **Olvidar `Content-Type: application/json`.** Con `curl -d` y sin `-H`, Hono no lee el cuerpo como JSON y todos los campos fallan con «Tiene que ser un número». Usa `--json`.
- **Usar `parse` en una ruta sin más.** Si los datos no cumplen, lanza un error, y el cliente recibe un `500` en vez de un `422`. En un servidor, `safeParse`, o un middleware como `validar`.

## Resumen

- Los tipos de TypeScript se borran al ejecutar: no protegen de lo que llega por la red. Un esquema sí, porque comprueba los datos cada vez que llegan.
- Con Zod, `z.object` describe la forma, cada punto añade una regla y `safeParse` dice si cumple o qué falla, campo por campo. `z.infer` saca el tipo del mismo esquema.
- El middleware `validar` comprueba el cuerpo, la ruta o la query string, y si algo no cumple responde `422` con cada problema, sin llegar a la ruta. Un cuerpo que no es JSON recibe un `400` de Hono: ni se ha podido leer.
- Lo que viene en la URL siempre es texto: `z.coerce` lo convierte antes de comprobarlo.
- El esquema comprueba la forma; las reglas que dependen de los datos de la tienda, como que el producto exista, las comprueba la ruta.
