## El problema

La empresa de reparto que va a usar la API de la tienda le escribe a Ana: «¿Qué campos lleva un pedido? ¿Qué respondéis si no existe? ¿El precio va en euros?». Ana contesta por correo. Una semana después, quien programa la app móvil pregunta lo mismo.

Imagina que, para no repetirse, Ana escribe un README (el fichero de texto que explica un proyecto) con cada ruta, en la época de la versión 1, con `precio` en euros. En la lección 4, «Versionado», la versión 2 pasó a `precioCentimos`, y nadie tocó el README. Ahora miente, y nadie se entera: **nada comprueba que un texto escrito a mano diga lo mismo que el código.**

Además, un README solo lo leen personas: ningún programa puede comprobar con él que la API cumple lo que promete. Hace falta una descripción que lean personas y programas, y que salga del propio código.

## La analogía

<Analogy>

Piensa en los planos de un edificio. Usan símbolos que cualquier arquitecto, electricista o fontanero entiende, y con ellos el fontanero sabe por dónde van las tuberías sin llamar al arquitecto.

Un documento OpenAPI es el plano de una API: en un formato que todos conocen, dice qué rutas hay, qué datos entran y qué sale. Como un plano, se puede dibujar antes de construir o sacar de lo ya construido.

<div slot="limits">

- Un plano dibujado a mano puede no coincidir con la obra. El de esta lección se genera desde el código: lo que dice de las peticiones siempre es verdad; de las respuestas, no del todo.
- Con un plano no puedes abrir un grifo. Con la página de la documentación sí: envía peticiones de verdad a la API.

</div>

</Analogy>

## Cómo funciona de verdad

### Un documento que describe cada ruta

Esto dirá la API de la tienda, al final de la lección, sobre `GET /v2/productos/{id}`. `jq`, de la [lección 8 de la Fase 3](/fase-3/errores-y-logs-node/), saca esa parte del documento:

```sh
curl -s localhost:3000/v2/openapi.json | jq '.paths["/productos/{id}"].get'
```

```json
{
  "tags": [
    "Productos"
  ],
  "summary": "Un producto",
  "parameters": [
    {
      "schema": {
        "type": "integer",
        "example": 2
      },
      "required": true,
      "name": "id",
      "in": "path"
    }
  ],
  "responses": {
    "200": {
      "description": "El producto",
      "content": {
        "application/json": {
          "schema": {
            "$ref": "#/components/schemas/Producto"
          }
        }
      }
    },
    "404": {
      "description": "No existe ese producto",
      "content": {
        "application/problem+json": {
          "schema": {
            "$ref": "#/components/schemas/Problema"
          }
        }
      }
    },
    "422": {
      "description": "Los datos no son válidos: «errores» dice qué falla",
      "content": {
        "application/problem+json": {
          "schema": {
            "$ref": "#/components/schemas/Problema"
          }
        }
      }
    }
  }
}
```

Sin leer el código, sabes lo que preguntaba la empresa de reparto:

- **`parameters`:** la ruta lleva un `id` (`"in": "path"`), entero y obligatorio.
- **`responses`:** cada <Term id="status-code">código</Term> que puede salir: un `200` con un `Producto`, o un `404` y un `422` con un `Problema`, el formato de errores de la lección 2.
- **`$ref`:** «la forma está en otra parte del documento». `Producto` se describe una vez, en `components`, y lo usan todas las rutas.

Este documento sigue **<Term id="openapi">OpenAPI</Term>**, un formato estándar para describir APIs <Term id="http">HTTP</Term>. Se escribe en <Term id="json">JSON</Term> o en YAML (otro formato de texto, con sangrías en lugar de llaves). La versión que usa el proyecto es la 3.1, de 2021; en septiembre de 2025 salió la 3.2.

Ese documento es el **<Term id="api-contract">contrato</Term>** de la API: lo que promete a quien la usa.

### OpenAPI y Swagger: un formato con dos nombres

Verás «Swagger» por todas partes, a veces como si fuera lo mismo que OpenAPI. Lo fue:

1. **2010:** Tony Tam, en el diccionario en internet Wordnik, crea Swagger: un formato para describir su API y herramientas que lo leen.
2. **2015:** SmartBear compra Swagger y regala el formato a la nueva OpenAPI Initiative, de la Linux Foundation.
3. **2016:** el formato pasa a llamarse OpenAPI Specification. Swagger 2.0 fue la última versión con el nombre antiguo.

Desde entonces, **OpenAPI es el formato y Swagger es una marca de herramientas** de SmartBear: Swagger UI (una página que enseña el documento), Swagger Editor y Swagger Codegen.

| Si lees… | Quiere decir… |
|---|---|
| Un `swagger.json` con `"swagger": "2.0"` | Un documento con la versión antigua del formato |
| Un `openapi.json` con `"openapi": "3.1.0"` | Un documento con el formato de hoy (3.0, 3.1 o 3.2) |
| «Tenemos Swagger en `/swagger`» | Una página de Swagger UI, que lee un documento OpenAPI |

### Code-first: el contrato sale de los esquemas

El documento se puede escribir a mano o generar desde el código. La tienda lo genera, y eso se llama ***code-first*** («primero el código»): sale de los mismos <Term id="schema">esquemas</Term> de Zod que validan desde la [lección 7 de la Fase 3](/fase-3/validar-datos-zod/), gracias a `@hono/zod-openapi`. ### Cada ruta, con lo que recibe y lo que responde

Cada ruta se describe en un fichero nuevo, `src/contrato.ts`. Esta es la de ver un producto:

<ProjectCode file="tienda-api/14-openapi/src/contrato.ts" region="ver-producto" />

- **`createRoute`** describe una ruta sin el código que la atiende: qué recibe (`request`) y qué responde (`responses`).
- **`path: '/productos/{id}'`** escribe el parámetro con llaves, como OpenAPI, no con `:id`.
- **`tags`** agrupa las rutas en la página de la documentación; **`summary`** es su nombre allí.
- **`request: { params: esquemaId }`:** el `id` se valida con `esquemaId`, el de la Fase 3.

`enJson` y `conProblema` son dos <Term id="function">funciones</Term> de ayuda, del principio del fichero:

`conProblema` dice que el error va como `application/problem+json`. `cuerpo` describe un <Term id="request-body">cuerpo</Term> JSON obligatorio. Así lo usa la ruta que crea un producto:

<ProjectCode file="tienda-api/14-openapi/src/contrato.ts" region="crear-producto" />

- **`security`** anuncia en el documento que la ruta pide un token. Lo comprueba `soloAdmin`, que **`middleware`** pone delante, antes de validar el cuerpo.
- **`headers: conLocation`:** el `201` lleva la cabecera `Location`, y el contrato lo dice.

### OpenAPIHono valida y apunta cada ruta

En `src/v2.ts`, la versión 2 deja de ser un `Hono` y pasa a ser un `OpenAPIHono`:

<ProjectCode file="tienda-api/14-openapi/src/v2.ts" region="crear-v2" />

- **`OpenAPIHono`** es un `Hono` que además apunta cada ruta en el documento.
- **`defaultHook`** es lo que responde si la petición no cumple el esquema. `siNoEsValido` es la función que antes iba dentro de `validar`, ahora con nombre, en `src/middleware/validar.ts`. Sin ella, `OpenAPIHono` respondería un `400` con el error de Zod entero; con ella, el `422` de siempre.
- **`registerComponent(…)`** dice cómo se manda el token, `Authorization: Bearer <token>` ([lección 4 de la Fase 2](/fase-2/cabeceras-http/)): es el `Bearer` del `security` de antes.

Y cada ruta pasa de `v2.get(…)` a `v2.openapi(…)`:

<ProjectCode file="tienda-api/14-openapi/src/v2.ts" region="ver-producto" />

`v2.openapi(contrato.verProducto, …)` registra la ruta, valida la petición con el contrato y la apunta en el documento. La función es la de antes, salvo que `c.json(producto, 200)` lleva el código. Hace falta para lo que viene.

### TypeScript comprueba que el código cumple el contrato

`@hono/zod-openapi` le da a TypeScript el contrato de cada ruta. Si la función devuelve un código que no está en `responses`, `npm run check` falla. Lo provocarás en «Pruébalo», quitando el `404` del contrato de `verProducto`. La última línea del error:

```
Type '404' is not assignable to type '422'.
```

TypeScript busca en el contrato un código que encaje con el `404` de `problemaHttp`, y no lo hay. Un `c.json(producto)` sin código también falla, y un producto sin `precioCentimos` no compila. **Lo que el contrato promete, el código no puede olvidarlo.**

### Lo que el contrato no comprueba

Hay dos agujeros:

- **Zod no valida las respuestas,** solo lo que entra. Lo que sale solo lo revisa TypeScript, antes de ejecutar.
- **A TypeScript no le importa un campo de más.** Un producto con un campo extra, como lo que le costó a la tienda, compila, y llega al <Term id="client">cliente</Term> sin que el contrato lo diga.

Los cierran las pruebas que miran las respuestas de verdad, como las del proyecto, que comparan el producto entero.

### Code-first o contract-first

La otra manera es ***contract-first*** («primero el contrato»): se escribe el documento, se acuerda con quien va a usar la API y después se programa.

| | Code-first | Contract-first |
|---|---|---|
| Qué se escribe primero | El código; el contrato sale de él | El contrato; el código lo cumple |
| A favor | Una sola fuente: lo que entra no puede desviarse | Los clientes empiezan antes, y el diseño se discute sin código |
| En contra | El diseño se decide programando | Contrato y código pueden separarse si nada los compara |
| Encaja cuando | La API ya existe y la hace un solo equipo | Varios equipos empiezan a la vez |

La tienda ya tenía su API: code-first encaja.

### Lo que se genera con un contrato

Como lo leen los programas, el contrato sirve para más que una página:

- **Clientes:** `openapi-typescript` saca sus tipos de TypeScript, y OpenAPI Generator escribe clientes en decenas de lenguajes.
- **Servidores de mentira** (*mocks*): Prism responde lo que dice el contrato antes de que exista la API.
- **Pruebas de contrato:** Schemathesis envía cientos de peticiones generadas y avisa si una respuesta no cumple su esquema. Cierra el primero de los dos agujeros de antes.

<SelfCheck question="Reto: la empresa de reparto quiere saber qué códigos puede responder la cancelación de un pedido, y qué significa cada uno. Averígualo sin abrir el código, solo con el contrato y jq.">

Las respuestas de `POST /pedidos/{id}/cancelacion` están en `paths`, bajo `post`. `keys` da sus códigos, y `.description`, lo que significa uno:

```sh
curl -s localhost:3000/v2/openapi.json | jq '.paths["/pedidos/{id}/cancelacion"].post.responses | keys'
curl -s localhost:3000/v2/openapi.json | jq -r '.paths["/pedidos/{id}/cancelacion"].post.responses["409"].description'
```

```
[
  "200",
  "404",
  "409",
  "422"
]
El pedido ya está enviado
```

`200` si se cancela, `404` si el pedido no existe, `422` si el id no es un número y `409` si ya ha salido. `-r` saca el texto sin comillas.

</SelfCheck>

## Ya lo has visto

- **Las APIs grandes publican su contrato.** GitHub, en [github/rest-api-description](https://github.com/github/rest-api-description), y Stripe, en [stripe/openapi](https://github.com/stripe/openapi).
- **Una dirección `/swagger` o `/api-docs`** con una página llena de rutas de colores: Swagger UI leyendo un documento OpenAPI.
- **Postman, Insomnia y Bruno**, programas para probar APIs, importan un documento OpenAPI y crean todas sus peticiones de una vez.

## Errores comunes

- **Escribir la documentación aparte del código.** Se queda vieja sin que nadie lo note, como el README del principio.
- **Olvidar `required: true` en el cuerpo.** Sin él, una petición sin cuerpo no se valida: quitándolo de la tienda, un `PATCH /v2/pedidos/25` sin cuerpo responde `{"id":25,"productoId":2,"estado":"pendiente"}`. El pedido se ha quedado sin `cantidad`.
- **Un parámetro con `z.coerce` sin su `.openapi()`.** `z.coerce` acepta cualquier cosa, y el documento no sabe de qué tipo es. Sin `.openapi({ type: 'integer', param: { required: true } })`, el `id` sale como `"type": ["integer", "null"]` y `"required": false`.
- **Confundir las versiones.** Un `swagger.json` con `"swagger": "2.0"` es del formato antiguo: mira qué versión acepta una herramienta antes de dársela.

## Resumen

- OpenAPI es un formato estándar para describir una API: rutas, parámetros, cuerpos y respuestas, también las de error. Swagger fue su nombre hasta 2016, y hoy es una marca de herramientas.
- El documento es el contrato de la API: lo leen personas, en páginas como `/docs`, y programas, que generan clientes, servidores de mentira y pruebas.
- Code-first genera el contrato desde el código; contract-first lo escribe antes. La tienda lo genera desde los esquemas que validan, así que no se queda viejo.
- `npm run check` falla si una ruta responde un código o una forma que su contrato no tiene. Lo que sale no se comprueba al ejecutar, ni un campo de más: para eso, las pruebas.
