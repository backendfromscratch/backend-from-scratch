## Phase 5: the database

From folder `18-modeling`, the project uses PostgreSQL 18 (the server keeps its data there from `19-postgres`), and the tests need it too: the introduction to Phase 5 explains how to install it and how to create the `shop` user with its two databases, `shop` (yours) and `shop_test` (the tests' one, which they empty and fill again every time). The server and the scripts find the database in the `DATABASE_URL` variable: copy `.env.example` as `.env` and put in your password. The tests use the one in `test/.env`.

```sh
npm run db:create    # folders 18 and 19: creates the tables with the sample data (drops the ones there were)
npm run db:migrate   # from 20: applies the missing migrations
npm run db:seed      # from 20: the sample data, into an empty database; from 24, also the
                     # practice accounts, even if the database already has data
```

## Phase 7: with Docker

From folder `32-dockerfile`, the project brings a `Dockerfile` to build the API's image, and from `34-compose`, a `compose.yaml` that starts the whole shop: the API, PostgreSQL 18 and Redis 8, each in its own container. You need Docker: the introduction to Phase 7 explains how to install it. The ports are published only on `127.0.0.1`, so only your computer reaches them.

**Without Docker**, everything stays as in the earlier phases: Node 26 and PostgreSQL on your computer, `npm run db:migrate`, `npm run db:seed` and `npm start`. Without `REDIS_URL`, the attempt limits are kept in the server's memory.

**With Docker** (from `34-compose`), copy `.env.example` as `.env`, generate its secrets as the file says and put a new password in `POSTGRES_PASSWORD` (`openssl rand -hex 24`). Then:

```sh
docker compose up --build                  # builds the image and starts everything: the API, on 3000 or 3001
docker compose up --build --scale api=2    # two copies of the API (3000 and 3001) that share Redis
docker compose down                        # stops it; with -v, it deletes the data too
docker compose port api 3000               # which port of your computer the API got
```

Before starting the API, Compose applies the migrations and loads the practice data (the `migrate` service). That database is a different one, in a Docker volume, not the one on your computer, and it doesn't clash with it: it publishes no port. Signing in with the practice provider (`npm run provider`) doesn't work from the containers, because inside a container `localhost` is the container itself; with email and password, it does.

Image size (`CONTENT SIZE` from `docker image ls`, on 2026-10-14): 145 MB for `32-dockerfile`'s, with one stage; 92 MB for `33-small-image`'s, multi-stage on `node:26-slim`. With the same final stage on `node:26-alpine` it would be 74 MB, and on distroless (`gcr.io/distroless/nodejs26-debian13`), 66 MB.

The Redis store's tests (`test/redis-store.test.ts`, from `34-compose`) need a Redis. Without one they're skipped, and the rest pass. To test them, start one and remove the `#` from `REDIS_URL_TESTS` in `test/.env`:

```sh
docker run --rm -d --name redis-tests -p 127.0.0.1:6379:6379 redis:8
```

## Phase 8: on a server

`35-production` brings what changes when you put the shop on a server, next to `compose.yaml` (which stays the one for your computer):

- `compose.production.yaml`: the same shop, with `restart: unless-stopped`, the image `${IMAGE:-shop-api}` (the one `--build` builds, or the published one if you set `IMAGE`), the network's subnet pinned (`172.18.0.0/16`) and no practice accounts: `migrate` only loads the sample products (`--no-accounts`). The API is still published only on `127.0.0.1`.
- `.env.production.example`: a server's configuration. Copy it as `.env` **on the server**, generate the secrets there (`openssl rand -base64 32` and `openssl rand -hex 24`) and change `shop.example` to your name. The four `OIDC_*` stay commented out: without an identity provider, the shop works with email and password.
- `nginx/shop.conf`: nginx in front, with port 80 redirecting to 443, the `X-Forwarded-For` and `X-Forwarded-Proto` headers, the two copies of the API in an `upstream`, and a `location` of its own for an order's events. It carries the instructions to install it. As it is, it uses your own certificate authority's certificate (`/etc/ssl/shop/`, the free path); with Let's Encrypt, `certbot --nginx` replaces those two lines.
- `deployment/backup.sh`, with `shop-backup.service` and `shop-backup.timer`: a `pg_dump` every night at 03:30, in `backups/` (readable only by your user), kept for 7 days. Your user has to be in the `docker` group (it's equivalent to root: be careful) and change `User` and the paths in the `.service` if it isn't `ubuntu` and `/opt/shop`.

```sh
cp .env.production.example .env && chmod 600 .env    # and generate the secrets in .env
docker compose -f compose.production.yaml up -d --build
docker compose -f compose.production.yaml run --rm api node scripts/create-admin.ts you@email.com
deployment/backup.sh                                 # a backup now
```

`create-admin` creates your admin account with a long random password, shows it just once and keeps only its hash. With `TRUSTED_PROXY`, the API reads the visitor's IP from `X-Forwarded-For` only when the request comes from that address (the gateway of Compose's network: `docker network inspect shop_default`). Only one proxy hop is supported (the last `X-Forwarded-For` entry): with another proxy in front, like Cloudflare's, the limiter would see that proxy's addresses.

`36-deployment` publishes the image and deploys it without GitHub having to get into your server:

- `.github/workflows/publish.yml`: on every pull request it installs, type-checks and runs the tests with a PostgreSQL 18; on every push to `main` it also builds the image for `linux/amd64` and `linux/arm64` and publishes it to `ghcr.io/<your-user>/shop-api` with the tags `sha-<7 letters of the commit>` and `main`. GitHub only runs the workflows at the root of a repository: here, inside the step's folder, it does nothing. Copy the step's contents to the root of your own repository and it switches on.
- `deployment/deploy.sh`, with `shop-deploy.service` and `shop-deploy.timer`: every two minutes the server asks whether `IMAGE` (in `.env`, for example `ghcr.io/your-user/shop-api:main`) points to a new image. If not, it does nothing and writes nothing. If so: backup, migrations, new API, and it waits for `/health`; if it never gets healthy, it goes back to the previous image (kept as `:previous`) and ends with an error. One deployment at a time (`flock`). It installs like the backup, with the same user.

```sh
# on the server: follow the published image (put yours)
echo 'IMAGE=ghcr.io/your-user/shop-api:main' >> .env
docker compose -f compose.production.yaml pull api       # downloads the published one (build isn't used)
sudo cp deployment/shop-deploy.service deployment/shop-deploy.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now shop-deploy.timer
journalctl -u shop-deploy                                # what it has done
```

The first time the image is published, ghcr.io creates it **private**: on its package page (Package settings → Change visibility) make it public, or the server won't be able to download it without credentials. An image the script judged bad isn't retried by itself (every attempt is seconds without an API): if the fault was in the environment and not in the image (a badly written `.env`, say), fix it and delete `.deploy-failed` so it tries again.

Going back changes the code, not the data: that's why the script makes a backup before migrating.

## Phase 9: the queue, the worker, Mailpit and the cache

From `37-queue`, what a request doesn't have to wait for goes to a job queue in Redis (with BullMQ): when an order becomes paid, one notification for each URL of the delivery company (with the `X-Event-Id` header, the same on every retry) and the confirmation email for whoever placed it. Another process does them, the worker (`scripts/worker.ts`): the same code and the same image as the API, with another command. A job that fails is tried again, up to five attempts in all, waiting 1, 2, 4 and 8 seconds between one and the next. Redis now keeps the queue on disk (`--appendonly yes`, in the `redis` volume).

With Docker, `docker compose up --build` also starts the worker and Mailpit, a practice mail server: it receives the shop's emails, sends them to nobody and shows them at `http://localhost:8025`.

```sh
docker compose up --build --wait                  # everything, in the background
npm run gateway -- 21                             # the payment gateway notifies: order 21, paid
curl -s http://localhost:8025/api/v1/messages     # the email, in Mailpit's inbox (or in the browser)
docker compose logs worker                        # what the worker has done
docker compose stop worker                        # without a worker, the jobs wait in the queue...
docker compose start worker                       # ...and go out as soon as it's back
```

`npm run gateway` reads `WEBHOOK_SECRET` from your `.env`, the same one the API uses in Compose, and calls the API on port 3000 (another one, with `PORT=3001 npm run gateway -- 21`).

**Without Docker**, the shop still works without Redis: the jobs are done in the API's own process, as soon as they arrive and without retries, as until Phase 8. With Redis on your computer (`REDIS_URL` in `.env`), start the worker in another terminal with `npm run worker`. Without `SMTP_URL`, no email goes out: the log says which one would have. On a server, `SMTP_URL` is optional (`.env.production.example` explains what an email provider asks for), and `deploy.sh` updates the worker together with the API.

Load tests are done with autocannon (`npm run load`), with the shop running:

```sh
npm run load -- -d 10 http://127.0.0.1:3000/v2/products   # 10 seconds of requests, and the results table
```

The queue's tests (`test/queue.test.ts`) need Redis, like the store's: without `REDIS_URL_TESTS`, the ones that use it are skipped.

From `38-cache`, the catalogue (the list of products and each product) is kept for a minute in a cache, a second Redis (the `cache` service, with `CACHE_URL`): at most 64 MB, it deletes the least-read keys when it fills up and keeps nothing on disk, the opposite of the queue's. Creating, changing (`PATCH /v2/products/{id}`, new in this step: the name or the price, admin only) or deleting a product, and placing an order, changing its quantity and cancelling it (all three change the stock) delete from the cache what has changed; buying still checks the stock in PostgreSQL. Without `CACHE_URL`, or with the cache down or stuck (no command waits for it longer than 200 ms), everything is read from PostgreSQL, as before. To look inside: `docker compose exec cache redis-cli keys '*'`. Its tests (`test/cache.test.ts`) use database 2 of the Redis in `REDIS_URL_TESTS`.

From `39-scaling`, the API can run as several copies (`docker compose up --scale api=2`, each one on its own port, 3000 or 3001: `docker compose port --index 1 api 3000`). The only thing that lived in a copy's memory, the notices of the changes in the orders that `GET /v2/orders/{id}/events` follows, now goes through Redis (pub/sub, on the `shop:orders` channel, `src/order-events.ts`): an order cancelled through one copy reaches whoever follows it on the other. Each copy subscribes to the channel the first time it needs it. If Redis is cut, whoever follows an order gets no changes; when it comes back, the API closes those streams, and the browser (`EventSource`) connects again and gets the current status. Without `REDIS_URL`, they stay in the process's memory, as before. To watch them go by: `docker compose exec redis redis-cli subscribe shop:orders`. Its tests (`test/scaling.test.ts`) use the Redis in `REDIS_URL_TESTS`, with a channel of their own on each run.

From `40-zero-downtime`, the server runs two copies of the API, `api-a` (port 3000) and `api-b` (3001), the two ports nginx already had in its `upstream`, so nginx doesn't need touching (in `nginx/shop.conf` only the `upstream` comment changes). `deploy.sh` changes them one at a time: `api-b` with the new image and, when Docker considers it healthy, 10 seconds of margin for nginx and then `api-a`; at the end, the worker, and `docker image prune` deletes the images with no tag (the new one and the previous one stay). If a new copy never gets healthy (it stops waiting as soon as Docker considers it `unhealthy`), the ones it has already changed go back to the previous image, also one at a time. The first deployment of this step removes the single copy of the earlier steps (the `api` service, which will be on 3000 or on 3001) once the new copy on the other port is already answering: if the old one is on 3001, it starts with `api-a`. On receiving `SIGTERM`, the API shuts down without cutting anyone off (`src/shutdown.ts`): it stops accepting connections, finishes the requests it has half done, closes the event streams and the WebSockets (their clients connect again, to the other copy), and then PostgreSQL and Redis, all within 8 seconds at most; meanwhile, `/health` answers 503. nginx repeats on the other copy what the one shutting down refuses, even if it's a POST, as long as Docker doesn't put its `docker-proxy` in front of the published ports: with it (it comes turned on), the port accepts the connection and cuts it, and nginx doesn't repeat a POST it already sent (502). So on the server, once only, before this step's first deployment, it is turned off in Docker's configuration, `/etc/docker/daemon.json`. If you followed Phase 8, that file already exists, with the log limits from its lesson 3, which must not be lost; look at it first:

```sh
cat /etc/docker/daemon.json
```

If it has those limits and nothing else, or doesn't exist ("No such file or directory"), write the whole file: those limits plus the new key:

```sh
sudo tee /etc/docker/daemon.json <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "userland-proxy": false
}
EOF
```

If it has other settings, open it with `sudo nano /etc/docker/daemon.json` and add `"userland-proxy": false` inside its braces without deleting anything, with a comma after the setting before it. Then:

```sh
sudo systemctl restart docker   # stops and starts every container, once
```

If Docker doesn't start, the JSON has a mistake: `sudo journalctl -u docker -n 20` tells you which.

The `127.0.0.1` ports keep serving on the server itself and stay closed from outside, and the API still sees nginx arriving from `172.18.0.1` (`TRUSTED_PROXY` doesn't change). As long as you haven't done it, `deploy.sh` warns about it on every deployment. Its tests: `test/shutdown.test.ts`, and `test/deployment-files.test.ts`, which runs `deploy.sh` with a fake `docker` (`test/docker-fake.sh`).

From `41-events`, paying an order no longer puts anything in the queue: in a single transaction, it writes down the gateway's event, turns the order into paid and saves its jobs (the notifications and the email) in the `outbox_events` table (migration `011`). If the API goes down right after, or the queue's Redis doesn't answer, the jobs are already in PostgreSQL. The worker relays them (`src/outbox.ts`): on start and every second, it takes the ones that haven't been sent (`FOR UPDATE SKIP LOCKED`: two workers never take the same one), puts them in the queue and writes down when (`sent_at`); if Redis fails or doesn't answer, it writes nothing down, and tries again a second later; if it is slow, it writes down the ones that arrived within 2 seconds and leaves the rest for the next round. A job can reach the queue twice (the worker goes down after enqueuing it and before writing it down), so each one carries its id (`email-<order>`; `notice-<payment id>-<notification>`), and BullMQ doesn't write down the same one twice. Without Redis, the API itself relays them, and each job is done in that process, as before. To look at the table: `docker compose exec db psql -U shop -c 'SELECT id, type, created_at, sent_at FROM outbox_events'`. Its tests: `test/events.test.ts`.

## Phase 10: tests, contract, traces, metrics and alerts

From `42-tests`, there are two more scripts. `npm run e2e` tests the real shop, the Compose one, with nothing but `fetch`: it signs in with Carmen's practice account (`carmen@example.com`, the one the development data loads), places an order, pays it with the gateway (`npm run gateway`), waits for the email to reach Mailpit and cancels the order, to give what it bought back to the stock. It needs the shop running (`docker compose up -d --build --wait`) and reads `BASE_URL` (by default `http://127.0.0.1:3000`; if your API ended up on 3001, `BASE_URL=http://127.0.0.1:3001 npm run e2e`) and `MAILPIT_URL` (by default `http://127.0.0.1:8025`). Its tests are in `test/e2e/`. `npm run coverage` runs `npm test` with Node's coverage option and shows which lines of `src/` no test executes. `npm test` only runs `test/*.test.ts`: without that, Node would also run `test/e2e/`, which fails with no shop running. The new unit tests of the signature are in `test/signature.test.ts`.

From `43-contract`, the API checks that its responses have the shape its contract promises (`/v2/openapi.json`). `src/contract-responses.ts` compiles each response of the document with Ajv and two things use it: the tests (`test/contract.ts`, `matchesContract(res, 'get', '/orders/{id}')`, with one case per route in `test/contract.test.ts`) and a middleware on `/v2`, which `VALIDATE_RESPONSES` controls: `no` (nothing, the default), `log` (a `warn` "response outside the contract" with the `requestId`, the route, the status and the failures, without the body, which may carry personal data) or `fail` (a 500 instead). `test/.env` uses `fail`: every test, besides its own job, is a contract test. `contract.json` is the published contract, kept in Git: if the document changes, `npm test` fails until you regenerate it with `npm run contract` and the change shows in the diff. The middleware is mounted first after the log, so it also sees what the middleware answer before reaching the route (the CSRF check, the session). It doesn't look at what has no JSON body (a 204, the event stream; a `HEAD` is validated as its `GET`), nor at the 405s of a method the route doesn't have, nor at any 5xx: a server failure is already logged by `app.onError`, and it isn't that the response breaks the contract. While writing the contract tests, reading the code, gaps in the contract appeared: it didn't say that the routes with a body answer 400 (badly written JSON) and 415 (without `Content-Type: application/json`), nor that `POST /v2/accounts`, `POST /v2/session`, `DELETE /v2/session` and `POST /v2/webhooks/payments` can answer 403 (the CSRF check, with another site's cookie). The 400s and 415s were found by the validation when running all the tests with `fail`; the 403s weren't: they were seen by reading the code, and there is a test for each one. `npm run load -- -d 10 http://127.0.0.1:3000/v2/products` costs, with `log` or `fail`, between 1% and 11% of requests per second, about 5% on average, depending on the run (in our tests, with 10 connections): measure it on your machine before turning it on in production.

From `44-tracing`, the API and the worker leave traces with OpenTelemetry: `src/instrumentation.ts` is loaded before the shop (`node --import ./src/instrumentation.ts`, in `npm start`, `npm run dev`, `npm run worker`, the `Dockerfile`'s `CMD` and the worker's command in both Compose files) and, only if there is an `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, sends the spans over OTLP to that URL; without it nothing starts, and the shop works as before. `compose.yaml` doesn't change: `docker compose -f compose.yaml -f compose.observability.yaml up -d --build --wait` adds Jaeger to it (the web page at `http://localhost:16686`; the traces are kept in memory) and gives the API and the worker the URL and their name (`OTEL_SERVICE_NAME`: `shop-api`, `shop-worker`). To avoid typing both files every time, put `COMPOSE_FILE=compose.yaml:compose.observability.yaml` in your `.env`. Each request has a single server span, `@hono/otel`'s, with the route's template (`GET /v2/orders/:id`) and the `requestId` as `shop.request_id`: in Jaeger, search by the tag `shop.request_id=<the response's X-Request-Id>`. Inside, a span for each query to PostgreSQL and each command to Redis (only inside a request or a job: the relayer's queries every second don't make loose traces), and the notices to the delivery company (`node:http`). The log lines carry `trace_id` and `span_id`. A payment is a single trace, from the API to the worker: the outgoing event saves the trace it was created in (the `context` column, migration `012`, with the W3C standard's `traceparent`), the relayer writes the job down in the queue inside that trace and BullMQ (`bullmq-otel`) carries it to the worker. The tests, with the spans in memory, are in `test/instrumentation.test.ts`. The traces need Node 24.11.1 or later (`module.registerHooks`; `engines` says so). A trace doesn't carry what the log doesn't: `url.full` goes without the query (the provider's return brings the code and the `state`), and the Redis spans only say the command and what the key is for (`ZADD limits:?`), without the email or the IP of the limits. In production there is no Jaeger: if you have somewhere to send the traces, put its URL in the server's `.env` (`.env.production.example`).

From `45-metrics`, the shop also measures. A metric is a number measured over time; Prometheus keeps them and Grafana draws them. `compose.observability.yaml` adds the two services: Prometheus at `http://localhost:9090` (with `--web.enable-otlp-receiver`, to receive over OTLP what the shop sends, and the metrics in a volume) and Grafana at `http://localhost:3100`, **with no password**: it signs in as an administrator (`GF_AUTH_ANONYMOUS_ENABLED`), and that is why it is only published on `127.0.0.1`; on a server, never like this. The API and the worker send their metrics to `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` (the whole URL, `http://prometheus:9090/api/v1/otlp/v1/metrics`), every 5 seconds; without that variable nothing starts (`src/instrumentation.ts`). Grafana is born provisioned, from files in `observability/grafana/`: the sources (Prometheus, in `provisioning/datasources/`) and the "The shop" dashboard (`dashboards/shop.json`), with the three RED ones (requests per second, 5xx errors and p99 duration, by route template, with `@hono/otel`'s metric, `http_server_request_duration_seconds`), the paid orders per minute, the jobs waiting in the queue and the responses outside the contract. The shop's own metrics are in `src/metrics.ts`: `shop.orders.paid` (v2.ts, only when the payment really changes the status), `shop.responses.outside_contract` (with the contract's route) and the gauge `shop.queue.waiting`, which is read from the queue with a maximum time; if Redis doesn't answer, it observes nothing, but the SDK keeps sending the last value it saw (cumulative temporality): the chart doesn't break, it goes flat. Be careful with attributes: each different combination is a series forever, so they only carry route templates and status codes, never a URL, an id or an email. With the shop running, `npm run load -- -c 10 -d 30 http://localhost:3000/v2/products` and watch how the dashboard moves. The tests, with the metrics in memory, are in `test/metrics.test.ts`. The alerts arrive in `46`.

From `46-alerts`, the shop says whether it is fine in three ways. `GET /health` doesn't change (the `HEALTHCHECK` and `deploy.sh` use it: PostgreSQL answers and the copy isn't shutting down). `GET /health/live` (liveness) only says that the process answers, without asking anybody: if it looked at the database, a PostgreSQL outage would make all the copies restart, and that fixes nothing. `GET /health/ready` (readiness; while shutting down, 503 without asking anybody) asks PostgreSQL, the queue's Redis and the cache's, each with 500 ms at most (`src/health.ts`), and answers `{ status, checks: { db, queue, cache } }` with `ok`, `failing` or `not-configured` in each one: 503 if the database or the queue fails; the cache is reported, but doesn't count. It fixes the three failures Phase 9 left: the attempt limits wait for Redis 200 ms at most and, if it doesn't answer, take it as down (they ask it no more than once a second, so commands don't pile up) and each one does what its `onFailure` says (`src/rate-limits.ts`): the two sign-in ones close (503 "The attempts can't be checked", with `Retry-After: 5`) and the account-creation one opens (it lets through, with a `warn` in the log at most once a second); `src/db.ts` listens to the `'error'` of borrowed connections, so a PostgreSQL outage in the middle of a transaction no longer stops the process; and `deploy.sh` only counts a copy as healthy if it sees it healthy twice, 5 seconds apart and with the same `RestartCount` (and it still waits 60 seconds at most). There is one more metric, `shop.outbox.age` (in Prometheus, `shop_outbox_age_seconds`): the seconds the oldest unsent outgoing event has been waiting, read from PostgreSQL (not from Redis, so it keeps working when Redis is the one failing). Grafana is born with four alert rules (`observability/grafana/provisioning/alerting/rules.yaml`): more than 5% of 5xx responses on `/v2` for 2 minutes, a p99 on `/v2` of more than 0.5 s for 2 minutes, an outgoing event unsent for more than 2 minutes and, so that a down API doesn't silence the other three, an API that has gone more than a minute without sending metrics (this one also alerts with no data); the thresholds, measured with `npm run traffic` (the reasoning, in the file). They warn by email (`contact.yaml` and `policy.yaml`): Grafana sends to Mailpit over SMTP (`GF_SMTP_*`, in `compose.observability.yaml`), and they arrive at `http://localhost:8025` (Mailpit now keeps 5000 emails, `MP_MAX_MESSAGES` in `compose.yaml`: with the earlier 500, the practice traffic deleted the alerts' emails in a few minutes). `npm run traffic` is a practice customer who buys nonstop until Ctrl + C: she signs in (and closes that session at once: she always buys with the first one), buys a mug, pays it with the gateway and cancels the order (so the stock doesn't run out), and writes one line per round with the codes. With it running, `docker compose pause redis` freezes the queue's Redis: payments keep answering, sign-ins give 503 without hanging (in about 200 ms: at that pace, each one is the probe of its second) and the outgoing events stop going out, and two alerts arrive; with `docker compose unpause redis`, the emails that were waiting go out. `docs/postmortem.md` is the template for a blameless postmortem. The new tests are in `test/health.test.ts` and `test/limits-failures.test.ts`.

## Phase 11: the assistant

From `47-model`, the shop has an assistant: `POST /v2/assistant`, only for customers with their session, receives the conversation (`{ "messages": [{ "role": "user", "text": "…" }] }`, at most 20 messages of 2000 characters), passes it to a Claude model with the instructions in `src/assistant/instructions.md` and answers `{ text, refused, usage: { input, output } }`. It needs a Claude API key (created in the Claude Console, `platform.claude.com`; set a monthly spend limit first) in your `.env` as `ANTHROPIC_API_KEY`: `.env` doesn't go to Git, and the key never goes in the code or in the frontend, because whoever has it spends on your account. Without it (empty, as in `.env.example` and `.env.production.example`), the shop works the same and the assistant answers 503 `assistant-not-configured`. The model is `claude-haiku-5-5`, with `low` effort (`MODEL` and `EFFORT` change them). If the API answers 429 or 529, or doesn't answer in time, the customer gets a 503 `assistant-not-available` with `Retry-After`; if it rejects the shop's request (400, 401, 404), a 500, with the reason in the log; if the model refuses to answer, a 200 with a fixed sentence and `refused: true`. Every question costs the shop money, so it has its limits (`src/rate-limits.ts`, in Redis with Compose, like the sign-in ones): each customer can ask 20 every 10 minutes, and 60 fit from one IP, whoever's they are (opening several accounts doesn't get around them). Past that, a 429 `too-many-attempts` with `Retry-After`, without calling the model; the `RateLimit` headers say how many are left. If Redis doesn't answer within 200 ms, these limits close, like the sign-in ones: a 503 `attempts-unchecked` with `Retry-After: 5`, because questions with no limit are exactly the spending they exist to stop. The times: the SDK repeats what's passing twice (`MODEL_RETRIES`), waits for each attempt 15 seconds at most (`MODEL_TIMEOUT_MS`) and for the whole answer, with its attempts and the waits between them, 50 (`ASSISTANT_TIMEOUT_MS`). Three attempts of 15 s and the SDK's waits add up to 46.5 s; the 50-second cap also cuts the wait the API asks for in a `retry-after`, which the SDK would respect in full however long it was (its only limit, read in the SDK 1.8.0 code: about 24 days, the longest a Node timer waits). That way the shop always answers before the 60 seconds nginx waits for the API (`proxy_read_timeout`), with its own 503 and not with a 504 from nginx. If the customer leaves before getting the answer (closes the tab, Ctrl + C in curl), the shop stops waiting for it: the call to the model also gets their request's signal (`c.req.raw.signal`, which `@hono/node-server` aborts when the connection closes), and the log says so: "the customer left: cancelling the call to the model". The tests never call the real model: `ANTHROPIC_BASE_URL` points at a fake model (`test/fake-model.ts`), a small server that answers like the API whatever each test asks it to and says how each response ended (`finished`: `'whole'` or `'cut'`), and `test/fake-model.test.ts` checks with the SDK itself that it speaks like it. Like Claude Haiku 5.5, which thinks before answering and doesn't show what it thinks, every message of it starts with a `thinking` block with empty text and a `signature`. The assistant's tests are in `test/assistant.test.ts` (the customer leaving, with the shop listening on a free port; and the limits) and `test/optional-assistant.test.ts`; the closed limit, in `test/limits-failures.test.ts`.

To practise with no key and without spending, the tests' fake model also works on its own (`scripts/fake-model.ts`): it answers every request with the scenario you choose, `normal` (a short answer, which repeats your last question), `429` (too many requests, with `retry-after: 3`: the SDK repeats twice, waiting that long, and the shop answers 503 with `Retry-After: 3`), `529` (overloaded, with no `retry-after`: the SDK repeats with its short waits and the shop answers 503 with `Retry-After: 30`) or `slow` (a long answer, a piece every 250 ms: streamed, it arrives little by little and, in JSON, whole, about 9 seconds later), and it leaves a line for each request it gets: the model, whether it's streamed, how many messages it carries and what it answers. Its answers and its tokens are made up. With Docker Compose it's the `fake-model` service, which only starts with the `practice` profile, on the shop's network and publishing no port: the API finds it by its name, so it works the same with Docker Desktop and with Colima. It builds nothing: it uses the `Dockerfile`'s Node image, with the files it needs from the project, read-only.

```sh
docker compose --profile practice up -d fake-model                 # the normal scenario
SCENARIO=429 docker compose --profile practice up -d fake-model    # another: 429, 529, slow…
docker compose --profile practice logs -f fake-model               # what it gets
```

Then, in your `.env`, any key in `ANTHROPIC_API_KEY` (with no key, the assistant answers 503 without asking anyone) and `ANTHROPIC_BASE_URL=http://fake-model:4100` (it's in `.env.example`, commented out), and `docker compose up -d --wait`, so the API and the worker read them. To go back to the real API: your key, `ANTHROPIC_BASE_URL` commented out, `docker compose up -d --wait` again, and `docker compose --profile practice rm -sf fake-model`. Careful: without the profile, `docker compose down` doesn't stop it (nor remove the shop's network); with it running, `docker compose --profile practice down`. Without Docker, `npm run fake-model` (or `npm run fake-model -- 429`, or `SCENARIO=429 npm run fake-model`) starts it at `http://127.0.0.1:4100`, for the shop of `npm run dev`. In the tests, a turn can be slow (`pause`, in `message()` and `text()`): streamed, a pause between one event and the next; in JSON, the whole answer arrives when the stream would have ended. `test/fake-model.test.ts` starts the real script, with the 429 scenario, on a free port.

From `48-streaming`, the assistant also answers streamed, piece by piece, as the model writes. It's the same route: with `Accept: text/event-stream`, `POST /v2/assistant` answers a stream of Server-Sent Events; without that header (or with `application/json`, or with the `*/*` curl sends), the whole answer in JSON, as before. The stream carries the shop's events, not the model's (the translation is in `src/assistant/events.ts`): `text` (`{ "text": "…" }`, one more piece; together, in order, they are the answer), `end` when it finishes (the same answer as in JSON, `{ text, refused, usage }`; if `refused` is `true`, its text, the fixed sentence, replaces what arrived before) and, if something fails halfway, `error` (a Problem Details) instead of `end`; after either of them, the stream closes. What fails before the model's first event (a 429, a 529, the model not answering) is the usual 503, in JSON and with `Retry-After`; what fails after it (an `error` event from the API or a cut connection) can't change the status code any more, and arrives as an `error` event. If the customer leaves halfway, an `AbortController` cancels the call to the model; if they leave before the first event, their request's signal does, as in JSON; and the log says so once: "the customer left: cancelling the call to the model". To see it, with the shop running and your key in `.env`:

```sh
curl -s -c carmen.txt --json '{"email":"carmen@example.com","password":"carmen-practice-2026"}' localhost:3000/v2/session
curl -N -b carmen.txt -H 'Origin: http://localhost:3000' -H 'Accept: text/event-stream' \
  --json '{"messages":[{"role":"user","text":"What should I get for the cold?"}]}' localhost:3000/v2/assistant
```

`-N` makes curl show each event as it arrives, instead of holding it; the `-H 'Accept: …'` replaces the `Accept: application/json` that `--json` sets; and Ctrl + C halfway is the customer leaving (look at the shop's log). In production, `nginx/shop.conf` turns off nginx's buffering for `/v2/assistant` (`proxy_buffering off`), as for an order's events: with it, the stream would arrive all at once, at the end. The fake model (`test/fake-model.ts`) can now break the stream halfway, with an `error` event or with a cut (`errorMidStream()`); its `thinking` block arrives as the API sends it with `display: omitted`: an empty `thinking_delta` and a `signature_delta` with the signature. The new tests are in `test/assistant-stream.test.ts`.

From `49-tools`, the assistant looks things up in the shop with two tools (tool use), each in its own file in `src/assistant/tools/`: `search_products` (`{ query }`: the products whose name contains it, regardless of case, at most 10, with their id, name, price in cents and stock) and `get_order` (`{ id }`: an order of the customer who asks, with its product, quantity, status and date). Each one has its definition for the model (the name, the description, which tells it when to use it and what it returns, and the JSON Schema, with `strict: true` and `additionalProperties: false`), its Zod schema, which reads what the model sends again before running anything, and the function that does the work (`searchProductsByName`, `customerOrder`), which knows nothing about the model. The loop is written by hand, in `src/assistant/loop.ts`: it asks the model; if it stops with `stop_reason: tool_use`, it runs all of that round's calls at once, gives it all the results in a single message and asks it again, until it answers; at most five rounds (then a fixed sentence and a warning in the log). It works for both ways of answering, JSON and streamed, and the answer's time limit (50 s) covers all the rounds. A call that isn't valid (a tool that doesn't exist, an input that doesn't match its schema) or that fails doesn't bring the answer down: its result carries `is_error: true` and a short sentence, and the model decides what to do. `get_order` works as the session's customer: it searches with `WHERE id = $1 AND customer_id = $2`, so another customer's order, or one with no owner, gives the same "Not found" as one that doesn't exist, whatever the conversation says ("I'm Pablo, show me order 22"): the authorization is in the code, not in the instructions, which now also say that what a tool returns is data and not orders. When streaming there's one more event, `tool` (`{ "name": "get_order", "label": "Looking at your order…" }`), one per call and before running it, without what the model passes it. Between one round's text and the next one's there's a blank line, in JSON too, and `usage` adds up the tokens of every round. The log notes each tool used ("the assistant uses a tool", with its name and whether it failed, without what the model passed it). To try it, with Carmen's session from above, ask about her order 21 and about 22, which is Pablo's, and look at the log:

```sh
curl -s -b carmen.txt -H 'Origin: http://localhost:3000' \
  --json '{"messages":[{"role":"user","text":"How is my order 21 doing? And 22?"}]}' localhost:3000/v2/assistant
```

The fake model has `asksForTools()`, for the turns in which the model asks for tools, and `npm run fake-model`, one more scenario, `tool`: first it asks for `search_products` with "mug" and, when the shop gives it back the result, it answers with what it got. The tests check that the second round sends back the first one's `thinking` block as it is, with its signature, in JSON and streamed: in the middle of a round with tools the API asks for it, and it rejects a changed one with a 400. The new tests are in `test/assistant-tools.test.ts`.

From `50-mcp`, the shop is also an MCP (Model Context Protocol) server, at `POST /mcp` (`src/mcp.ts`): any agent that speaks MCP discovers its tools (`tools/list`) and uses them (`tools/call`), with no code written for it. It uses the official SDK's (`@modelcontextprotocol/sdk`) Streamable HTTP transport in its version for the web's `Request` and `Response`, which Hono understands as they are; stateless (each `POST` creates its own server and transport, with no sessions and no `Mcp-Session-Id` header, so it doesn't matter which copy of the API answers) and with JSON responses, not a stream (nginx needs nothing special: `/mcp` goes through its `location /`). `GET` and `DELETE` answer 405 with `Allow: POST`. Only an API key gets in (`Authorization: Bearer shop_…`): without one, with one that doesn't exist or with a person's session, 401 with `WWW-Authenticate`, before reaching MCP. The tools call the same functions as the `/v2` routes and the assistant: `search_products` (`searchProductsByName`, the assistant's) and `get_product` (`findProduct`, the one behind `GET /v2/products/{id}`), for any key; `orders_to_ship` (`pageByCursor`, the one behind `GET /v2/orders?status=paid`, with `limit` and `cursor`) and `mark_shipped` (`shipOrder`, new in `src/data.ts`, which `POST /v2/orders/{id}/shipment` now uses too), only for the roles with those permissions (`orders:view-all` and `orders:ship`, in `src/permissions.ts`): delivery and admin. Keys have one more role, `catalogue` (migration `013`), with no permission at all: the key of an agent that only browses the catalogue, like a price comparison site's. `npm run create-key` takes the role after the name (`delivery` if none is given). Each request's server only has the tools its key's role allows: with a `catalogue` key, `tools/list` shows two, and if the agent calls `mark_shipped` anyway, it gets `isError: true` ("MCP error -32602: Tool mark_shipped not found") and the order doesn't change. MCP isn't the authorization: the authorization is the key and its role. Each result is a text block with JSON, bounded (at most 10 products or 50 orders); what can't be done (a product that doesn't exist, an order that isn't paid) is `isError: true` with a sentence that says why, and if something breaks inside, the agent gets a short sentence and the log, the whole error. The log notes each use ("an agent uses a tool (MCP)", with the tool and the key's id). `/mcp` isn't in the OpenAPI contract (MCP describes itself, with `tools/list`) nor goes through `VALIDATE_RESPONSES`, which only looks at `/v2`. To try it with the Compose shop running, create a key of each role and ask by hand, as an agent would:

```sh
docker compose exec api node scripts/create-key.ts "Fast Delivery"
docker compose exec api node scripts/create-key.ts "Price Comparison" catalogue
KEY=shop_…   # the delivery one, as it was shown
curl -s localhost:3000/mcp -H "Authorization: Bearer $KEY" -H 'Accept: application/json, text/event-stream' \
  --json '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"orders_to_ship","arguments":{"limit":3}}}'
```

Streamable HTTP asks for the `Accept` with both types (without it, 406). With a real client: the MCP Inspector, which needs no model (`npx @modelcontextprotocol/inspector@2.15.0 --transport http --server-url http://localhost:3000/mcp --header "Authorization: Bearer $KEY"` opens its web page with the connection already set up; with `--cli` first and `--method tools/list`, or `--method tools/call --tool-name mark_shipped --tool-arg id=13`, it answers in the terminal; it needs Node 22.23.4, 24.22.1 or 26.12.1 or later), or Claude Code (`claude mcp add --transport http shop http://localhost:3000/mcp --header "Authorization: Bearer $KEY"`, and ask it which orders are waiting to be shipped). With the `catalogue` key instead of the delivery one, neither sees the orders' tools. The new tests are in `test/mcp.test.ts`, with the SDK's own client against the shop listening on a free port, and one that speaks the protocol by hand with `fetch` (`initialize`, `notifications/initialized`, `tools/list` and `tools/call`).

From `51-embeddings`, the shop searches by meaning: "something for the cold" finds the hoodie, the blanket and the scarf, even though they share no word with it. Each product now has a description and a vector (an embedding: 384 numbers that say what it's about), and PostgreSQL stores and compares them with pgvector. Both Compose files use the `pgvector/pgvector:0.8.7-pg18-trixie` image (PostgreSQL 18 with the extension already installed, pinned by its digest; the data in the volume from before works as it is), and migration `014` turns the extension on (`CREATE EXTENSION IF NOT EXISTS vector`), adds `products.description` (`text`) and `products.embedding` (`vector(384)`, both may be `NULL`) and an HNSW index (`USING hnsw (embedding vector_cosine_ops)`), with its drizzle-kit snapshot (`drizzle/0011_embeddings.sql`; the extension is the one thing drizzle-kit doesn't write). Turning the extension on is a superuser's job: in Compose the `shop` user is one; **without Docker**, install pgvector for your PostgreSQL (`brew install pgvector` on a Mac, `sudo apt install postgresql-18-pgvector` on Ubuntu) and turn it on once in each database, as a superuser: `psql -d shop -c "CREATE EXTENSION vector"` and the same with `shop_test` (on Linux, `sudo -u postgres psql …`). The tests no longer drop the `public` schema to empty their database, only its tables (`test/db.ts`), so the extension stays. The practice catalogue goes from 4 to 20 products, all with a description, in groups the search has to tell apart: warm clothes, coffee and kitchen things, summer things and gifts (the usual four keep their id, name and price). Since `npm run db:seed` only loads the products into a database with none, if you come with the previous step's Compose volume, `docker compose down -v` before starting this one. In `/v2`, products have a `description` (or `null`), and `POST` and `PATCH /v2/products` accept it; `/v1` doesn't change. `GET /v2/products` doesn't search by meaning: it's a list with exact filters and a sort order, and with a cache, while search by meaning is approximate, by likeness, and needs the model in the API; it lives in the two doors that need it, the assistant and MCP.

The vectors are computed by a small model that runs on your computer, for free and with no other account (the Claude API doesn't compute embeddings): `Xenova/paraphrase-multilingual-MiniLM-L12-v2`, in q8, with Transformers.js (`@huggingface/transformers`, `src/embeddings.ts`), pinned to a commit of its repository on Hugging Face (`EMBEDDING_REVISION`, the one of 2025-07-22), like an exact version in `package.json`: if its files changed, the new vectors would stop being comparable with the stored ones. It isn't in the image: it's downloaded the first time it's needed (about 135 MB, about 30 seconds) into `MODELS_DIR` (by default `./models`, in `.gitignore`; in Compose, the `models` volume, which the API and the worker share and which survives `docker compose down`), and loaded into memory with the first request that needs it (after that, in a second, and with no internet). By its name, Transformers.js 4.3.2 asks huggingface.co every time it loads it whether the model has a tokenizer (about the `main` version, even when the pinned one's files are already stored): two requests on every load, and with no internet, an error. That's why, when the pinned version's four files are already in `MODELS_DIR/Xenova/paraphrase-multilingual-MiniLM-L12-v2/<revision>/` (where Transformers.js downloads them), the shop gives it that folder's path instead of the name (`modelSource`), and with a folder it asks nobody; if one is missing, by its name, which downloads them. Creating a product, or changing its name or description, clears its old vector (`embedding = NULL`, in the same `UPDATE`) and saves a `product-vector` outbox event in the same transaction; the worker gets it through the queue and saves the new vector (if the product changes again meanwhile, it doesn't save the old one). Changing the price doesn't touch the vector. For the products that were already there, `npm run embeddings` computes the missing ones, 32 at a time (`npm run embeddings -- --all`, all of them again); in Compose, `docker compose exec worker node scripts/embeddings.ts`. `SEMANTIC_SEARCH` turns it on (`yes`, as in the tests) or off (`no`, unless told otherwise: `search_products` searches by name, as in `49`, the worker computes no vectors and nobody loads the model). The `search_products` tool, the assistant's and MCP's (`searchCatalogue`, in `src/assistant/tools/search-products.ts`), does a hybrid search: first, the products that have the query in their name (also the ones with no vector yet, with `distance: null`), and then the five nearest by meaning (`ORDER BY embedding <=> $vector LIMIT 5`, with Drizzle's `cosineDistance`), each with its description and its `distance` (from 0, the same, to 2, the opposite). The first part, because an embedding model understands sentences and not always a lone word: here "mug" finds the Mug first (0.226), but in the Spanish shop «taza» left the Taza out of the five nearest. Its description for the model changes with `SEMANTIC_SEARCH`. With Compose, `docker compose exec worker node scripts/embeddings.ts` and ask the assistant "what should I get for the cold?", or call `search_products` through MCP with a key.

Memory, measured on 2026-11-21 on the author's Mac (Colima, arm64; with `docker stats`, after restarting the shop): the API goes from about 188 MiB to 566 when it loads the model, and the worker from 151 to 532; each process that loads it adds about 380 MiB. With the API and the worker loaded and Docker limited to 2 GB (what Colima gives unless told otherwise), opening one more process made the system kill the API for lack of memory (code 137): that's why `.env.example` has it off (`SEMANTIC_SEARCH=no`): before setting it to `yes`, give Docker 4 GB (`colima stop && colima start --memory 4`). `.env.production.example` has it off too: on Phase 8's 2 GB machine, leave it that way; on a server with memory to spare, `yes` and, once, `docker compose -f compose.production.yaml exec worker node scripts/embeddings.ts`. The image weighs more because of Transformers.js: 580 MB for `50`'s, 1.23 GB for `51`'s as it is and 669 MB removing what Linux doesn't use (the `Dockerfile` deletes, in the same `RUN` as `npm ci`, `onnxruntime-node`'s programs for macOS, Windows and the other processor, and `onnxruntime-web`, the engine for browsers). `npm run check-embeddings` tries the real model, with no database (it isn't part of `npm test`, which uses a fake embedder, `test/fake-embedder.ts`: a bag of words in 384 dimensions): it shows the nearest ones to four questions and fails if, for "something for the cold", the first three aren't warm clothes, or if, once loaded, its files aren't where `modelSource` looks for them. On the author's Mac: Hoodie (0.477), Blanket (0.492), Scarf (0.514), Wool hat (0.529) and, fifth, the Hand fan (0.547): the model understands what it's about (the temperature), not always which way. `npm run db:many-vectors` fills a separate table, `test_vectors`, with 50,000 vectors grouped in 500 topics (each one a random centre plus a little noise), which look like a real model's (`-- --random`, fully random: HNSW's worst case; `-- 100000`, that many; `-- --drop`, drops it), builds its HNSW index, shows the two `EXPLAIN ANALYZE` plans of the search's query, with the index and without it, and measures its recall: of the true 10 nearest to 20 new vectors, how many the index finds with `hnsw.ef_search` at 40 and at 100; in Compose, `docker compose exec api node scripts/many-vectors.ts`. On the author's Mac (Colima, 4 GB), on 2026-11-21: grouped, 7 s to fill it, 11 s for the index, 0.5 ms with the index against 22.6 ms reading the whole table, and a recall of 93% with `ef_search` 40 and 98% with 100; at random, 39 s for the index and a recall of 12% and 27%, because in 384 dimensions random vectors are all at almost the same distance from each other. The new tests are in `test/embeddings.test.ts` and `test/model-source.test.ts`.

From `52-rag`, the assistant answers about shipping, returns, payments and the account with what the shop says, and not with what the model thinks it knows: that's RAG (retrieval-augmented generation). The help pages are in `help/` (`shipping.md`, `returns.md`, `payments.md` and `account.md`, in Markdown; the returns policy and delivery times are this practice shop's own), and `npm run help` (`scripts/help.ts`, `src/help.ts`) splits them into chunks, one per `##` section (16 in all), each with its page's title and its section's, computes each chunk's vector with the same model as the products and swaps the ones in the `help_chunks` table for the new ones, in a transaction (with `LOCK TABLE … IN EXCLUSIVE MODE`, so two loads at once don't leave the chunks twice). It can run as many times as needed: after changing a page, or after turning semantic search on. With `SEMANTIC_SEARCH=no` it saves the chunks without a vector. Migration `015` creates the table (`page`, `title`, `section`, `text`, `embedding vector(384)` and `search`, a `tsvector` PostgreSQL computes by itself: `GENERATED ALWAYS AS (to_tsvector('english', …)) STORED`) with an HNSW index (`vector_cosine_ops`) and a GIN one for `search`, with its drizzle-kit snapshot (`drizzle/0012_help.sql`). The worker loads the help when it starts if the table is empty, so with Docker Compose there's nothing to do the first time; after changing a page, `docker compose up --build` and `docker compose exec worker node scripts/help.ts`. Without Docker, `npm run help`. The new tool, `search_help` (`{ question }`, in `src/assistant/tools/search-help.ts`, "Searching the help…" in the `tool` event), returns the three chunks nearest to the question (`ORDER BY embedding <=> $vector LIMIT 3`), with their page, their section and their text (at most 1500 characters). It always returns three, even if the help says nothing about the question. With semantic search off, or with the chunks without vectors, it searches by words, with PostgreSQL's full-text search (`search @@ websearch_to_tsquery('english', $1)`, sorted by `ts_rank`): it only finds the sections that have all the words (with `or` between them, one is enough), so its description for the model asks for two or three keywords instead of the question. The chunks reach the model as the API's `search_result` blocks (`source`, `title` and `content`, with `citations: { enabled: true }`): that way its answer cites which chunk each sentence comes from (the `citations` on its text blocks, which the shop joins into a single text). And the answer, in JSON and in the `end` event, carries `sources`: the sections it cites (`{ page, title, section }`, without repeats and in the order it cites them; empty if it cites none, as in an "I don't know", or if the model refused). They come from those citations: the shop looks each one up, by its `source` and its `title`, among the chunks `search_help` returned (a citation of something it wasn't given doesn't count), so each section's data is the shop's own; and an answer that doesn't say where it got something from has no sources, even if the model read three sections to write it. The instructions ask it to answer only with what the results say, to say which page it takes it from and, if they don't answer the question, to say so and suggest the support address the pages give (`support@shop.example`), without guessing. Through MCP, `search_help` is there for any key, with the same function (`lookUpHelp`) and the chunks in JSON, with their `distance`. With the real model (on 2026-11-21, on the author's Mac), the longest chunk has 118 word pieces (the model's tokens), and for "Can I return a mug I do not like?" the results were "Products that can't be returned" (0.577), "Returning a product" (0.755) and "If the payment fails" (0.757); for "Can I pay with PayPal?", the three sections of `payments.md` (0.459 to 0.533); and for "Do you have a physical shop where I can go and see the products?", which the help doesn't answer, "Invoices" (0.694), "What you can do with your account" (0.705) and "Returning a product" (0.766): the nearest neighbours always exist, even when they're further away. By words, none of the three questions finds anything, and "return product" does. The fake model (`test/fake-model.ts`) now sends text blocks with citations (`citedBlock()`, and `citations_delta` in the stream) and, like the API, answers 400 to a `tool_result` that mixes `search_result` with other blocks or to citations turned on in some and off in others. The new tests are in `test/help.test.ts`.

From `53-production`, the shop knows what the assistant costs it. Every call to the model (every round of the assistant and every description the worker writes, further down) leaves a `call to the model` line in the log, with the `requestId` (or the product, in the worker), the model, the message id, the `usage` with the four kinds of token the API charges (`input`, `output`, `cacheRead` and `cacheWrite`) and the cost in dollars, `costUsd` (`src/assistant/cost.ts`): (input × input price + cacheWrite × cache write price + cacheRead × cache read price + output × output price) / 1,000,000. The prices, per million tokens, are in `src/config.ts` (`PRICES`, from Claude's pricing page, checked on 2026-11-21): for `claude-haiku-5-5`, $0.10 for input, $0.50 for output, $0.125 to write to the cache (1.25 times the input, with the 5-minute cache) and $0.01 to read from it (0.1 times), the prices for requests of up to 100,000 input tokens (the shop doesn't come anywhere near it); `claude-sonnet-5-5` and `claude-opus-5-5` are there too, and with a `MODEL` without a price the shop doesn't start. The answer, in JSON and in the `end` event, carries the four in `usage` (`{ input, output, cacheRead, cacheWrite }`): with the cache, the instructions and the tools move from `input` to `cacheRead`. The new metrics (`src/metrics.ts`): `shop_ai_tokens_total`, by `model` and `kind` (`input`, `output`, `cache_read`, `cache_write`); `shop_ai_cost_dollars_total`, by `model`; and the histogram `shop_ai_time_to_first_token_seconds`, which measures in streamed answers how long it takes from when the shop starts asking the model until it sends the customer the first piece of text (with tools, with the rounds before it inside). The "The shop" Grafana dashboard has two more panels: the AI cost in the last hour, by model, and the time to first token, p50 and p95. In the traces, every call to the model is an `anthropic.messages.create` span inside the request's (or the job's, in the worker): the SDK itself (1.8.0) makes it with the provider `src/instrumentation.ts` registers, with OpenTelemetry's attributes for generative AI (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, which includes the cache ones, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.response.id` and, when streaming, `gen_ai.response.time_to_first_chunk`) and why the model stopped, in `anthropic.message.stop_reason`; without the conversation's content, which is the customer's (`openTelemetry: { traces: { contentMode: 'metadata_only' } }`, in `src/assistant/client.ts`). Under it, undici's span with the HTTP request to the API.

On top of the question limits, each customer has a token budget per day (`src/assistant/budget.ts`): `DAILY_TOKEN_BUDGET`, 100,000 by default, adding up everything the model reads (whether it comes from the cache or not) and what it writes. That's about 20 questions (a question with one tool is two calls, about 4,500 tokens, estimated), and at Haiku 5.5's prices they cost at most 5 cents of a dollar a day (if they were all output) and, with what is really spent, nearly all input, about 1.2 cents. It's checked before calling the model, right after the question limits, and charged after every call; a stream the customer cuts halfway is charged with what's known of it (the whole input, from its first event). Past the budget, a 429 `budget-exhausted` with `Retry-After` until 00:00 UTC, without calling the model. It lives in the limits' Redis (`budget:<customer>:<day>`, with `INCRBY` and `PEXPIREAT`, in `src/redis-store.ts`; without Redis, in memory), and if Redis doesn't answer in 200 ms it closes, because it protects money: a 503 `budget-unchecked` with `Retry-After: 5`. If what fails is charging, the answer arrives all the same (it's already paid for), with a warning in the log. `withinTime`, the limits' bounded wait, moves out of the limiter to serve both.

The request to the model carries caching (prompt caching): `cache_control: { type: 'ephemeral' }` on the instructions, which become a `system` block to carry it (`src/assistant/conversation.ts`). The API reads `tools`, `system` and `messages` in that order, and stores what goes in front of the mark, so a mark at the end of the instructions stores the tools and the instructions together, which are the same in every question; the conversation, different every time, isn't marked. Whether Claude Haiku 5.5 stores anything depends on what goes in front of the mark reaching its minimum, 512 tokens according to the caching documentation: below that, `cache_creation_input_tokens` and `cache_read_input_tokens` stay at 0, without any error. The lesson will measure it with real calls. Counted without calling the API, an estimate: the instructions have 2,300 characters and the three tools, as JSON, 3,052; at about 4 characters per token in English, about 575 and 765 tokens, plus the 286 the API adds when there are tools (Haiku 5.5's, according to the pricing page): about 1,600, well above the minimum.

`POST /v2/products/{id}/description` (admin only, `products:manage`) asks the model for a product's description, in the background: it answers 202 `{ productId, status: "queued" }` with the product's `Location`, 404 if it doesn't exist and 503 `assistant-not-configured` without a key. The route doesn't call the model: it saves a `product-description` outbox event (`requestDescription`, in `src/data.ts`), and the worker does it with the queue and its retries (`src/assistant/description.ts`, with its instructions in `src/assistant/description.md`; `src/queue.ts` loads it with `import()` only when it gets one, so the queue doesn't bring the SDK client to every process that uses it). It's one call, without tools, with the product's data as JSON; the text is checked with the same schema as a description written by hand (1 to 500 characters): if it isn't valid, the job fails and BullMQ repeats it. It's saved with `updateProduct`, which, like any description change, deletes the product's vector and requests the new one (lesson 5). A refusal from the model goes to the log and isn't repeated. For many products at once, the Claude API has Message Batches (at half price, with the results within 24 hours).

The evals are in `evals/`: 12 cases (`evals/cases.ts`), questions from Carmen with what is checked for each one (`evals/graders.ts`): that it calls `get_order` with her order's number; that it gives no data about order 22, which is Pablo's, not even if it's asked with a story (injection); that it says it doesn't know when the help doesn't say (a physical shop, a phone number); that `sources` has the returns page or the shipping page; that it uses `search_products` before talking about a product or its price; and one, marked `judge` in the table, that another model grades with a short rubric (LLM-as-judge, with structured outputs: `messages.parse` and `zodOutputFormat`). The rest are code: exact, always the same and free. `npm run evals` (`evals/run.ts`, which runs `evals/evaluate.ts`) runs them against the real model, one after the other, inside the process and without HTTP (that way it sees which tools the model asks for and with what), with the shop's instructions, tools and model, as Carmen, and writes a table: the case, whether code or the judge decides it, whether it passes (and, if not, why), its tokens and its cost, and the total. Without `ANTHROPIC_API_KEY` it doesn't start, and says so. It needs the shop's database with the practice data and the help loaded; with Docker Compose, it runs in the API's container, which sees both and has the key (the image now carries `evals/`):

```sh
docker compose exec api npm run evals
```

Without Docker, `npm run evals`, with your `.env`. What it costs, estimated until it's measured: about 25 calls, of about 2,000 input tokens and 200 output ones, under a cent of a dollar per run (about $0.008 without the cache; less with it). It doesn't go in CI: the tests (`test/evals.test.ts`) run the same cases against the fake model, with a good answer for each case (which has to pass) and bad answers for some (which have to fail), so the graders and what runs the evals keep working without a key. The fake model can now say the cache's tokens (`cacheRead` and `cacheWrite`, in its `usage`).
